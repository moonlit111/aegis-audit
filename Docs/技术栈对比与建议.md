本文件比较课程推荐的 Rust 后端、TypeScript + Svelte 前端、Connect RPC，与原方案的 Python + FastAPI 后端、TypeScript + React 前端、REST + SSE。资料核查日期为 2026-09-07；本次未进行本项目性能或协议互通实测。

**已确定采用：Rust + Axum/Tokio 承担核心后端，TypeScript + Svelte 构建前端，Connect RPC 提供业务接口与进度流，SQLite 保存任务与证据元数据；Python/Java 用于必要的工具桥接。** 用户已确认这一组合，[具体实现方案](具体实现方案.md)作为编码依据。应用实现尚未开始，工具与依赖版本在实际验证后固定。

几项技术属于不同层次：Rust/Python 是后端语言，Axum/FastAPI 是 HTTP 服务框架，Svelte/React 是界面技术，TypeScript 可用于两种前端，Connect RPC 是通信协议及工具库。Svelte 和 React 都能使用 Connect 的 TypeScript 客户端，后端语言与前端框架也可以独立搭配。

后端比较如下。

| 方面 | Rust + Axum/Tokio | Python + FastAPI | 对本项目的意义 |
| --- | --- | --- | --- |
| 状态与类型约束 | 编译期类型检查、枚举和所有权有助于约束状态及并发访问 | 类型提示、Pydantic 运行时校验和测试支撑结构化接口 | 任务、证据和验证状态多，Rust 便于建立明确约束；两者都要验证语义 |
| 模型与安全生态 | 可直接调用模型 HTTP API、执行 CLI，也有相应库；部分 Python 模块需适配 | 模型 SDK、智能体实验和安全脚本通常更容易直接复用 | Python 集成代码更少，Rust 可通过脚本/进程接口保留现有工具能力 |
| 并发与资源 | Tokio 支持异步 I/O，原生代码适合控制任务和进程；没有语言级 GC | 异步服务可以满足大量 I/O 任务，CPU 密集工作通常交给进程或原生工具 | 本项目主要耗时预计在模型、反编译与模糊测试；更换语言不直接加快这些外部工作 |
| 修改与调试 | 编译检查能提前发现一类错误；所有权、异步边界与依赖配置增加实现复杂度 | 代码修改与验证路径直接，运行时错误更多依赖测试发现 | 由 Codex 承担实现后，不必按组员对语言的熟悉程度来限制选择 |
| 部署 | 主服务可构建为平台可执行程序，需匹配目标与构建环境 | 需 Python 环境和依赖，虚拟环境或容器可以固定 | Rust 主程序分发较集中；两者仍需 Ghidra/JDK、模糊测试器等外部依赖 |
| 功能实现 | 可实现全部课程功能 | 同样可实现全部课程功能 | Rust 本身不会提升漏洞检出率，Python 也不会限制可审计语言 |

Rust 的优势主要作用于自研控制程序：状态管理、接口约束、并发协调和原生执行管理。Python 的优势主要在直接调用现有库、快速组合研究逻辑。Python 常规代码同样有内存管理；不能简单把比较说成 Rust 安全、Python 不安全。目标隔离、权限检查、模型输出校验和进程回收都需要单独实现。

本项目不训练大模型，模型运行在 API 服务端；Ghidra、Semgrep、AFL++、UPX 也可作为外部工具调用。因此采用 Rust 主后端并不要求重写这些工具。必要的 Python 模块以受控适配脚本接入，传递结构化结果与产物；核心任务、智能体协调、证据和接口逻辑仍由 Rust 实现。

前端比较如下。

| 方面 | Svelte + TypeScript | React + TypeScript |
| --- | --- | --- |
| 组件表达 | 模板、样式和响应式状态紧密结合，常见界面的组件代码较集中 | 使用组件、JSX 和 Hooks，状态及副作用组织方式明确 |
| 更新机制 | 编译器生成响应式更新代码 | 使用 React 的渲染和更新机制，组件生态成熟 |
| 生态 | 适合仪表盘、表单、日志与详情界面；可接入通用图和代码编辑器库 | 表格、图编辑、代码展示及复杂界面的现成组件选择通常更多 |
| 本项目适配 | 任务列表、实时进度、证据与报告页面都可以实现 | 同样可以实现，没有功能上的必然差距 |
| 主要取舍 | 适合从零构建集中、清晰的项目界面 | 若已有大量 React 组件要复用，会更有优势 |

两者均适合本项目。日志量大时都需要限制渲染数量、分页或虚拟化；不能凭框架名称保证某个界面更快。当前没有已有 React 产品需要迁移，因此选定 Svelte，并保留 TypeScript。采用 Vite 构建客户端界面，暂不引入额外的服务端渲染框架；构建出的静态文件可以由 Rust 后端提供。

通信方式比较如下。

| 方面 | Connect RPC | REST + SSE |
| --- | --- | --- |
| 接口定义 | 使用 Protocol Buffers 定义服务和消息，生成客户端/服务接口 | 使用 HTTP 路由和 JSON；FastAPI 可从模型生成 OpenAPI，并进一步生成 TypeScript 客户端 |
| 前后端一致性 | 共享协议和生成代码有助于减少字段、枚举及方法漂移 | 同样可以通过 schema、生成代码和测试保证一致；不能理解为没有类型约束 |
| 实时进度 | 使用服务端流式 RPC 传送事件 | 普通 API 处理操作，SSE 单向推送事件 |
| 工具链 | 需要管理协议、代码生成及运行库的兼容版本 | 通常起步更直接，HTTP/JSON 与 EventSource 易于检查 |
| 调试 | 普通 Connect 请求支持常规 HTTP 与 JSON 调试，流式请求有自己的帧格式 | JSON 与 SSE 事件直观 |
| 项目需要 | 适合任务、发现、证据等结构化接口和进度流 | 同样足以实现课程界面，协议性能通常不是挖掘瓶颈 |

Connect RPC 不会自动完成任务持久化、事件补读和工具进程取消。服务端仍需保存事件游标，客户端断线后补读；显式取消任务与停止接收进度分别处理。大文件上传/下载可使用同一 Axum 服务的 HTTP 路由，其余业务使用 RPC。

本次核查发现，[官方 connect-rust 仓库](https://github.com/connectrpc/connect-rust)已经提供 Rust 实现，支持 Tower/Axum 集成和普通/流式调用。[最新已发布版本 v0.9.0](https://github.com/connectrpc/connect-rust/releases/tag/v0.9.0) 发布于 2026-08-25，README 标记为 pre-1.0，并声明最低 Rust 1.88。上游声明通过协议一致性测试，这不等于本项目已经完成验证。应锁定运行库及生成器版本，用真实浏览器客户端检查普通请求、服务端流、错误与取消，而不是自行重写 Connect 协议。

可组合的方案如下，避免把后端和前端误当成不可拆分的套餐。

| 组合 | 适用条件 | 本项目判断 |
| --- | --- | --- |
| Rust + Svelte + Connect RPC，辅以必要工具脚本 | 重视明确的数据契约、任务控制和原生主程序，同时复用安全工具 | 已选定，贴合课程建议 |
| Python/FastAPI + React + REST/SSE | 重视直接复用 Python 模块和 React 组件，追求较少集成代码 | 功能可达，是合理替代方案 |
| Python/FastAPI + Svelte + REST/SSE | 需要 Python 的直接集成能力，同时偏好 Svelte 界面 | 可行，前端选择不依赖后端语言 |
| Rust + React + Connect RPC | 需要 Rust 核心，又有适合的 React 组件要复用 | 可行，当前没有必须选 React 的依赖 |

推荐 Rust 组合的依据是本项目核心需要长期运行的任务、证据状态、跨平台执行控制和一致的接口，而模型与分析工具可以通过 API/进程边界复用。推荐 Svelte 是因为界面从零实现，主要由任务、日志、代码、证据和报告组成。推荐 Connect 是因为这些对象适合统一消息与服务定义，且官方 Rust 与 TypeScript 实现已经存在。课程原文允许自选技术栈；采用推荐栈不自动证明创新，也不能替代 R01—R15 的功能与测试证据。
