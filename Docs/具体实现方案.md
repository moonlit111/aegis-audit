# 具体实现方案

本文件描述当前代码结构和需要遵守的契约，不把设计目标当成已完成能力。需求及最新缺口统一见[课程要求与进度](课程要求与进度.md)，实测范围见[测试与验收方案](测试与验收方案.md)。

## 1. 定位与架构

AegisAudit 面向单机、单操作员的软件审计，不实现多用户账号、团队共享或渗透攻击链。支持 Python、Go、C/C++ 源码和 PE x86/x64、ELF x86_64 静态分析；Windows 宿主不原生执行 ELF。首版漏洞范围为注入、路径遍历、认证/授权、内存越界，这是项目选择，不是老师指定的全部漏洞清单。

```text
Svelte 浏览器
  -> Connect RPC / HTTP 文件接口
  -> Rust 控制服务 -> SQLite + 按哈希保存的产物
                  -> 多智能体编排 -> DeepSeek API
                  -> 持久化工作队列
  <- Windows 执行器领取任务、心跳、回报
       -> Tree-sitter / Ghidra / Semgrep / UPX 静态工具
       -> FLOSS / IDA + D-810 智能体恢复链路
       -> Windows 宿主机 VERIFY 运行器
```

控制服务独占数据库写入，执行器通过协议领取任务和提交证据，不直接修改数据库。模型密钥由控制服务保管，不提供给目标或执行器。前端生产资源由 Rust 服务提供，不需要独立 Node 或数据库服务。

## 3. 导入、分析与保护

源码目录由浏览器打包或上传 ZIP；HTTPS Git 固定最终提交，不自动执行 hooks、安装脚本或递归子模块。导入检查相对路径、符号链接、大小写/Unicode 冲突、数量及大小，记录排除原因。只读分析不等于运行目标程序。

Tree-sitter 提取函数、模块、位置、语法分支及调用候选。动态分派、宏、跨模块关系无法确定时保留推断/未知，不宣称全程序污点分析。Ghidra Headless 导出函数、伪代码、入口/RVA、基本块、P-code、字符串和引用，保留反编译失败、截断及原始日志；伪代码不是可直接编译的 C，地址映射主要在函数级。

| 保护能力 | 当前行为 | 边界 |
| --- | --- | --- |
| 识别 | [protection.rs](../crates/application/src/protection.rs)检查节区签名、熵、入口、导入等 | 签名或高熵只是线索，不证明保护已处理，也不证明闭源资格 |
| UPX | 固定 5.2.1，由 REVERSE 计划调度；保留原件、派生产物、哈希、节区/入口映射及失败 | 只支持 UPX 可处理格式；派生文件作为后续工具输入，不修改原始目标 |
| 字符串恢复 | FLOSS 3.1.1 用于 PE x86/x64 模拟执行；另有内建 XOR/Base64 启发式候选 | 恢复字符串进入伪代码注释和证据，不证明全部混淆已还原 |
| 反编译与代码级优化 | Ghidra 12.1.3 输出伪代码；可选本机 IDA/Hex-Rays + D-810-ng 按规则优化微码 | IDA 由使用者提供并真实探测；D-810 命中数和前后伪代码必须留痕，不能宣称通用解混淆 |

REVERSE 根据保护特征、工具能力和已有产物提交恢复计划；服务端校验工具、输入类型、步骤数（最多 8 步）、输入哈希和产物归属后创建 `RECOVER` 工作项。执行结果、失败原因、原始/派生哈希和可读伪代码进入后续语义审计与报告。模型不能提供任意命令或路径。

## 4. 智能体与审计

六个角色可以共用一个模型服务，不要求六个不同模型，也不是开发成员 A/B/C。

| 角色 | 当前职责 |
| --- | --- |
| PLANNER | 根据目标、入口及现有结构安排审计优先级 |
| REVERSE | 二进制任务中识别保护特征、规划 UPX/FLOSS/Ghidra/IDA-D-810 恢复步骤，并评估恢复质量 |
| AUDITOR | 阅读代码、追踪输入/危险操作/防护，提出候选及关键逻辑标注 |
| REVIEWER | 在新上下文中根据原始代码独立复核，记录支持、反证和不确定性 |
| VERIFIER | 生成受校验的验证配置或说明缺少的正常运行条件，不自行写入成功状态 |
| REPORTER | 根据已存证据整理解释和修复建议，不补写执行结果 |

[Corpus](../crates/application/src/audit.rs)提供 `inspect_target`、`read_unit`、`read_span`、`search_code`、`query_graph`、`scan_rules` 和 `key_logic_candidates`。查询限于当前快照；读取有长度/轮次预算。无规则告警的程序单元也会进入语义审计，Semgrep 命中不自动成为已确认漏洞。

发现按“可控输入 -> 危险操作 -> 防护缺口 -> 前提/影响”组织。服务从真实代码和有效行范围形成引文，拒绝外部单元、越界位置及伪造引文。独立复核不继承审计角色的整段对话；同模型仍可能重复判断错误，必须结合修复对照和真实执行。

认证、加解密、注册标签独立于漏洞发现，安全函数也可被标注。候选模式、调用关系和模型语义共同提供依据，不能只按名称贴标签。人工修改带修订号，保留原始证据、冲突检测和历史。

模型配置使用官方 DeepSeek 接口，当前默认 `deepseek-v4-flash`；记录实际模型标识、时间、调用、失败和 token，用量未知不记作零。产品不再限制模型上下文大小和单次输出 token：`max_output_tokens=0` 时不发送 `max_tokens`，由提供方决定；仍保留任务时限、工具轮次和模型调用数限制。JSON 解析只取模型输出的第一个 JSON 值，提供方追加的系统提示不参与协议，但原始响应仍完整归档。

## 5. 数据与证据约束

| 对象 | 必须保持的关系 |
| --- | --- |
| Project / Snapshot | 导入形成不可变版本；源文件、来源/提交和目标哈希一致 |
| Artifact / ProgramUnit / ProgramEdge | 原始与派生产物分开；源码用文件/行号，二进制用原文件/地址/RVA；推断边不冒充确定边 |
| AuditRun / WorkItem / AgentTask / ModelCall | 任务、角色、尝试、租约、状态、工具及用量可追溯 |
| Finding / Review / LogicAnnotation | 发现、独立复核、人工修订分别保存，引用本任务有效代码和产物 |
| RuntimeRecord / RuntimeResult | 固定原分析、目标、配置、范围、运行观察和回收证明 |
| RunEvent / Report | 事件有持久化序号；报告引用已经保存的事实，不由浏览器内存或模型口述决定 |

状态与事件在数据库事务中更新；创建请求使用幂等标识，人工修订检查版本。执行器回报校验 attempt 和租约，迟到结果不能覆盖新尝试。浏览器断线只停止订阅；显式取消才要求回收进程。`COMPLETED` 表示工作结束，不表示目标安全。

同一快照同时只允许一条结构分析或漏洞审计流程（包括排队、等待执行器和取消回收期间）。不同请求编号提交相同配置时返回已有任务，切换范围或预算时返回冲突；任务结束后通过“重新运行”明确新建一轮。快照主操作随状态显示开始审计、查看进度或查看结果，“仅反编译 / 仅结构分析”为次级入口。

二进制审计依次展示目标准备、逆向与反编译、审计策略、审计与复核、验证方案和结论汇总。目标准备不表示反编译完成。审计启动时可复用同快照已完成的原始二进制 Ghidra 结果：校验输入哈希、结果完整性、产物归属、可用工具版本及固定执行参数，为新任务建立代码、调用边与日志引用，并记录 `analysis_reuse` 来源。部分结果、派生输入或不同工具配置不命中；逆向智能体仍可按证据补充恢复。源码审计保留原有解析和 Semgrep 流程。

没有启动外部进程的工作，应明确记录“无待回收进程”；启动过但未确认终止的工作不能伪造回收。执行器重启时必须先完成旧任务回收或幂等重报，不能把未知进程状态当作成功。

## 6. 当前 Windows 运行契约

产品外层配置是 [RuntimeConfig](../crates/domain/src/runtime.rs)；客体桥接配置是 [WindowsRuntimeConfig](../crates/application/src/windows_runtime.rs)，两者不能混为同一 JSON。后者携带 schema/config 版本、目标/配置摘要、入口、输入、次数、超时及环境要求。

| 产品适配器 | 当前用途 |
| --- | --- |
| `WINDOWS_PYTHON_CALL` | 目标 Python 函数的组件验证；不支持 globals/kwargs，拒绝静默丢弃输入 |
| `WINDOWS_NATIVE_SOURCE` | 单入口 C/C++ 构建与执行；不能推定所有项目构建系统可用 |
| `WINDOWS_ORIGINAL_PE32` / `WINDOWS_ORIGINAL_PE64` | 匹配架构的原始 EXE 命令行执行；不等同于 GUI/DLL/服务适配 |

**产品支持 VERIFY 和最小化的预构建 libFuzzer FUZZ。** UI、配置、执行器、崩溃产物、两次复放与报告已贯通；崩溃按签名去重并调用 libFuzzer `-minimize_crash` 缩减。`CVE-2016-5180` 已完成漏洞版/修复版对照复现，最小崩溃输入为 `\.`。TinyInst 仍是独立引擎实验。

FUZZ 复现成功后，服务自动归档最小崩溃输入、受限 Python 复现器和结构化利用证据，并把源任务报告的 `exploitation` 更新为 `COMPLETED`。该闭环证明稳定触发内存安全异常，不外推为任意代码执行；复现器只能用于授权本地目标。

VERIFY 固定正常输入一次和探测输入 2-5 次，单次目标时限 1-15 秒。观察器与适配器匹配；Windows 目前不支持 `RETURN_CANARY`。当前源代码客体编译仅使用 Zig `-O0`，虽然范围标签为 `INSTRUMENTED_BUILD`，不能据此声称已经启用 ASan 插桩。

[Windows 宿主机运行器](../crates/application/src/windows_host.rs)使用 Job Object 管理目标进程树，提供固定输入、超时、取消、环境白名单和临时目录；结果记录实际平台为 `WINDOWS_HOST`。Job Object 不是文件或网络隔离，只导入和执行有权测试的目标。

当前 `RuntimeResult.image_id` 对 Windows 表示执行策略/版本组合的摘要，**不是 Docker 镜像 ID，也不是完整客体镜像的内容哈希**。报告应连同工具版本、平台、会话、目标/配置及原始日志理解，后续应显式区分这些语义。

运行结论区分组件验证、异常复现、未复现、错误、取消及未知回收。崩溃不能推导任意代码执行；当前没有完整利用证据时，`exploitation` 保持 `NOT_RUN`。

## 7. 报告、部署与后续扩展

JSON 是结构化事实，HTML/Markdown 是阅读形式；展示漏洞、严重等级及理由、证据链、修复建议、人工修订、覆盖缺口和运行范围。目标文本和模型内容按不可信文本处理，HTML 转义。数据库迁移见 `migrations/0001-0005`；备份时同时保留数据库/WAL 和 blobs。

Rust 控制服务加执行器、SQLite 和静态前端足够满足单机工作流，不另建微服务集群或向量数据库。技术选择及复用边界见[开源参考与依赖](开源参考与依赖.md)。

当前架构已移除 Sandbox 运行链路，VERIFY 与预构建 libFuzzer FUZZ 直接在 Windows 宿主机执行。普通权限、Job Object、超时/取消、临时目录、最小环境、输入哈希、崩溃输入与复放仍是必要契约；宿主结果不得伪装成沙箱或容器证据。`CVE-2016-5180` 已完成漏洞版/修复版对照复现、崩溃缩减和受限自动利用证据闭环；正式软件验收也不能用自制恢复夹具抵扣。
