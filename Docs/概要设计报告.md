## 2. 系统总体设计

### 2.1 设计目标与原则

| 目标 | 设计含义 |
| --- | --- |
| 可信 | 结论必须可回溯到真实代码与真实执行；模型不能自证成功 |
| 可控 | 模型只做判断，工具与目标运行由受控执行器完成 |
| 可部署 | 单机、单操作员、无外部服务依赖即可运行 |
| 可扩展 | 新语言、新工具、新适配器可增量接入而不改协议骨架 |
| 诚实 | 未完成、未覆盖、不确定必须显式表达，不伪造成功状态 |

### 2.2 总体架构（逻辑视图）

系统分为三层 + 一条外部依赖：

```text
                     ┌───────────────────────────────────┐
   表示层            │  Svelte 浏览器工作台（单页应用）   │
                     └────────────────┬──────────────────┘
                                      │ Connect RPC / HTTP 文件接口
                     ┌────────────────▼──────────────────┐
   控制层            │  Rust 控制服务（server）           │
                     │  业务编排 / 状态机 / SQLite / 队列  │
                     └───────┬────────────────┬──────────┘
                             │ 内部执行协议    │ HTTPS
                     ┌───────▼──────────┐  ┌──▼─────────────┐
   执行层            │ Windows 执行器    │  │ DeepSeek API   │
                     │ 静态/恢复/动态工具 │  │（模型审计）    │
                     └──────────────────┘  └────────────────┘
```

核心不变量：控制服务是数据库的唯一写入方；执行器与浏览器都不直连数据库；模型凭据只存在于控制服务。

### 2.3 分层职责

| 层 | 组件 | 职责 | 不负责 |
| --- | --- | --- | --- |
| 表示层 | `frontend`（Svelte 5 + TypeScript） | 项目/导入/任务/代码图/审计/运行/模型连接/报告的交互与展示 | 不承载业务判定，不直接写库，不持有模型密钥 |
| 控制层 | `crates/server`（Axum + Tokio + SQLx） | 事务、状态机、队列与租约、模型调用编排、校验、报告、静态资源 | 不执行目标程序，不调用逆向工具 |
| 执行层 | `crates/executor`（Tokio 客户端） | 领任务、跑工具、跑目标、上传产物、回报证据 | 不判定漏洞真伪，不直接写库 |
| 契约 | `crates/protocol` + `proto/audit/v1/audit.proto` | 前后端与执行器共享的唯一协议 | 生成物不手改 |

### 2.4 运行视图（进程与部署单元）

| 进程 | 可执行体 | 实例数 | 说明 |
| --- | --- | --- | --- |
| 控制服务 | `aegis-server` | 1 | 监听 127.0.0.1:7331，提供 RPC 与前端静态资源 |
| 执行器 | `aegis-executor` | ≥1 | 主动向控制服务注册、拉取工作；可多实例但受限 |
| 浏览器 | 用户浏览器 | 1+ | 访问工作台 UI |
| 外部 | DeepSeek API | — | 模型审计（可选，纯结构分析不需要） |

执行器并发约束（设计）：单个执行器同一时刻只持有一个活动租约；运行类（`RUNTIME`）工作全局同一时刻只允许一个，且一个尚未确认清理的运行租约会阻塞所有执行器，以保护宿主机资源。

### 3.2 关键模块说明

M2 导入与解析
- 输入：ZIP 包、服务器目录、HTTPS Git 仓库（固定提交）。
- 处理：路径规范化 → 安全检查（相对路径、符号链接、大小写/Unicode 冲突、数量与体积限制）→ 记录排除原因 → 形成不可变快照与清单 → 分派解析工作项。
- 输出：`Snapshot` + `SnapshotManifest`（文件记录 + 排除记录 + 目标哈希 + 提交号）+ `ProgramUnit`/`ProgramEdge`。

M4 保护识别与恢复（差异化能力）
- 识别：节区签名、熵、入口、导入表。
- 规划：REVERSE 角色提交 `RecoveryPlan`（工具枚举 + 输入枚举 + 理由，≤8 步）。
- 执行：计划保存到 `run.summary.recovery`，每次工具调用只创建一个 `RECOVER` 工作项；可选步骤包括 UPX 解包、FLOSS 字符串恢复、Ghidra 反编译和（本机可用时）IDA/Hex-Rays + D-810 优化，顺序由 REVERSE 角色根据真实工具结果决定。
- 输出：派生产物（解包文件、伪代码、字符串）+ 映射关系 + 失败原因。
- 约束：模型不提供命令与路径；派生文件只作为后续输入，不修改原始目标。

M5 多智能体编排
- 角色：PLANNER / REVERSE / AUDITOR / REVIEWER / VERIFIER / REPORTER。
- 机制：任务幂等（run+role+item_key 唯一）、工具轮次预算、上下文隔离、校验-修复回路、受限重试。

M10 工作队列与租约
- 状态：`QUEUED → RUNNING → (COMPLETED|FAILED|EXPIRED)`，支持 `cancel_requested`。
- 授权：`attempt_id` + `lease_token`（数据库仅存哈希）+ 过期时间。
- 规则：迟到结果丢弃；超时不自动重跑；未确认清理阻塞运行类工作。

## 4. 数据设计

### 4.1 数据模型总览

```text
Project 1 ── n Snapshot
Snapshot 1 ── n AuditRun 1 ── n {ProgramUnit, ProgramEdge, RunEvent, Finding,
                                 Review, LogicAnnotation, AgentTask, ModelCall,
                                 RuntimeRecord}
Snapshot 1 ── n WorkItem
AuditRun 0..1 ── n WorkItem
Executor 0..1 ── n WorkItem 1 ── n WorkAttempt
Artifact（内容寻址）被 Snapshot / WorkItem / Report / ModelCall 等引用
```

说明：`WorkItem.snapshot_id` 必填，`run_id` 可空（导入工作项没有审计运行）；`executor_id` 在任务被领取后才写入，因此 Executor 与 WorkItem 是领取绑定关系，而不是项目归属关系。

### 4.2 主要实体与关键字段

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| Project | id, name, created_at | 项目 |
| Snapshot | id, project_id, kind, state, original/normalized/manifest_artifact_id, resolved_revision, target_sha256, file_count, total_bytes, metadata | 不可变分析对象版本 |
| Artifact | id, sha256(64), size, name, media_type | 内容寻址字节对象 |
| AuditRun | id, project_id, snapshot_id, state, scope, unit_count, summary | 一次审计运行 |
| ProgramUnit | id, run_id, snapshot_id, artifact_id, name, path, language, start/end_line, start/end_byte, address, code, quality, metadata | 统一程序单元 |
| ProgramEdge | source_id, target_id, target_name, kind, certainty, line, address | 调用/引用边（区分确定与推断） |
| WorkItem | id, kind, state, capability, input_artifact_id, payload, executor_id, attempt_id, lease_hash, lease_expires, cancel_requested, cleanup_confirmed | 分派任务 |
| WorkAttempt | attempt_id, work_item_id, executor_id, lease_hash, started_at, finished_at, outcome, detail | 尝试审计 |
| AgentTask | id, run_id, role, item_key, status, result, error | 智能体任务 |
| ModelCall | id, model, role, prompt_version, status, token 用量, usage_available, latency, artifact_id | 模型调用留痕 |
| Finding | id, run_id, fingerprint, revision, review_status, verification_status, draft, evidence | 审计发现 |
| Review | id, finding_id, actor, verdict, assessments, evidence, revision | 独立复核 |
| LogicAnnotation | id, run_id, unit_id, tag, subtype, rationale, evidence, revision | 关键逻辑标注 |
| RuntimeRecord | id, run_id, source_run_id, finding_id, status, config, result | 运行验证记录 |
| RunEvent | run_id, seq, kind, message, work_item_id, current, total | 持久化事件流 |
| Request（幂等） | (method, request_id), body_hash, object_id | 幂等键 |

### 4.3 状态机

RunState（`domain::RunState`）

```text
QUEUED / WAITING_EXECUTOR ──▶ RUNNING ──▶ COMPLETED
        │                        │  ├──▶ PARTIAL
        │                        │  ├──▶ FAILED
        │                        │  └──▶ LIMIT_REACHED
        └──▶ CANCELLING ─────────┘
```

- 取消必须经过 `CANCELLING` 再进入 `CANCELLED`——不存在 `RUNNING → CANCELLED` 的直接迁移，因为进程回收需要一个独立阶段（有单元测试固化该约束）。
- 终态（`terminal`）：`COMPLETED / PARTIAL / FAILED / CANCELLED / LIMIT_REACHED`。
- 语义边界：`COMPLETED` = 工作结束 ≠ 目标安全。

SnapshotState：`IMPORTING → READY | PARTIAL | FAILED`。

WorkItem 状态：`QUEUED → RUNNING → COMPLETED | FAILED | CANCELLED | LIMIT_REACHED | EXPIRED`；`CANCELLED` 也可由排队态直接进入，`EXPIRED` 表示租约超时且回收尚未确认。

### 4.4 数据完整性规则（设计约束）

| 规则 | 实现手段 |
| --- | --- |
| 快照不可变 | 快照创建后只读；新版本 = 新快照 |
| 产物完整 | `sha256` 长度 CHECK = 64；按哈希命名落盘 |
| 分析结果可信 | `AnalysisResult::validate` 校验单元/边/覆盖与清单一致 |
| 引文可信 | 引文由服务端从原始代码重建，拒绝越界与伪造 |
| 事件有序 | `run_events` 主键 `(run_id, seq)`，支持 `after_seq` 补读 |
| 幂等 | `requests(method, request_id)` 主键 + `body_hash` 一致性 |
| 引用完整 | 外键约束覆盖 snapshot/run/work_item/artifact |

## 5. 接口设计

### 5.1 对外接口（Connect RPC）

协议共定义 8 个 service，普通请求与事件流同构。

| Service | 主要 RPC | 用途 |
| --- | --- | --- |
| `ProjectService` | CreateProject / ListProjects / GetProject / CreateSnapshot / GetSnapshot | 项目与快照 |
| `RunService` | CreateRun / ListRuns / GetRun / WatchRun(stream) / CancelRun | 运行与实时事件 |
| `ProgramService` | ListUnits / GetUnit / GetGraph / UpdateAnnotation | 程序单元、调用图、标注修订 |
| `ReportService` | CreateReport / GetReport | 报告生成与获取 |
| `ExecutorService` | RegisterExecutor / ClaimWork / Heartbeat / ReportProgress / CompleteWork | 仅执行器内部使用 |
| `SystemService` | GetCapabilities / CheckModelConnection | 能力与模型连通性 |
| `FindingService` | GetAudit / ListFindings / GetFinding / SubmitReview | 审计结果与人工复核 |
| `RuntimeService` | CreateRuntime / GetRuntime / ListRuntime | 运行验证 |
| （含） | — | 见 `proto/audit/v1/audit.proto` 全文 |

文件接口：HTTP 上传/下载用于 ZIP 与产物字节流，受大小与类型限制。

### 5.2 内部执行协议（控制服务 ↔ 执行器）

```text
执行器                                控制服务
  │  RegisterExecutor(caps) ────────────▶│  颁发 executor_token（库中仅存哈希）
  │  ClaimWork(executor_id) ─────────────▶│  返回 WorkLease{work_item_id, attempt_id,
  │                                       │                 lease_token, kind, payload,
  │                                       │                 timeout_seconds}
  │  Heartbeat(...) ─────────────────────▶│  返回 {cancel_requested, lease_valid}
  │  ReportProgress(...) ────────────────▶│  追加 RunEvent
  │  CompleteWork(outcome, artifact, ────▶│  校验 attempt+租约+产物归属 → 落库
  │               processes_reaped)       │
```

关键设计：`payload` 是声明式数据（工具枚举、输入枚举、理由），不是命令行字符串。

### 5.3 三种运行适配器接口（设计契约）

| 适配器 | 输入 | 观察器 | 当前边界 |
| --- | --- | --- | --- |
| `WINDOWS_PYTHON_CALL` | 目标 Python 函数 + args | 与适配器匹配的观察器 | 不支持 globals/kwargs |
| `WINDOWS_NATIVE_SOURCE` | 单入口 C/C++ 源码 | 构建+运行观察 | 不推定任意构建系统可用 |
| `WINDOWS_ORIGINAL_PE32/PE64` | 原始 EXE + 命令行 | 进程观察 | 不等同 GUI/DLL/服务 |

VERIFY 契约：基线 1 次 + 探测 2–5 次；单次 1–15 秒；Windows 无 `RETURN_CANARY`。

### 5.4 错误模型

| 类别 | 处理方式 |
| --- | --- |
| 客户端参数错误 | RPC 错误，明确说明违反的约束 |
| 模型输出不合规 | 校验失败 → 回喂错误信息要求重出（有次数上限） |
| 提供商可重试错误 | 最多重试 1 次 |
| 执行器失联/租约超时 | 工作置 `EXPIRED`；非取消流程的运行置 `FAILED`，不自动重跑 |
| 工具失败 | 记录退出码、日志产物与失败原因，失败也是证据 |

## 6. 关键流程设计

### 6.1 导入到建模

```text
上传 ZIP / 指定目录 / Git URL
   → 路径与安全检查，记录排除项
   → 形成不可变快照（清单 + 目标哈希 + 提交号）
   → 分派解析工作项 → 执行器解析 → AnalysisResult 校验入库
   → 生成 ProgramUnit / ProgramEdge（边带 certainty）
```

### 6.2 审计主流程

```text
CreateRun → 载入 Corpus
   ├─（二进制）REVERSE 提交恢复计划 → 校验 → RECOVER → 恢复产物并入 Corpus
   ├─ PLANNER 排优先级
   ├─ 逐单元 AUDITOR 审计 → FindingDraft 校验 + 引文校验 → 入库
   │    └─ 发现入库后立即由 REVIEWER 以新上下文独立复核
   ├─ 对 VALIDATED 发现（可选）VERIFIER 生成验证配置；生成失败只保留静态证据
   │    动态执行必须另行创建 Runtime 工作项，审计流程不会自动宣称已运行
   └─ REPORTER 依已存证据生成报告（JSON/HTML/Markdown）
```

### 6.3 动态验证流程

```text
选择发现 → 生成/载入 RuntimeConfig（含 fingerprint）
   → 创建运行工作项 → 执行器在 Job Object 中运行基线+探测
   → 收集观察结果与回收证明 → 结论分类（组件验证 / 异常复现 / 未复现 / 证据不足）
   → exploitation 保持 NOT_RUN（无完整利用证据时）
```

## 7. 非功能设计

### 7.1 安全性

| 面 | 设计 |
| --- | --- |
| 模型-执行边界 | 恢复计划不能提供命令或任意宿主路径；VERIFIER 只能提交快照内相对路径和声明式配置，服务端校验后才创建执行任务。恢复、发现、复核、标注和运行配置等严格结构使用 `deny_unknown_fields` 与封闭枚举；规划/报告输出允许附加描述字段，但核心字段仍受校验 |
| 密钥管理 | 模型密钥仅在控制服务；执行器持有自身执行器令牌，控制服务库内只保存令牌哈希 |
| 目标运行 | Job Object 管进程树 + 超时/取消 + 最小环境 + 临时目录；非文件/网络隔离 |
| 路径安全 | 目标路径限快照内相对路径，拒绝绝对路径与 `..` |
| 报告注入 | 目标文本与模型输出按不可信文本处理并转义 |
| 数据完整性 | 内容寻址 + 哈希校验 + 外键 + 校验器 |

### 7.2 可靠性

- 单写锁 + 事务保证状态一致；
- 租约与 attempt 保证迟到结果不覆盖新尝试；
- 幂等键保证重发不产生重复对象；
- 事件流可断线重连并从 `after_seq` 补读；
- 进程回收需显式证明，未确认不冒充成功。

### 7.3 性能与成本

| 项 | 约束 |
| --- | --- |
| 模型调用 | `max_model_calls` 4–2000（默认 240） |
| 程序单元 | `max_units` 1–500（默认 80） |
| 工具轮次 | `max_tool_rounds` 1–100（默认 24；PLANNER 压缩为 ≤1） |
| 运行时限 | 任务 60–86400 秒（默认 10800）；单次目标 1–15 秒 |
| 数据规模 | 单元 ≤50000、边 ≤500000、运行配置 ≤128 KiB |
| 目录规模 | 导入文件数与单文件/总大小上限，超出记录排除原因 |

### 7.4 可维护性与可扩展性

- 语言扩展：在 `source.rs` 增加 Tree-sitter 语法与 `import.rs::language` 映射；
- 工具扩展：新增 `RecoveryTool` 枚举项 + 适配器 + 执行分支；
- 适配器扩展：新增 `WINDOWS_RUNTIME_ADAPTERS` 项 + 观察器映射；
- 协议演进：`.proto` 为唯一来源，重新生成 Rust/TS，生成物不手改。

### 7.5 部署约束

- Windows 11 x64；不需要 WSL / Docker / Windows Sandbox；
- 开发与脚本依赖 Python 3.9+、MSVC + Windows SDK、Git；产品 VERIFY/SAST 使用项目私有 Windows Python 3.13.13 与 Zig 0.15.2，Java/Ghidra 作为可选逆向工具；
- 默认端口 7331；`.data/` 存数据库、产物、日志、凭据；`.tools/` 存私有工具；两者均不提交；
- 便携包入口 `AegisAudit.exe` 需完整目录。

## 8. 设计取舍记录

| 取舍 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 单体 vs 微服务 | 控制服务 + 执行器单体 | 单机工作流，避免部署复杂度 | 不直接支持分布式扩展 |
| 数据库 | SQLite | 单写方即可满足一致性 | 多用户/高并发非目标 |
| 模型接入 | 官方 API 单一接入点 | 集中管理密钥与用量 | 依赖外部服务可用性 |
| 模型输出 | 严格结构化 + 校验 | 抑制幻觉与注入 | 需要修复回路，增加调用 |
| 隔离方式 | Job Object（非沙箱） | 满足课设，无需虚拟化 | 无文件/网络隔离，须限授权目标 |
| 取消语义 | 两阶段 `CANCELLING → CANCELLED` | 进程回收需独立阶段 | 取消不是瞬时操作 |
| 租约超时 | 置失败不自动重跑 | 防重复执行与资源叠加 | 需人工介入重跑 |

## 10. 后续设计演进方向

1. FUZZ 覆盖扩展：预构建 libFuzzer 链路已贯通 `RuntimeConfig`、执行器分发与报告（含崩溃去重、`-minimize_crash` 缩减、最小输入两次复放，以及 `CVE-2016-5180` 漏洞/修复对照）；继续扩展目标构建、harness 与调用约定适配——TinyInst 覆盖输出不替代完整模糊测试；
2. 自动利用闭环：受限闭环已通（二进制 `MEMORY_BOUNDS` 发现可复用为 libFuzzer 任务，产出最小输入、复现器与证据 JSON）；继续推进正式目标的利用证据与影响判据，并据此更新 `exploitation` 语义；
3. 动态观察器与输入契约修复：当前宿主机运行器已用真实 argv 回显确认空格、反斜杠和双引号参数可正确传递；仍需修复 stderr 关键词误判、阻塞 stdin 不纳入单次时限，以及 VERIFIER 提示/配置中未完整展开的 `{{work}}`、`{{canary}}` 等占位符；
4. 协议语义拆分：显式区分 `image_id` 的多重语义（执行策略摘要 / 客体镜像哈希）；
