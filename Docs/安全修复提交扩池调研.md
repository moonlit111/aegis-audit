# 安全修复提交扩池调研

更新：2026-09-11。目标：用 Git 历史里"安全修复提交"扩充评测 ground truth 池——**每个修复提交给出一对（父提交 = 有洞版本，该提交 = 已修复版本）**，规模应远大于 CVE 池。

## 1. 结论摘要

1. **这一招有效，但不能用在 DeepSeek-Coder / V3 / Coder-V2 这三个仓库上。** `deepseek-ai/DeepSeek-Coder`（92 个非合并提交）、`DeepSeek-V3`（50 个）、`DeepSeek-Coder-V2`（7 个）合计 149 个提交，**没有任何一条安全修复**，唯一命中的一条还是 `CITATION.cff` 文档改动。池子必须去"真的有安全修复史"的仓库里扩。
2. **但 DeepSeek 确实有 CVE，而且就在 deepseek-ai 组织的第四个仓库里。** `deepseek-ai/deepseek-harness` 是 **CVE-2026-82533**（CVSS 9.4 认证绕过）的载体，它和上面三个不是一类东西，见第 6 节。上一版只扫了那三个仓库就下了"DeepSeek 全线没有安全修复"的结论，是范围性错误。
3. **扩池幅度在 5–10 倍量级，不是"免费"的 10 倍。** 在我们扫的 6 个仓库里，关键词粗筛得到 299 条候选、44 条"简单"、6 条高置信；但人工逐条读 diff 后，**即使最严的一档精度也只有约 1/3**。剩下 2/3 是正确性 off-by-one、兼容性 workaround、错误信息改进、以及方向相反的"放宽限制"。**每一条都必须复核后才能计入成绩，否则会把"父提交其实没洞"算成漏报。**
4. **真正好用的那部分非常干净。** 9 对已核实对照里，5 对是单文件 1–4 行的改动（如 ctypes 缓冲区 8→16 字节、临时历史文件 `0o666`→`0o600`、取下标前补 `i < len(...)`），第 4 节逐条列出。其中一条（`561e8806`）**正是 CVE-2024-34359 的修复提交**——说明关键词法不仅能扩池，还能重新发现已公开 CVE 的修复点。
5. **对 harness 的直接影响**：这些对照的"有洞版本"只是父提交的源码树，做静态审计可以直接用；但**必须把审计范围钉到改动文件/函数**，因为目标仓库动辄 2000–5000 个提交，默认 `max_units=80` 根本扫不到那一行。

## 2. 方法

关键词（需求给出的 8 个）先按匹配质量分档，因为它们在提交信息里的信噪比差别极大：

| 关键词 | 档位 | 说明 |
| --- | --- | --- |
| security / bypass / injection / sanitiz / permission | HIGH | 基本只在安全语境出现 |
| auth / validat / escape | WEAK | 大量非安全语境：`author`、`Co-authored-by`、参数校验、JSON 转义、`attention` |

再叠加三类证据通道，每条候选记录它靠什么被选中（`channels` 字段）：

| 通道 | 判据 |
| --- | --- |
| `MESSAGE_HIGH` | 提交信息命中 HIGH 关键词 |
| `MESSAGE_PHRASE` | 提交信息命中高置信安全短语（如 `path traversal`、`out of bounds`、`cross-site scripting`、`unauthenticated`） |
| `MESSAGE_WEAK+DIFF` | 只命中 WEAK 关键词，但 diff 里出现了新增的防护语句（`if not`、`raise`、`basename`、`allowlist`、`bound`…） |
| `DIFF_SECURITY_PATH` | diff 有防护型改动，且改动文件路径是安全相关（server / api / auth / file / download / exec…） |
| `ADR_REVERSE_LOOKUP` | `--adr-dir` 专用：架构决策记录里含边界/越权/信任措辞，按笔记反查其实现提交 |

简单度评分（小 diff、少文件、单一类别、有防护型改动、只碰代码文件）决定 `simple`，再叠一条"收紧方向"判定得到 `curated`：

- **排除"放宽限制"型改动**：`remove ... check`、`relax`、`loosen`、`accept additional`、`retry`、`revert`、`unescape`、`add support`。不加这一步，"放开 CORS""增加重试""SetEscapeHTML(false)"都会被当成安全修复。
- 剔除只改文档/清单、以及全部落在 `tests/ example/ docs/ scripts/` 的提交。

第 1 条最初差点被工具漏掉：它靠 `security` 关键词进了 HIGH 档，但当时没有任何类别短语能匹配 `jinja templates in immutable sandbox`，因此 `categories` 为空、`simple=false`。补上 `jinja|immutable sandbox` 短语后即被正确归类为 INJECTION。**这说明"命中关键词但没有类别"的候选必须单独回看**，否则最容易漏掉的恰恰是最重要的那条。

精度备注：已核实的 9 对中有 6 对来自 `ollama`，而 ollama 的 39 条 simple 只人工看了约 15 条。所以"约 1/3 精度"是**抽样估计**，不是精确统计；扩池后应继续按批复核。

## 6. DeepSeek Harness：CVE-2026-82533 与关键词法的失效

### 6.1 事实核对

`deepseek-ai/deepseek-harness` 是 deepseek-ai 组织下的**第四个仓库**（不是 Coder / V3 / Coder-V2 的任何一个），MIT，2026-08-13 建仓但推送了完整历史。**CVE-2026-82533**（2026-09-08 公开，CVSS 4.0 = 9.4 / CVSS 3.1 = 9.6，CWE-807）：

> 本地 HTTP 代理控制 API 只靠 `Host` 头判断调用方是否本机，接受客户端自报的 loopback `Host`，而不校验真实 TCP 连接来源。受限在工具沙箱内的进程可借此访问回环 API，逃离 OS 沙箱、提权到非受限执行并关闭审批提示；端口一旦经隧道 / SSH 转发 / 反向代理暴露，远程攻击者无需凭据即可创建会话、执行任意命令、导出会话记录。

| 项 | 值 |
| --- | --- |
| 有洞版本 | `19c772f46c03649ac73f8c4a065cc46ade1ff658` |
| 已修复版本 | `3e24087bfaeabe40b58ba2f7b936895b8f93fe27`（2026-08-25） |
| 随哪个版本发布 | `dsh-v0.1.2-alpha.1` |
| 修复内容 | 新增 `browser-auth.ts`（276 行）为整个 Host API 引入浏览器令牌认证，CLI 拒绝 `--host 0.0.0.0` |
| 根因 | 前一步 `01d68dee4e` 明确把认证写成 deferred work，只做 Host/Origin 栅栏——防的是浏览器混淆代理人，不是身份 |

NVD 以 deepseek 为关键词共 10 条，其中 9 条与 DeepSeek 品牌产品相关（另 1 条是 WordPress 插件，属误命中）。除 harness 外，DeepSeek MCP Server（2 条）、CodeWhale（4 条）、DeepSeek 网页对话 XSS（2 条，其中 1 条标注有争议）都在第三方项目里，各自也有可挖的修复提交，见 pairs-verified.json 的 `other_deepseek_brand_cves`。

### 6.2 关键词法在这个仓库上失效

harness 有 16 511 个提交（9 612 个非合并）。按需求给的 8 个关键词跑：**命中 2 462 条候选、768 条 tier=HIGH、86 条"简单候选"，人工查看后几乎全是误报**——`settle prompts at whole-agent idle`、`an omitted agentOptions must not materialize an empty object`、`bound pre-push test gate vitest workers`、`defer the first readiness poll` 这类生命周期 / 并发 / CI 改动被误判成 PATH_TRAVERSAL。

两个原因：

1. **领域词汇就是安全词汇。** 这个仓库里 `injection` 指 context injection、`token` 指 token 预算、`authorization` 指工具授权、`permission` 指审批模式。关键词的"高置信档"在这里全部失真。
2. **真实修复的提交信息里一条安全关键词都没有。** 见 6.4 的表：`neutralize terminal controls`、`pin model discovery to loopback`、`spawn the worker with an empty environment`、`mint RPC ids on insecure origins`。再长的关键词表也捞不到它们。

> 结论：**同一个方法在 2 000 提交的 Python 库上精度约 1/3，在 9 600 提交的 agent 单体仓库上精度接近 0。** 精度不是方法的固有属性，它随目标仓库的词汇分布变化。

实测补救（2026-09-11，`--strict`）：只收窄 `DIFF_SECURITY_PATH` 通道——要求新增行含强边界原语（basename / realpath / allowlist / path.join / startswith 等）且改动 ≤40 行、≤2 文件。效果：harness 上该通道单通道候选 **1245 → 13**（总候选 2462 → 1230，"simple" 86 → 44），已核实的 H1/H2/H4/H5/H6 全部保留（H3 本来就不靠关键词法，走 ADR 反查）。两个仓库维度验证：6 个通用仓库上 9 对已核实对照 **全部保留**（ollama 265→159、FastChat 10→4、llama-cpp-python 36→24，去掉的都是非 simple 噪声）。

### 6.3 在这个仓库上可行的方法：ADR 反查

仓库把边界决策写成架构决策记录（`.agents/notes/implemented/**/*.md`，308 篇），每篇对应一次实现提交。用"笔记 → 实现提交"反查，直接得到 (父提交, 修复提交) 对：

```bash
git log --all --diff-filter=A --format='%H %ad %s' --date=short \
    -- '**/2026-08-24-browser-token-authentication.md'
# → 3e24087bfa 2026-08-25 fix(web): authenticate the browser Host API   ← 正是 CVE 的修复提交
```

工具已支持 `--adr-dir .agents/notes/implemented`。两个坑：

- **必须 `--all --diff-filter=A` 且按 basename 匹配**：仓库会把笔记搬进 `archived/`，只按当前路径查会把"归档提交"错认成实现提交。
- **ADR 信号同样会被词汇重叠淹没**：223 条候选里 `injection` / `token` / `authorization` 大多是功能语义。必须再按信号种类数与文件名排序后人工判读，或直接用 6.4 的已核实清单。

## 7. 接入评测的建议

1. **范围必须钉死**：审计输入用父提交的源码快照，但把 scope 限定到改动文件（必要时到函数）。否则几千个文件的仓库会让 `max_units` 预算在到达目标前耗尽，结果是"没检出"而不是"没能力检出"。
2. **声明式对照**：`vulnerable_rev` 建快照跑 `SECURITY_AUDIT`，期望至少一条对应类别的 `VALIDATED` 且引文落在改动行附近；`fixed_rev` 建快照跑同配置，期望 0 条 `VALIDATED`。这与现有 [check_audit.py](../scripts/check_audit.py) 的漏洞版/修复版对照形式一致，可直接复用。
3. **不是每条都能做动态验证**：本池里只有越界写入类（第 2 条）适合接 FUZZ；注入类（第 1、3 条）适合静态审计 + 组件级复现；权限类（第 4、9 条）与路径类（第 8 条）只能做组件级验证，不要硬接 VERIFY/FUZZ 然后声称失败。
4. **注意"修复不彻底"**：第 2 条把 8 改成 16，并没有做真正的长度查询；报告里应作为"修复版仍不彻底"的讨论素材，不要写成"已彻底修复"。
5. **许可与固定**：三个仓库分别为 MIT / Apache-2.0 / MIT，代码许可与模型许可分开核对；FastChat 第 2 条同时改了 `pyproject.toml`，基准要固定依赖版本。

## 8. 坑与限制

- **提交信息不可信**：`auth` 会命中 `Co-authored-by`（已通过剥离 git trailer 解决），`escape` 会命中 JSON 转义，`validat` 会命中评测集校验。任何只靠信息的匹配都会大面积误报。
- **方向性陷阱**：删掉边界检查、放开 CORS、增加白名单、加 retry，提交信息里同样会出现 security/permission/auth 字样。必须有"收紧方向"判定。
- **off-by-one 不等于内存越界**：切片上界、生成长度、枚举值这三类 off-by-one 都不是安全漏洞，但它是最容易被关键词法捞上来的东西。
- **blobless 克隆的代价**：PDF 等二进制会触发 textconv 让 `git show` 失败（DeepSeek-V3 自带论文 PDF 就撞上了），工具已加 `--no-textconv` 并容错跳过整批；更稳的做法是完整克隆或关掉 textconv 驱动。
- **未覆盖**：本次没有扫 `open-webui`、`vllm`、`text-generation-webui` 等更大的目标（体积 400 MB+）；`ollama` 只人工看了约 15 条。
- **方法有适用边界**：下面的精度结论只在"词汇不重叠于安全术语"的仓库成立。一旦目标仓库本身就在讲信任边界、沙箱、权限（agent harness、网关、鉴权中间件都是这种），关键词法立刻失效，必须改用 ADR 反查或路径锚定 + 人工判读。
