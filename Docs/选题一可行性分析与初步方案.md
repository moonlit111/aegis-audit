本文件记录第 1 题已确定的项目目标和实施路线，更新于 2026-09-07。选题名称为“基于大模型智能体的软件漏洞挖掘系统设计与实现”，产品定位为“面向源码与受保护二进制的多智能体漏洞挖掘与验证系统”。全部设计、实现、调试、测试和技术文档由 Codex 承担，主体验证环境采用 Windows 电脑。课程组队为 5 人，不据此分配开发任务。

**首要目标：在明确支持的语言、格式、平台和保护方式内，新项目导入后无需修改核心检测逻辑，系统能够理解目标、主动寻找风险、提出漏洞假设、独立复核，并构造验证；对已确认可利用的缺陷生成或适配利用代码，在实际目标上验证影响。**

设计以课程要求与通用挖掘能力为依据。历史漏洞提供功能检验与结果核对标准；漏洞位置、CVE 编号、现成 PoC 和修复补丁不作为独立发现阶段的输入。模型未发现漏洞或证据不足时，应如实返回分析范围和状态。

本项目优先选第 1 题的原因是成熟分析工具较多，目标可逐个验证，工作较易拆分。二进制逆向、自主分析与自动利用仍然具有较高难度。当前已交付程序结构分析基础链路，完整目标的已实现与未完成部分见[首轮交付记录](首轮交付记录.md)。

本次确定的项目约束为：U01 通用机制能迁移到未专项适配的新项目；U02 自行实现主体，允许借鉴开源思路与源码模块；U03 使用 DeepSeek 官方 API，首版按此前偏好优先适配 deepseek-v4-flash；U04 历史漏洞用于检验，以简单案例为主并包含 1—2 个较复杂案例；U05 测试伴随开发，保留未用于开发调试的独立评测案例；U06 由 Codex 承担全部开发、调试、测试和技术文档工作，计划只保留执行顺序、依赖与完成标准，不制定时间排期或成员开发分配。

技术访谈已确认：系统供单人使用，无共享需求。首版围绕一个操作员会话设计，不实现多用户账号注册、成员管理、项目共享或角色权限分配；保留任务队列、执行器身份校验及模型密钥保护。

技术访谈已确认：目标构建、启动和正常输入方式优先由系统自动识别并在执行器中尝试；缺少必要信息时，允许用户补充正常运行配置。成功配置保存复用，缺少运行条件时静态审计可继续。漏洞位置、触发条件和利用输入由系统自行寻找。

技术访谈已确认：API 费用不设项目总额上限。API 接入与适配细节由 Codex 自主处理，后续不再向用户询问 API 相关问题。实现保留实际用量与费用记录；费用上限为可选配置，当前不启用。

后续访谈只确认影响系统能力、分析方式和验收标准的核心决定；环境安装、兼容性和常规配置由 Codex 自行核查处理。

用户确认老师未额外解释测试对象范围，课程验收以提供的 PDF 原文为依据。正式样本的筛选、类别核查和适配由 Codex 承担；原文明确要求的功能、软件类别与数量均须保留，不将缺乏依据的替代对象计为合格。

通用性首先体现在按漏洞原理分析：外部输入是否可控、是否进入危险操作、防护是否充分、调用和分支条件是否可达。首版正式支持范围已确定为注入、路径遍历、认证/授权缺陷和内存越界（越界读/写），相应能力仍待实现和验证。新增目标可配置构建、启动和输入接口，不能要求人工预先指出漏洞函数或在核心代码中新增项目名称/CVE 专用分支。

2026-09-07 重新核对课程 PDF 第 2 页及通用考核要求：课题 1 没有指定必选漏洞类型、CWE 清单或漏洞类型数量，也没有要求覆盖全部漏洞类型。用户已授权在符合原文或原文未限定时采纳建议，因此上述四类确定为首版范围。此决定不减少源码与二进制分析、去壳/解混淆、静态审计、动态模糊测试、独立复核、自动利用和证据报告要求；认证、加解密、注册属于独立的关键逻辑标定要求，三类软件各两种的正式测试仍须完成。

检测采用三种互补机制：静态工具产生模式与代码线索；模型自主阅读入口、关键逻辑及相关上下文，即使没有规则告警也能提出候选；模糊测试探索真实运行行为。所有候选都需保留可检查的依据。控制流与调用关系不完整时标记未知或近似，不虚构完整路径。

已确定的技术路线如下，具体依赖版本在互通和工具验证后固定。[技术栈对比与建议](技术栈对比与建议.md)记录 Rust/Python、Svelte/React、Connect RPC/REST+SSE 的区别；[具体实现方案](具体实现方案.md)确定工程模块、接口与验收依据。技术栈及首轮兼容版本已固定，结构分析工作台已实现。

| 层次 | 已选技术 | 用途 |
| --- | --- | --- |
| 核心后端 | Rust、Axum、Tokio、Serde、SQLite/SQLx | 领域状态、API、任务调度、进程管理、证据持久化 |
| 前端 | TypeScript、Svelte、Vite、pnpm | 项目、任务、代码/证据、人工修正与报告界面 |
| 通信 | Connect RPC、Protocol Buffers、官方 Rust/TypeScript 实现 | 业务接口、共享消息与服务端进度流；大文件使用 HTTP 产物接口 |
| 调度 | 自研明确状态的任务编排器、独立工具进程、持久化事件 | 依赖、有限重试、预算、取消与恢复 |
| 模型 | Rust 中的 DeepSeek 官方 API 适配层，保留可配置模型标识 | 工具调用、结构化输出、分角色上下文、消耗记录 |
| 工具桥接 | 必要的 Python/Java 脚本及结构化进程接口 | 复用工具生态与既有模块，返回实际结果和产物 |
| 源码解析 | Tree-sitter、Semgrep CE、函数/调用/分支索引 | 首批适配 Python、Go、C/C++；解析对象语言独立于后端语言 |
| 二进制 | Ghidra 无界面脚本、UPX、按保护模式扩展的适配器 | PE/ELF 的函数、伪代码、地址、控制流与交叉引用 |
| 动态测试 | Linux 上 AFL++；Windows 上统一测试接口下的输入变异与运行监测 | 适用的命令行/文件输入目标；按目标评估进一步接入 WinAFL/TinyInst |
| 存储与报告 | SQLite 元数据、文件产物、JSON 与 HTML/Markdown 报告 | 每条证据回溯到真实输入与执行记录 |

Rust、Svelte、Connect RPC 为 PDF 建议，原 Python/FastAPI + React + REST/SSE 组合也能实现相同课程功能。现已选定 Rust 组合，主要考虑自研任务与证据的类型约束、原生执行控制及统一通信契约。必要工具脚本保留 Python/Java，不要求把安全工具重写为 Rust。两种模型 API 不计入 R14 的两种被测大模型软件。

Connect 的官方 Rust 实现已存在，当前已发布 v0.9.0，仍处于 0.x。应固定兼容的生成器和运行库，并验证 Rust 服务与浏览器客户端的普通调用、服务端流、错误与取消。任务持久化、事件补读、显式任务取消仍由系统实现，不能把通信库当成完整任务调度器。

Windows 主机承担最终部署与验收。Linux 分析工具及 ELF 目标通过 WSL2 或 Linux 虚拟机运行；历史 Windows PE 的执行和利用验证安排在可重置的 Windows 虚拟机中。Mac 用于编写代码、前后端调试及非目标执行的检查。最终演示尽量由 Windows 一台电脑完成，平台不依赖 Mac 在线。

Windows 主机为 Windows 11 专业版、i9-13900HX、32 GB 内存、500 GB 硬盘，配置由用户确认。具体系统构建号、虚拟化可用性、磁盘余量、JDK、工具和运行镜像尚未实际检查。先限制任务并发并确认运行开销，不预设所有环境可以同时满负载运行。

二进制处理是核心要求。Ghidra 能反编译不代表完成去壳和解混淆；UPX 仅覆盖受支持格式。处理适配器应面向保护方式，能用于该范围内的新样本。简单字符串编码和控制流变换可作为初始适配方向，最终必须与选定的正式软件相匹配。函数改名本身不算解混淆，开源程序隐藏源码或自行加壳也不自动成为符合 R14 的闭源软件。

源码和伪代码进入统一审计对象，但保留差异：源码使用文件与行号，二进制使用模块、函数地址/RVA 与伪代码位置；规范化结果保留原始依据。Semgrep CE 跨过程能力有限，伪代码也不一定可按标准 C 解析；相关失败需要显式记录，由其他分析方法补充。

智能体角色采用编排、导入与逆向、审计、独立复核、验证与利用、报告六类职责。角色可以共用一个模型服务，但上下文和任务权限按职责分开。复核智能体依据原始代码与工具证据检查候选，不能将前一角色的结论直接视为事实。报告角色只能引用已有证据，不能补写不存在的执行结果。

产品中的核心对象概述如下，规范名称与状态约束以[具体实现方案](具体实现方案.md)为准，编码时固定为版本化数据结构。

| 对象 | 必需信息 |
| --- | --- |
| Project / Snapshot / Artifact | 类型、版本/哈希、来源、正常构建/运行配置、平台及不可变产物 |
| ProgramUnit | 函数、源码位置或二进制地址、代码/伪代码、控制流与调用引用、解析质量 |
| AuditRun / WorkItem / ToolRun / ModelCall | 角色、依赖、输入摘要、模型/工具版本、参数、预算、退出状态、日志与产物引用 |
| Finding | 漏洞假设、CWE、严重度依据、可控输入、触发条件、代码位置、证据引用 |
| VerificationRun | 实际目标哈希、环境标识、输入/利用代码、执行记录、判据、结果 |
| Review / Report | 人工与智能体结论、修正历史、结果状态、结构化导出 |

静态判断、局部测试、真实目标复现和利用成功分别记录。利用成功由执行证据决定；模型置信度、脚本退出码或打印出的“成功”文字不能单独升级状态。未复现可能意味着环境或输入条件不足，不直接等于误报。崩溃与任意代码执行分别记录，漏洞影响决定其成功判据。

目标代码、README、日志和二进制字符串均作为待分析数据。执行器只接收当前目标与任务产物，不接收评测答案、其他项目或模型密钥；目标执行使用可重置环境。模型配置保存在环境变量或本地配置中，报告中不输出密钥。这些边界同时保证执行可追溯和评测输入清晰。

借鉴范围以成熟能力为主：复用 Ghidra、Semgrep、AFL++、UPX 等工具，参考 DeepAudit 的角色分工和工具封装；系统的数据结构、调度、证据关联、模型调用适配、执行接口和界面由本组实现。可复用源码模块，但应记录出处、版本、许可证和本组改动。

自主贡献拟验证为：面向新项目的分析决策与上下文选择；源码/二进制证据统一；独立复核和由真实执行证据决定的验证状态。与 DeepAudit 等现有开源系统进行实际比较，静态工具和单智能体对照作为补充。参考资料本身和六个角色的名称不构成创新证明。

现阶段 R14 的六个正式条目尚未形成合格清单。S1/S2 优先从原文列举品牌官方发布的开源大模型软件中筛选两个不同项目；llama-cpp-python 和 Ollama 暂作开发回归候选。闭源软件需落实真实发布物及其加壳/混淆特征。样本身份、类别、版本和实际挖掘/利用证据由 Codex 核查，缺少依据时保留缺口，不通过修改文字认定样本合格。测试具体安排见[测试与验收方案](测试与验收方案.md)，阶段计划见[开发实施计划](开发实施计划.md)。
