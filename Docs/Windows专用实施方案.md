# Windows 专用实施方案

更新：2026-09-09。用户要求整套系统只支持 Windows，并在本机完成开发、实际验证和全部项目交付。本方案取代“Mac 日常开发、Windows 最终接力”的环境分工，但不缩减 R01—R15、U01—U06 或六项正式软件的要求。

动态验证按当前项目约定直接使用 Windows 宿主机运行器，不再并行建设 Windows Sandbox、Docker 或其他隔离后端。

## 平台边界

- 唯一支持的宿主、开发、构建和交付平台是 Windows 11 x64。Windows ARM64、macOS、Linux 均不作为支持平台。
- 日常使用入口为便携目录内的 `AegisAudit.exe`；Python、Git、Java、Ghidra 等必要组件随包提供，不要求使用者配置开发环境。构建源码时仍使用 MSVC/Windows SDK、Rust、Node 和 Python。
- 最终动态执行直接使用 Windows 宿主机和 Windows 工具链，不把 Docker、WSL、Windows Sandbox 或远端 Mac/Linux 服务列为运行前提。
- PE32、PE64 仍是主要二进制对象。保留在 Windows 上静态分析 ELF 的能力，因为目标文件格式不等于宿主操作系统。原生 Windows 能否执行某种目标必须单独登记，不能将静态可解析等同于动态可运行。
- 以前的 Mac/Linux 日志只保留为历史来源，不能改写平台字段，也不能充当本机 Windows 结果。

## 主要难点

1. **宿主机运行边界必须明确。** Job Object 保证工具和目标进程树在超时、取消或执行器退出后被回收，但不提供网络、文件系统或权限隔离。系统只应运行用户有权测试的目标，不能用于恶意软件或未授权样本。
2. **PE 的执行前提复杂。** 32/64 位、DLL、服务权限、GUI/交互入口、文件与注册表状态、ASLR、DEP/CFG，以及厂商保护都可能影响验证。运行器必须保存这些前提，不用 Linux ELF 的成功记录替代。
3. **证明漏洞与证明利用不同。** 模型发现、静态复核、局部行为、异常复现、完整利用各自独立；尤其不能以进程退出 0、打印成功或崩溃一次作为完整利用证据。
4. **便携包的正确性不只是一个 EXE。** 要验证 DLL 搜索、非 ASCII/空格路径、离线组件、凭据保存、端口冲突、重复启动、升级保留数据、SmartScreen 和签名状态。当前未持有代码签名证书，不能伪造“已签名”。
5. **正式软件资格和资源有真实约束。** 当前正式验收仍为 0/6。真实加壳/混淆证据、合法可得的固定发布物和完整模型软件部署需要逐项调查；32 GB 主机还须给 Windows 及宿主机运行器留出余量。不得以自制加壳夹具或两个模型 API 替换课程软件名额。

## 完成判定

Windows-only 迁移不是删除所有历史文档里的 “Mac” 字样，也不是只把入口变成 `.exe`。只有开发、构建、静态分析、模型审计、原生隔离动态执行、保护处理、正式评测和最终交付都不需要非 Windows 环境，并且各自取得真实证据，才符合用户要求的全部完成状态。
