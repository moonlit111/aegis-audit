本文件定义[项目方案](选题一可行性分析与初步方案.md)和[具体实现方案](具体实现方案.md)的检验方式，更新于 2026-09-09。**已有漏洞用于检验系统自主挖掘、定位、验证与报告的能力。** 运行公开 PoC 可以检查评测环境，但不能计作系统独立发现。

首版正式支持范围确定为注入、路径遍历、认证/授权缺陷和内存越界。该分类属于经用户确认的能力边界；课程原文未指定漏洞类型清单或数量。评测应提供四类的实际分析与验证证据，同时完整检验课程功能；三类软件各两种按软件条目计数，不能用四类漏洞覆盖情况替代，也不自行增加“每个软件必须同时具有全部四类漏洞”的要求。

评测持续伴随实现，同时保留一组未用于开发调试的目标作最终评测。按用户最新的[三人分工](后续执行与三人分工.md)，C 组织样本资格与结果核对，A 负责动态能力，B 负责审计与保护能力。评测侧与产品侧仍是必须落实的数据及程序权限边界，不能仅靠“不同人负责”代替权限隔离。测试与产品的输入边界如下。

| 所在侧 | 可持有的信息 |
| --- | --- |
| 产品分析侧 | 目标代码或二进制、正常构建/启动方式、输入接口、范围与预算、自己产生的分析和执行证据 |
| 评测管理侧 | CVE/缺陷标注、公开 PoC、补丁与修复说明、预期影响、对应位置和计分依据 |
| 结果核对阶段 | 对照系统输出与评测答案，保留原始输出及全部失败/不确定记录 |

评测答案不得挂载到分析工作目录，产品模型的文件工具也不能读取项目自身的 evaluation/reference、开发文档或其他目标。目标仓库的修复历史和评测说明不随盲测任务提供；原始目标中已有信息的暴露情况应记录。公开 CVE 可能存在于模型训练数据中，因此盲测不等于证明完全未见过该漏洞。

测试由四部分构成：开发回归案例，用于持续检查功能；正式课程案例，用于满足 R14；开发未使用的保留案例，用于检验迁移能力；修复版和经确认正常对照，用于检查误报。一个案例可以同时承担开发检验与正式课程记录，但不能在参与调试后仍标成保留案例。

用户确认老师没有额外解释测试对象范围，并要求严格按 PDF 原文执行。R14 按原文设置六个条目，由 Codex 负责筛选和核查；目前均未确认为已经满足验收。

原文为“支持对 deepseek、智谱、kimi 等任意 2 种开源大模型软件的漏洞挖掘和利用验证”。为减少样本归类的解释空间，优先核查原文列举品牌官方发布的开源大模型软件，确认具体代码仓库、开源属性、软件版本、可运行入口及漏洞依据后再确定 S1/S2。优先选择这些来源是本项目的实施策略，不能改写为老师只允许这三个品牌。模型权重、聊天截图或品牌名称本身不能代替软件分析与实际利用证据。

| 条目 | 要求类别 | 当前候选/状态 | 仍需落实 |
| --- | --- | --- | --- |
| S1 | 开源大模型软件 1 | 候选 DeepSeek-Coder，代码来源/许可已核实，结构解析已运行 | 具体项目、开源依据、固定版本、运行环境及真实挖掘/利用记录 |
| S2 | 开源大模型软件 2 | 候选 ChatGLM3，代码来源/许可已核实，结构解析已运行 | 与 S1 不同的软件，以及同类归属和实际挖掘/利用证据 |

每个条目需要相应软件上的漏洞挖掘和利用验证，单有导入或扫描记录不能计为通过。原文没有明确要求两种软件使用不同保护算法，也没有明确允许类别间重复计数，因此当前不预设重复抵扣。接入两个模型 API 不计入 S1/S2；开源程序编译、隐藏源码或自行加壳不自动符合闭源要求。

llama-cpp-python、Ollama 暂作为开发回归候选，不占据 S1/S2。PDF 未明确否定这些项目，但当前没有充分依据把它们计入所要求的软件类别。闭源条目需核查发布物的闭源属性和实际加壳/混淆特征；自制夹具仅用于机制测试。正式样本不匹配当前能力时，继续筛选符合原类别的样本或扩展通用适配能力，不修改验收类别来迁就现有实现。

以原理清楚的历史漏洞覆盖基础功能，1—2 个较复杂案例检验跨模块分析、内存问题或复杂验证。复杂案例可以属于上述六个正式条目；若不符合类别，只作为额外能力测试。开发过程可以使用小型自制程序检验机制，但需标注其性质。

通用性 U01 通过开发未使用项目和同类缺陷的不同实现检验。更换项目可以提供正常运行适配信息，不能靠新增项目专用检测分支通过测试。修复版应检查是否仍误报同一已修复缺陷，而非假定整个修复版不存在其他问题。无法解析或运行的目标应按实际原因记录等待配置、失败或不支持状态，不能报安全。

正常运行配置检验覆盖自动识别成功、信息缺失、补充后继续执行、配置复用及目标/环境变化后的重新检查。缺少运行信息时应说明具体缺项并继续可独立执行的静态审计，不能要求提供参考 PoC，也不能把动态等待状态记为验证成功。配置每次修订均保存版本，已有执行证据继续引用原版本。

U02 通过来源与改动记录、自研模块说明及对照实验检查；U03 记录实际模型 API 与调用结果；U04 记录简单/复杂案例及历史依据；U05 核对持续回归记录、保留集合的冻结时间和是否曾参与调试；U06 按最新三人任务书执行、交叉检查及集成，记录实际完成情况与 AI 协助，不编造贡献比例或按期完成结论。

状态判定遵循以下规则：疑似发现可以尚未验证；静态依据充分不代表已执行利用；局部或模拟依赖测试与真实完整目标验证分开；真实复现与达到利用目标分开。单独异常退出不能证明特定根因，单独退出码 0 或输出“成功”也不能证明利用成功。未复现不直接判为误报。每个成功状态都需可核对的实际证据。

指标记录原始数量与分母：已知缺陷检出情况、定位正确性、经判定的真/误报、证据不足数、自动验证成功与失败数、利用成功与失败数、耗时、模型消耗和人工辅助。只有标注充分时计算召回率；未知结论不并入已确认真阳性。一次任务的重试与失败都保存，预算和尝试次数在运行前固定。

对照包含实际开源审计系统（优先评估 DeepAudit）、静态工具、单智能体和完整系统。使用相同目标版本、可用信息及可比较预算，并记录工具差异。仅在双方适用的任务上比较准确性；对方不支持的二进制任务标为不适用。功能扩展、验证质量、检出效果、耗时分别报告，不将工具覆盖差异合并成单一优越结论。

优先编写能检查真实行为的测试：位置/地址映射；没有执行证据不能写入利用成功；修复与正常对照；任务取消/超时回收；工具或模型失败的传播；报告不伪造证据；分析工具无法读取评测答案。按已确定技术栈还需验证 Rust/TypeScript 生成接口的一致性、Connect 服务端流的错误与重连补读、浏览器断线和任务取消的区别，以及具体实现方案规定的幂等请求、过期租约、人工修订冲突和服务重启恢复。解析器、执行器和接口可以使用小型可控夹具；整体挖掘效果必须由实际目标检验。低影响界面改动由 Codex 进行界面检查。

最终保留集合在功能冻结后运行；针对失败修改系统后需记录版本变化，不能继续把反复使用的同一集合称为未见测试。最终报告既包含成功案例，也包含漏检、误报、不能验证或不支持的情况。测试说明能力在已声明范围内的表现，不保证在任意新项目中必然找到漏洞。

当前正式课程软件验收为 **0/6**。0.2.0 开发夹具已完成真实模型的四类缺陷/修复对照、13 项真实动态回归及 5 项浏览器测试，范围与证据见[审计与动态验证交付记录](审计与动态验证交付记录.md)。静态回归中的动态状态仍为 `NOT_RUN`；单独的运行器回归不冒充每份模型方案都已在完整部署执行。开发夹具曾用于调试，不属于保留测试集。结构分析历史结果见[首轮交付记录](首轮交付记录.md)，正式对象资格证据见[正式样本筛选](正式样本筛选.md)。后续结果由真实运行产生，与[开发实施计划](开发实施计划.md)一同维护。
