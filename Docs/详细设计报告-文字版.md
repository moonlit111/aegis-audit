## 1. 文档定位与编写方法

### 1.1 为什么需要文字版

技术版详细设计按“模块—数据结构—函数签名”组织，适合实现人员快速定位代码，但不适合评审、答辩和跨角色沟通。文字版回答的是另一组问题：系统为什么这样分层，各模块承担什么责任，关键流程如何推进，异常和失败如何处理，哪些设计是刻意的取舍，哪些能力仍未完成，以及后续修改时不能破坏哪些边界。

因此，两版报告不是互相替代关系。文字版给出稳定、可讨论的设计骨架；技术版给出随代码变化的精确细节。代码发生重构时，字段名和函数名可能变化，但只要职责边界、数据关系、状态机和安全约束不变，文字版仍然适用。

## 2. 执行摘要

AegisAudit 是一个面向 Windows 11 x64 单机的软件漏洞挖掘与验证工作台。用户导入源码包、源码目录、指定提交的 Git 仓库或 PE/ELF 二进制后，系统建立不可变快照和程序索引；随后由多个角色智能体完成恢复规划、语义审计、独立复核和验证方案设计；需要动态执行时，再由独立执行器在 Windows 宿主机上运行受控验证配置，并保存观察结果、工具日志、代码引文和产物哈希。

系统的设计重点不是“让模型直接给出漏洞结论”，而是把模型限制在受控的认知任务内：模型可以阅读代码、规划工具步骤、提出候选结论和解释证据，但不能直接运行命令、读取宿主文件、决定执行成功状态或绕过服务端校验。真正的导入、反编译、恢复、运行和状态写入由 Rust 控制服务与执行器完成。

当前 `main` 已合入 Windows 宿主机 VERIFY、预构建 libFuzzer FUZZ 和智能体规划的恢复链路，但仍是集成中的 0.2.0 原型。自动利用仍是受限闭环（崩溃 PoC，不等同代码执行），六项正式软件样本已全部通过（6/6）。本文把仍未闭合的项目当作设计风险明确保留，不把“机制已实现”写成“课程验收完成”。

## 3. 背景、问题与范围

### 3.1 课程背景

课程题目要求一个基于大模型智能体的软件漏洞挖掘系统，覆盖多智能体协作、源码和二进制分析、加壳与混淆处理、静态审计、动态模糊测试、独立复核、自动利用、证据链、关键逻辑标定、人工修订、结构化报告以及开源项目对比。项目需要在有限时间内形成可演示、可追溯、可复现的单机系统。

### 3.2 要解决的问题

第一，模型输出天然不确定。语言模型可能引用不存在的代码、伪造执行结果或在条件未知时宣布漏洞成立，因此系统必须让模型“可提出、不可自证”。

第二，软件分析目标形态复杂。源码、目录、Git 仓库、PE 和 ELF 的导入方式、文件结构、文件寿命与工具链不同，不能用一个临时目录加一条命令草率处理。

第三，动态验证有副作用。被分析程序可能读写文件、创建子进程、占用 CPU 或等待输入。即使目标不是恶意软件，也不能把“能在宿主机运行”理解为“没有任何风险”。

第四，证据链必须可复核。一个结论要能回到原始文件、具体行号或地址、工具调用、模型调用、运行配置和原始观察，而不是只保留一段模型生成的解释。

第五，单机原型必须控制规模。课程要求集中在设计实现和验证，不需要多租户、分布式调度或真正的隔离平台。

### 3.3 系统范围

系统覆盖从导入、建模、恢复、审计、复核、验证方案生成、动态验证到报告导出的完整工作流。它支持 Python、Go、C/C++ 源码和 PE x86/x64、ELF x86_64 的静态分析；动态验证当前只支持 Windows 宿主机上的 Python 函数、单入口 C/C++ 源码和原始 PE32/PE64。

### 3.4 明确不做的事情

系统不在本阶段建设多用户协作、权限平台、云任务队列和分布式数据库；不承诺完整的全程序污点分析、通用反混淆、任意构建系统识别或自动漏洞利用；不把自然语言模型当作唯一裁判；不使用 Windows Sandbox、Docker、WSL 或虚拟机作为当前产品运行前置条件。

## 4. 目标与非目标

### 4.1 核心目标

系统的第一目标是可信。任何漏洞结论都必须能回溯到真实代码或真实运行，证据不完整时必须显示为部分完成、不确定或未运行。控制服务、执行器和模型之间的关系必须能够被审计。

第二个目标是可控。模型只能选择已注册工具和已声明输入，不能提供任意命令、宿主路径或执行脚本；动态运行必须有固定目标、固定输入、次数、时限、取消和回收确认。

第三个目标是可复现。导入形成不可变快照；配置生成指纹；动态运行固定正常输入和探测输入；报告引用数据库中的事实而不是浏览器内存或模型口述。

第四个目标是有边界。系统只支持明确列出的语言、工具和适配器。缺少工具、缺少条件或超出支持范围时，系统应拒绝执行并保留原因，而不是降低证据标准。

### 4.2 工程目标

系统应能在单台 Windows 计算机上完成构建、启动、分析、验证和打包；常规路径不依赖外部控制服务；本机凭据与目标数据分离保存；导入、分析、运行和报告分别有错误边界；开发测试可重复执行。

### 4.3 非目标

不把系统设计成恶意软件沙箱，不声称 Job Object 能提供文件或网络隔离，不把“漏洞审计完成”解释为“目标安全”，不在没有完整利用证据时把验证状态改成已利用。也不把 FUZZ、TinyInst 或 libFuzzer 的历史实验等同于当前产品能力。

## 5. 系统上下文与总体架构

### 5.1 系统上下文

操作员通过浏览器访问本机控制服务。控制服务负责项目数据、任务状态、模型调用和报告；执行器从控制服务领取工作并运行本机工具；DeepSeek API 是可选的外部模型服务，只参与审计推理，不接触执行器、目标进程或数据库。项目目录中的 `.data` 保存数据库、产物和本机凭据，`.tools` 保存固定版本工具。

最重要的信任边界有三条。第一条位于模型与工具之间：模型输出经过结构校验后，才能变成工作项或数据库记录。第二条位于控制服务与执行器之间：执行器只能通过 RPC 领取租约、上传产物和回报状态，不能直接修改数据库。第三条位于宿主与目标之间：目标运行在普通用户权限下，使用独立临时目录、固定输入、时限、取消和 Job Object 进程树回收，但不具备文件或网络隔离。

### 5.2 逻辑分层

表示层是 Svelte 单页工作台，负责导入、任务查看、代码和图谱展示、审计结果、恢复面板、运行验证、模型连接和报告下载。它不实现业务判定，不直接访问数据库，也不保存模型密钥。

控制层由 Rust 服务组成，负责事务、状态机、队列、租约、模型调用编排、证据校验和报告生成。它是数据库的唯一写入方，也是模型凭据的唯一持有方。

执行层由 Rust 执行器组成，负责领取任务、运行 Tree-sitter、Ghidra、Semgrep、UPX、FLOSS、IDA/D-810 和宿主机 VERIFY 运行器，上传产物并回报结果。执行器不判断漏洞真伪，不直接写库，也不接触模型密钥。

契约层由 Protocol Buffers 定义生成 Rust 与 TypeScript 代码，保证前端、控制服务和执行器使用同一套消息与状态定义。生成物不手工修改。

### 5.3 部署形态

默认部署是一个控制服务、一个执行器和一个浏览器会话。控制服务默认监听本机回环地址；执行器通过注册令牌接入。执行器可以存在多个实例，但同一执行器一次只持有一个活动租约；运行类任务全局一次只允许一个，且未确认回收的运行租约会阻塞所有执行器，以避免宿主机上出现多份目标进程。

### 5.4 数据与信任流

导入数据从浏览器或本机文件进入控制服务，形成原始产物、规范化产物和清单。执行器下载这些产物到任务临时目录，完成分析后上传派生结果。控制服务校验目标哈希、产物归属、租约身份和记录一致性后，才把结果写入数据库。模型只接收经过别名化、裁剪和封装的目标上下文；模型响应先被保存为原始产物，再经过结构校验和引文校验。

## 6. 关键架构决策

| 决策 | 选择 | 理由 | 代价与约束 |
| --- | --- | --- | --- |
| 控制服务与执行器分进程 | 单控制服务加可注册执行器 | 数据库唯一写入、执行任务隔离、便于观察回收状态 | 需要租约、心跳和恢复协议 |
| 数据库选择 | SQLite 单写方加内容寻址产物 | 单机工作流简单，事务足够，备份直观 | 不适合多用户高并发，需要控制写入入口 |
| 模型调用位置 | 只在控制服务调用模型 | 密钥集中管理，用量和提示词可留痕 | 控制服务承担模型编排复杂度 |
| 执行配置形式 | 声明式枚举、结构化配置，不给模型命令行 | 降低命令注入和任意路径风险 | 新工具需要显式扩展枚举与适配器 |
| 恢复方式 | 智能体规划，单步工作项执行 | 模型根据真实结果调整下一步，失败可保留 | 流程比固定脚本复杂，需要持久化计划历史 |
| 动态运行边界 | Windows 宿主机 VERIFY，Job Object 管理与回收 | 课程不要求虚拟化，部署简单 | 不是文件/网络隔离，必须限制目标与副作用 |
| 取消语义 | 两阶段 CANCELLING 到 CANCELLED | 必须先确认旧进程回收 | 取消不是瞬时操作，需要等待执行器确认 |
| 租约超时 | 标记 EXPIRED 或 FAILED，不自动重跑 | 避免旧进程未终止时启动第二份目标 | 失败后需要人工判断和重跑 |
| 独立复核 | REVIEWER 使用新上下文重新读取原始代码 | 减少同一对话内的确认偏差 | 同模型仍可能共享系统性偏差，需要真实对照实验 |
| 报告生成 | JSON 为事实源，HTML/Markdown 为阅读界面 | 结构化数据可机器处理，页面文本可阅读 | 不同格式必须保持一致的事实边界 |

## 7. 领域模型与数据设计

### 7.1 设计原则

领域模型只描述“系统认为什么是事实”，不直接依赖文件系统、数据库或网络。项目、快照、程序单元、发现、复核、标注、运行记录和任务状态都在领域层定义，因此控制服务、执行器、报告和前端共享同一套语义。

数据设计的核心不是字段数量，而是三条关系：所有输入必须绑定到不可变快照；所有分析结论必须绑定到该快照中的真实文件和位置；所有动态结论必须绑定到冻结的配置、目标哈希、运行观察和回收状态。任何脱离这三条关系的“结论”都不能进入正式报告。

### 7.2 主要实体

Project 表示一次课程设计中的分析项目，是用户可见的最高层容器。Snapshot 表示一次导入形成的不变版本，包含原始产物、规范化产物、清单、目标整体哈希、来源提交号和导入状态。同一个项目可以导入多个快照，但旧快照不会被新文件覆盖。

Artifact 是按内容哈希保存的字节对象。原始目标、规范化目录包、清单、工具日志、模型请求与响应、运行观察和报告导出都以产物形式保存。产物 ID 用于引用，SHA-256 用于核验内容，媒体类型用于解释用途。

AuditRun 表示一次结构分析、语义审计或动态验证运行。它记录范围、状态、开始和结束时间、单元数量、摘要和错误信息。ProgramUnit 与 ProgramEdge 表示程序索引中的函数、模块、调用或引用关系；边的确定性字段区分工具确认、静态推断和未解析目标。

WorkItem 与 WorkAttempt 表示任务分发。工作项描述“要做什么”，尝试描述“谁在何时领取过、租约是什么、最终结果是什么”。Executor 表示执行器注册信息与工具能力。租约只保存令牌哈希，明文令牌只在领取响应中出现一次。

AgentTask、ModelCall、Finding、Review 和 LogicAnnotation 组成审计证据链。AgentTask 以运行、角色和输入键唯一标识一次智能体任务；ModelCall 记录模型、角色、提示词版本、请求产物、响应产物、时间、用量、完成原因和错误；Finding 保存候选漏洞及其代码引文；Review 保存独立复核结论和分项前提；LogicAnnotation 保存认证、加解密和注册等关键逻辑标注及修订。

RuntimeRecord 与 RuntimeResult 表示动态验证。记录绑定原审计运行、可选发现和冻结配置；结果保存目标哈希、配置指纹、执行环境摘要、配方产物、观察产物和工具执行记录。RunEvent 是持久化事件流，用于前端重放和排错。Report 保存导出的报告产物和格式。Request 幂等表记录客户端请求 ID、内容哈希和已创建对象，避免网络重试产生重复数据。

### 7.3 数据关系与完整性

项目包含多个快照，快照包含多个审计运行。每个运行拥有自己的程序单元、边、发现、复核、标注、任务和模型调用。工作项必须关联快照；来自导入的工作项可以没有审计运行，来自分析、恢复或动态验证的工作项通常关联一个运行。执行器与工作项不是静态父子关系，而是通过领取绑定。

完整性由四层保证。第一层是内容寻址与哈希校验，确保目标、配置和输出没有被替换。第二层是外键和唯一约束，确保运行、工作项、产物和发现不会引用不存在的对象。第三层是领域校验器，确保程序单元位置、文件覆盖、发现引文和复核前提合法。第四层是服务端事务，确保状态变化与事件写入同时成功或同时失败。

### 7.4 状态机

运行状态包含排队、运行、等待执行器、取消中、完成、部分完成、失败、已取消和达到限制。排队和等待执行器可以进入运行，也可以被取消或直接失败；运行可进入取消中、完成、部分完成、失败或达到限制；取消中必须先进入已取消或失败。系统不允许从运行状态直接跳到已取消，因为进程树回收需要单独阶段确认。

快照状态包含导入中、就绪、部分和失败。当前导入路径主要产生就绪或失败；部分状态保留给“导入成功但覆盖不完整”的设计场景。工作项状态包含排队、运行、完成、失败、取消、达到限制和过期。任务完成只表示工作流结束，不表示目标安全。

### 7.5 数据生命周期与备份

导入完成后，原始和规范化产物按哈希归档。分析结果、工具日志、模型请求响应和运行观察追加保存。人工修订保留修订号和历史记录，不覆盖旧证据。报告导出生成新产物，不修改原始数据。备份需要同时保留数据库、WAL 和 blobs 目录；只备份数据库会丢失证据文件，只备份文件会丢失状态关系。

## 8. 模块详细设计

### 8.1 模块总览

系统由十四个模块组成，分别位于表示层、控制层、执行层、契约层和支撑层。模块划分的目标是让安全边界和数据所有权清晰，而不是追求细粒度微服务。

### 8.2 项目与快照管理

项目模块负责创建项目、列出项目、读取项目详情和创建快照。创建快照时，系统把上传或本机来源登记为原始产物，记录目标类型和来源，然后创建导入工作项。快照在导入完成前处于导入中状态，导入完成后更新规范化产物、清单、目标整体哈希、文件数量和来源提交号。

该模块的关键约束是快照不可变。任何后续分析都不能修改已有快照的文件集合；需要更新目标时必须创建新快照。这样，发现的代码位置、工具结果和动态配置才能稳定地指向同一版本。删除项目在课程原型中不是核心流程，因此当前设计更强调保留证据而不是提供级联清理。

### 8.3 导入与解析

导入模块面向四种来源：ZIP 源码包、浏览器目录、固定提交的 HTTPS Git 仓库和单个 PE/ELF 文件。所有来源先进入统一的规范化流程，再生成清单。路径检查拒绝绝对路径、盘符、空段、父目录跳转、符号链接和大小写或 Unicode 归一化冲突。每个被排除的文件都写入排除记录和原因，避免静默丢失。

源码解析使用 Tree-sitter 提取模块、函数、行范围、字节范围、语法分支和调用候选。二进制解析使用 Ghidra Headless 导出函数、伪代码、地址、基本块、P-code、字符串和引用。解析器区分完整、部分和失败质量，保留解析错误与覆盖缺口。动态分派、宏展开和跨模块调用不能确定时，系统保留推断边或未知目标，不宣称完整调用图。

解析结果必须与快照清单一致：单元只能引用清单内文件，语言必须与文件记录匹配，源码位置必须落在原文件大小以内，代码字节长度必须与位置范围一致，文件覆盖记录必须完整。任何不一致都会导致整次结果拒绝入库。

### 8.4 静态规则扫描

静态规则扫描模块在源码目标上运行固定版本的 Semgrep，并把规则命中作为候选线索而不是漏洞结论。结果校验要求每条命中都属于清单内真实文件，规则版本匹配，扫描覆盖记录完整。解析错误、忽略文件和未覆盖文件都要进入报告。

模型侧还有一个只读的规则线索工具，用于返回内建词法特征，例如执行边界、文件路径边界、身份权限边界和内存操作。该工具明确标注不具备语义证明能力，只能帮助模型决定下一步阅读位置。Semgrep 命中、词法线索、危险函数名都不能单独构成发现。

### 8.5 保护识别与恢复

保护识别模块依据节区签名、熵值、入口点和导入表等线索判断加壳或混淆特征。高熵和已知节区名只是线索，不能证明保护已经处理，也不能证明目标具备合法资格。恢复模块把保护判断转成智能体可选择的工具步骤。

逆向智能体先提交恢复计划，计划只包含工具枚举、输入枚举、理由和限制，不包含命令或任意路径。工具范围包括 UPX 解包、FLOSS 字符串恢复、Ghidra 反编译、可选的本机 IDA/Hex-Rays 加 D-810 微码优化，以及内建 XOR/Base64 字符串候选。服务端保存计划版本，每次只把当前步骤变成一个恢复工作项。执行器按步骤运行工具，上传派生产物、哈希、日志和观察；服务端校验后写入恢复历史，并把可读伪代码或字符串证据并入后续语料库。

恢复失败的退出码、日志和未恢复范围都会保留。UPX 产物是新的派生对象，原始目标不被修改。IDA/D-810 属于本机商业工具，系统只做真实探测和结果记录，不承诺通用解混淆。当前版本修复了一处恢复链路缺陷：FLOSS 返回空字符串集时，曾因上传 0 字节文本工件被服务端拒绝而把该步骤误记为失败；执行器现跳过空集（`crates/executor/src/recovery.rs`），恢复步骤的失败判读不再被该问题污染。

### 8.6 多智能体编排

审计编排包含规划、逆向、审计、复核、验证方案和报告六个角色。角色可以共用一个模型服务，不要求六个不同模型，也不等同于开发人员分工。每个角色任务以运行、角色和输入键唯一标识，已完成任务可复用，失败任务保留错误。

规划角色读取目标目录和程序索引，给出审计优先级和策略。逆向角色只在二进制任务中出现，先规划恢复步骤，再根据真实工具结果决定是否继续、调整或收束。审计角色逐个阅读程序单元，提出候选发现和关键逻辑标注。每个新发现立即由复核角色在新上下文中阅读原始代码，独立判断输入可控性、可达性和防护缺口。对已经静态复核成立的发现，验证角色生成声明式运行配置；验证角色失败不会丢弃已完成审计。报告角色只总结已保存事实，不补写执行结果。

智能体循环有工具轮次上限、模型调用上限、任务时限和修复次数限制。模型输出未完整结束、引用不存在单元、引文不匹配或证据条件冲突时，系统会要求修复；修复超过上限后，任务失败并把错误保留为缺口。

### 8.7 发现、复核与标注

发现模块把漏洞结论拆成标题、类别、CWE、严重程度、严重程度理由、输入来源、危险操作、缺失防护、前提、影响、修复建议和证据。证据必须来自当前运行的真实程序单元，行范围有限，引用文本由服务端从原始代码重建。主位置必须出现在证据中，二进制位置按函数级地址处理。

复核模块要求模型对输入控制、可达性和防护缺口逐项表态，并列出额外攻击前提。只有所有必要前提都得到支持，结论才能是成立；要判定不成立，必须至少有一个由原始代码支持的反证；条件未知时必须是不确定。重复函数名、危险函数名或代码风格问题不能替代真实证据。

关键逻辑标注独立于漏洞发现，认证、加解密和注册逻辑即使实现安全也可以被标注。人工复核和标注修订带有期望版本号，版本冲突会拒绝覆盖；修订历史保留在数据库中，原始证据不被静默替换。

### 8.8 动态验证

动态验证的设计目标是把“静态结论”变成可重复、可检查的组件级或目标级观察，而不是宣称完成攻击。验证配置声明运行模式、适配器、目标路径、函数或命令行入口、基线输入、探测输入、观察方式、重复次数和单次时限。

系统当前只接受 Windows 宿主机验证模式，适配器包括 Python 函数、单入口 C/C++ 源码和原始 PE32/PE64。Python 适配器不接受被静默丢弃的全局变量或关键字参数；原生源码适配器只支持本地头文件的单入口构建；原始 PE 适配器只运行不可变目标字节。Windows 适配器不支持返回值金丝雀观察，当前主要使用文件创建观察和崩溃文本观察。

执行器把产品配置映射为客体桥接配置，准备输入、输出和工具目录，复制运行脚本，并显式传入项目私有 Python 与 Zig 路径。运行时以正常输入执行一次，再以探测输入重复执行若干次。每次运行有单次时限，取消时终止进程树。输出收集只接受声明过的文件，回执、观察和日志都保存为证据。

结论分为组件验证、异常复现、未复现、证据不足、错误和未知回收。组件验证和异常复现只有在基线正常、重复探测一致且进程回收确认时成立。未复现不等于程序安全，错误和未知回收不能当作失败或成功的替代状态。当前没有完整利用证据，因此利用状态保持未运行。

### 8.9 证据与产物存储

存储模块提供内容寻址、事务、状态保存、产物读取、事件流和幂等请求。所有业务写入经过控制服务的单写锁与事务；执行器和前端只能通过协议请求写入。产物按 SHA-256 保存，相同内容只存一份。读取产物时带大小限制，避免单个超大文件拖垮服务。

数据库保存对象之间的关系和状态，blobs 目录保存字节内容。备份和迁移必须同时考虑二者。运行事件在事务内写入并具有单调序号，前端断线后可以从指定序号继续读取，不需要重新推断任务状态。

### 8.10 报告生成

报告模块从数据库事实生成 JSON、HTML 和 Markdown。JSON 是结构化事实源，包含项目、快照、运行、程序单元、产物、覆盖、检查状态和审计证据；HTML 与 Markdown 面向阅读，包含概览、单元质量、逆向与解混淆、发现与复核、运行验证、覆盖缺口、错误和证据产物。

报告不采用模型口述作为事实来源，不把任务完成解释为目标安全。目标源码、函数名、字符串和模型解释都按不可信文本处理，HTML 输出执行转义。报告中的镜像摘要目前表示 Windows 执行环境组合，不是 Docker 镜像 ID，也不是完整客体镜像哈希。

### 8.11 工作队列与租约

工作队列采用数据库排队、执行器主动领取的模型。领取时控制服务更新执行器心跳，检查该执行器是否已有活动工作，检查是否已有运行类任务占用或存在未确认回收，再按创建时间选择能力匹配的排队任务。命中后生成尝试 ID 和一次性租约令牌，把令牌哈希、过期时间和执行器写入工作项，然后返回租约。

执行器定期心跳并上报进度。控制服务通过心跳返回取消请求和租约有效性。完成回报必须携带工作项、尝试和租约信息，服务端还会核对产物是否属于该尝试。迟到或重复结果不会覆盖新尝试；相同完成结果幂等返回，不同完成结果冲突拒绝。

租约超时不会自动重跑。非运行类工作默认有较短租约，运行类工作按冻结配置的总时限加缓冲计算。超时后工作项变为过期，关联运行进入失败或保持取消中；导入工作超时会把快照标记为失败。这样做的原因是旧进程是否终止尚未确认，自动重跑可能产生第二份目标进程。

### 8.12 协议与代码生成

协议是前端、控制服务和执行器之间的唯一共享契约，当前包含项目、运行、程序、报告、执行器、系统、发现和运行验证八个服务。普通请求与运行事件流使用同一份协议，避免两套状态定义漂移。

协议源文件是唯一事实来源，Rust 与 TypeScript 生成物不允许手工修改。协议变更需要重新生成并检查差异。执行器协议不暴露数据库对象，只传递租约、任务负载、产物和状态；模型密钥不会进入协议。

### 8.13 前端工作台

前端工作台提供项目创建、导入向导、任务状态与事件流、程序单元列表、代码查看、调用关系图、审计发现与复核、恢复面板、运行验证、模型连接和报告导出。前端只展示后端事实，不在本地推断漏洞或执行结果。

事件流按序号去重，断线时按最后序号补读。创建类操作使用请求 ID 保证幂等。复核和标注提交携带期望版本号，冲突时提示刷新。代码与模型输出按纯文本渲染，HTML 报告由服务端转义。界面把完成、部分完成、失败和未运行分开显示，不把完成状态显示为安全。

### 8.14 构建运维与模型连接

构建运维脚本负责工具引导、构建、启停、诊断、打包、通知和回归。项目私有工具安装在 `.tools`，运行数据、凭据和产物保存在 `.data`。启动器负责管理服务与执行器进程，退出时清理本实例拥有的子进程。便携包必须完整解压，不能只复制主程序。

模型连接模块只在控制服务持有 API 密钥，按当前 Windows 用户加密保存，执行器不接触密钥。连通性检查会真实调用模型并记录用量，不能代替漏洞审计测试。模型调用记录包含提示词版本、角色、请求产物、响应产物、时间、用量、完成原因和错误；用量未知时明确标记未知，不记为零。

验收样本与验证脚本（当前版本新增）：`evaluation/programs/` 提供四个自研受控二进制（ParcelDrop、RowVault、PermitLedger、TextRelay），配套脚本覆盖构建（`build_protected_tools.py`）、审计（`audit_protected_tools.py`）、防护验收（`verify_protected_tools.py`）、缺陷验收（`verify_vulnerabilities.py`）、智能体计划验收（`verify_agent_plans.py`）、PoC 复放（`verify_pocs.py`）与带显式 oracle 的变异模糊测试（`fuzz_protected_tools.py`）。这些样本用于在缺少合格外部软件时验证完整链路，不抵扣课程正式名额；正式软件验收仍以合格外部软件为唯一口径。

## 9. 关键运行流程

### 9.1 从导入到快照

用户选择导入方式后，控制服务先创建项目、快照和导入工作项，再等待执行器领取。执行器下载来源、执行路径检查、记录排除项、生成规范化内容和清单，最后上传清单、规范化产物和文件记录。控制服务校验清单版本、文件数量、路径规范、文件哈希、目标整体哈希和产物归属，全部通过后把快照置为就绪。

这条流程的重点是“先验证再可见”。用户看到可分析快照之前，系统已经完成文件边界、覆盖记录和哈希校验；失败快照保留错误信息，不会被当作空快照继续分析。

*图 4：导入与快照生成流程。路径检查、排除记录、规范化产物和控制服务校验之间的顺序。*

### 9.2 从恢复到审计

二进制任务进入审计后，控制服务先载入当前语料库，运行逆向角色。逆向角色检查保护特征和工具能力，提交恢复计划。服务端保存计划并逐步推进；每一步可能是不可用、缺少输入、执行失败或成功。执行成功时，派生产物、字符串证据和可读伪代码进入恢复历史，并在下一步前刷新程序目录。

![图 5 恢复计划与单步执行](diagrams/05a-recovery-flow.png)

*图 5：二进制恢复循环。计划版本、单步工作项、工具执行、恢复历史和语料库刷新之间的关系。*

恢复结束后，控制服务重新载入语料库并更新可审计单元数量。如果仍然没有可读代码，审计结束为部分或失败，保留恢复证据，不编造审计结果。如果有可读单元，规划角色给出优先级，审计角色逐单元分析，新发现立即进入复核；所有单元完成后，对已复核成立的发现生成验证方案，最后由报告角色基于数据库事实输出总结。

![图 6 审计与复核流程](diagrams/05b-audit-flow.png)

*图 6：语义审计与复核流程。规划、逐单元审计、独立复核、验证方案和报告输出之间的关系。*

### 9.3 动态验证

动态验证可以由用户直接提交配置，也可以使用验证角色保存的方案。控制服务先校验配置模式、适配器、目标路径、目标哈希、观察方式、输入限制和快照归属；存在关联发现时，还要求运行路径与发现证据文件一致。

创建成功后生成独立运行记录和运行工作项。执行器只接受 Windows 宿主机验证模式，准备冻结输入和工具脚本，在 Job Object 中运行正常输入一次和探测输入若干次。每次运行有独立输出、退出码、超时和回收状态。服务端收集回执、观察、日志和回收证明，校验目标、配置、环境摘要、工具记录和产物归属，再计算组件验证、异常复现、未复现或证据不足。

![图 7 动态验证时序](diagrams/06-runtime-sequence.png)

*图 7：动态验证时序。配置冻结、租约领取、宿主执行、结果校验和结论返回。*

### 9.4 取消与崩溃恢复

取消请求先进入取消中状态。排队任务可以被直接取消；已经运行的任务通过心跳收到取消请求，执行器终止进程树并等待 Job Object 报告活动进程归零。服务端只有在活动工作项和智能体任务都结束后，才把运行置为已取消。

控制服务或执行器异常退出后，恢复逻辑根据持久化记录判断旧任务。运行类任务随进程退出由 Job Object 回收，未完成结果不会计为成功；静态任务必须取得进程回收证明后才允许领取新任务。如果旧进程状态无法确认，执行器拒绝继续领取任务，要求人工检查或重置测试环境。

### 9.5 报告与复现

报告生成读取数据库中的项目、快照、运行、程序单元、审计证据、运行记录和产物。JSON 报告用于机器处理，HTML 和 Markdown 用于阅读。报告同时展示完成状态、覆盖缺口、错误、未运行状态和人工修订，不把缺失证据隐藏成完成。

复现一次报告时，需要保持相同快照、相同审计配置、相同模型设置和相同检查点。动态验证复现还需要相同目标哈希、配置指纹、工具版本和输入。工具或模型版本变化时，报告应说明差异，而不是沿用旧结论。

## 10. 接口设计

### 10.1 对外 RPC 接口

系统当前对外提供八个服务。项目服务负责项目和快照；运行服务负责任务创建、查询、取消和事件流；程序服务负责单元、图和标注；报告服务负责报告创建和读取；发现服务负责审计结果、发现和人工复核；运行验证服务负责动态验证；系统服务负责能力和模型连通性；执行器服务只供受信任执行器注册、领取任务和回报结果。

普通请求返回结构化对象，运行事件使用流式订阅。接口设计要求客户端提供请求 ID 的创建操作必须幂等；读取接口使用偏移和上限；事件流使用序号游标；人工修订使用期望版本号。接口错误分为参数错误、前置条件不满足、冲突、未找到、权限拒绝和服务内部错误，前端据此显示可操作提示。

### 10.2 控制服务与执行器协议

执行器先注册并提供能力清单，再通过领取接口获取工作租约。租约包含工作项、尝试、一次性租约令牌、任务类型、快照、运行、输入产物、任务负载和超时。执行器通过心跳接收取消请求，通过进度上报更新事件，通过完成接口提交结果、产物 ID、错误和进程回收确认。

任务负载是声明式数据。导入负载描述来源和快照；分析负载描述目标与清单；恢复负载描述单个工具步骤和输入哈希；运行动态负载描述冻结配置、清单和总时限。执行器不能通过负载提交任意命令或宿主路径。

### 10.3 运行适配器接口

Python 适配器用于组件函数验证，要求目标文件是快照内 Python 文件，函数名合法，输入是数据参数，不接受被静默丢弃的全局变量或关键字参数。原生源码适配器用于单入口 C/C++ 文件及本地头文件，当前只承诺固定 Zig 构建路径。原始 PE 适配器只运行不可变 EXE，不覆盖 DLL、服务和 GUI 场景。

验证模式要求正常输入一次、探测输入反复若干次，单次时限受上限约束。观察方式必须与适配器匹配。Windows 环境不支持返回值金丝雀，文件创建观察需要安全相对标记路径，崩溃观察依赖目标退出状态和可识别的崩溃文本。

### 10.4 错误与失败语义

客户端参数错误直接拒绝；模型输出不合规进入修复回路；模型提供商可重试错误最多重试一次；执行器租约超时不自动重跑；工具失败记录退出码、日志和失败原因；进程回收未确认时结果不能被采纳。系统把“失败”“未完成”“未运行”“部分完成”和“未复现”区分开，避免用同一种状态混合表达。

## 11. 安全设计

### 11.1 威胁模型

主要威胁包括：目标内容试图通过提示注入影响模型；模型幻觉伪造代码、工具结果或执行状态；执行器伪造或复用其他任务产物；客户端重复提交造成重复对象；路径穿越和符号链接破坏快照边界；运行目标产生意料之外的进程、文件或资源消耗；本机凭据被日志、打包文件或目标程序读取；工具版本被替换导致结果不可复现。

系统的防护重点与威胁匹配：所有模型输出结构化并校验；代码引文由服务端重建；执行器回报绑定尝试与租约；请求幂等；导入路径检查与符号链接拒绝；动态运行使用固定输入、时限、取消和进程回收；模型密钥只在控制服务并通过当前用户加密保存；工具版本固定并有供应链说明。

![图 8 信任边界与安全控制](diagrams/08-trust-boundaries.png)

*图 8：信任边界。不可信目标输入、受信任控制面、受限执行面和外部模型服务之间的数据流。*

### 11.2 与 SSDF 的对应

参考 NIST SSDF 的四个实践组，本项目做了如下映射。准备组织方面，工具版本、依赖、发布脚本和运行边界都有文档与校验。保护软件方面，模型输出、证据、密码学和凭据处理采用结构化边界。生产软件良好实践方面，导入、构建、打包和运行都有可重复流程。响应漏洞方面，失败、超时、未知状态和未完成项都保留证据并要求人工处理。该映射用于说明设计关注点，不代表项目已经完成正式合规认证。

### 11.3 模型安全边界

模型只能看到经过裁剪的目标内容、别名化单元 ID 和有限工具结果。提示词明确规定目标内容是不可信证据，不是指令。模型不能执行命令、读取宿主文件、访问网络或修改状态。恢复计划中的工具和输入来自封闭枚举；发现、复核和标注有字段白名单和长度限制；执行配置需要服务端再次校验。

模型响应在解析前保存为原始产物，解析失败和校验失败都记录模型调用状态。这样既能复现提示词与响应，也避免把模型叙事直接写进结论。独立复核使用新上下文，不复用审计对话，降低确认偏差。

### 11.4 运行安全边界

动态验证运行在普通用户权限下，使用独立临时目录、最小环境、固定目标与输入、单次时限、取消和进程树回收。Job Object 负责管理工具和目标进程树，能在取消、超时或句柄关闭时终止子进程；它不提供文件、网络、注册表或账号隔离。

因此，系统明确要求只导入和执行有权测试的目标。面对不熟悉的闭源程序、安装器、服务或驱动时，必须先评估副作用和恢复办法。源码编译和工具执行同样可能读取环境或写入临时文件，所以运行前要固定输入和哈希，运行后要保存日志与回收确认。

### 11.5 供应链与凭据

外部工具和依赖使用固定版本或提交，Ghidra、Semgrep、UPX、FLOSS、Zig、Python 和 Java 等工具在能力探测时校验版本。IDA 与 D-810 由使用者本机提供并真实探测。导入 Git 仓库时禁用钩子、递归子模块和凭据助手，只允许 HTTPS 与固定提交。

模型密钥由控制服务读取和调用，执行器与目标不接触密钥。令牌、数据库、产物和模型配置都保存在本机运行数据目录，不进入源码提交。便携包分发原始构建产物，不能分发已经运行并带有凭据的目录。

## 12. 可靠性与一致性设计

控制服务的所有写操作串行化，并在事务内同时更新业务对象、产物关联和事件。数据库是唯一事实源，前端和执行器不能绕过 API。对象创建使用请求 ID 与内容哈希保证幂等，同一请求重放返回原对象，不同内容复用同一请求 ID 会被拒绝。

任务分发使用尝试 ID 和租约令牌。每次领取生成新尝试，数据库只保存令牌哈希，明文令牌只在领取响应中出现。完成结果必须匹配尝试、工作项、执行器和租约哈希；旧尝试的迟到结果标记为陈旧，不覆盖当前状态。完成指纹使重复回报保持幂等，不同回报产生冲突。

状态机限制合法迁移，取消必须经过独立回收阶段。事件流有单调序号，断线重连不依赖浏览器内存。租约超时不会自动重跑，未确认回收会阻塞运行类任务。任何“完成”状态都必须有对应结果和回收证据，否则只能保持失败、部分或未知。

## 13. 性能、容量与成本

系统面向单机单操作员，性能设计以稳定、可预测和可恢复为主。模型调用默认上限 240 次，允许范围 4 到 2000 次；可审计程序单元默认 80 个，允许 1 到 500 个；单次智能体工具轮次默认 24 轮、允许 1 到 100 轮，规划角色压缩为一轮；单次审计总时限 60 秒到 24 小时（默认 10 800 秒）。

程序索引最多五万个单元和五十万条边，运行配置序列化后不超过一百二十八 KiB。代码读取单次最多两百行、两万四千字符，搜索最多返回三十条，图查询最多返回六十条，目录最多列出五百个单元。恢复计划最多保存四个版本，恢复历史最多八条，其中包含不可用和缺少输入的记录；单个审计单元最多提出五条发现和六条关键逻辑标注。

动态验证的重复次数为二到五次，另有正常输入一次；单次目标时限为一到十五秒。总时限由运行模式、重复次数和编译需求计算，并加入回收缓冲。模型和工具产生的日志有大小上限，超出时截断并标记。成本控制依赖调用预算、轮次预算、输入裁剪和产物复用，而不是依赖不稳定的费用估算。

## 14. 可维护性与可扩展性

新增源码语言时，需要增加 Tree-sitter 语法、语言识别映射、单元抽取和处理测试；新增恢复工具时，需要增加工具枚举、能力名、执行适配器、输入输出校验和恢复测试；新增运行适配器时，需要增加适配器枚举、入口类型、环境要求、观察器约束和端到端测试；新增协议字段时，需要修改协议源文件、重新生成 Rust 与 TypeScript，并保持旧数据可读。

模块边界遵循“谁拥有事实，谁负责校验”。领域层拥有结构和状态约束，应用层拥有工具适配与转换，控制服务拥有事务与编排，执行器拥有真实工具运行。扩展时不能把命令拼接、数据库写入或模型密钥带进新的执行分支。

## 15. 部署与运维

系统要求 Windows 11 x64。源码开发需要 Python 3.9+、Git、Visual Studio C++ 工具和 Windows SDK；产品验证与规则扫描使用项目私有 Windows Python 3.13.13 和 Zig 0.15.2；Ghidra 12.1.3、UPX 5.2.1、FLOSS 3.1.1 由引导脚本或工具清单安装；IDA 与 D-810 由使用者提供。

控制服务默认监听本机回环地址，前端生产资源由服务提供。执行器通过本机注册令牌接入，使用独立工作目录。运行数据保存数据库、产物、日志和凭据，工具保存在私有工具目录，两者都不进入源码提交。

运维重点是先停止再备份，数据库和产物必须一起保存；不要把其他会话正在使用的服务停止；不要删除活动任务记录来绕过进程回收确认；不要在带凭据的已使用目录上重新打包。诊断脚本输出工具能力，但仍需逐项查看，工具存在不代表功能验收通过。

## 16. 测试与验证策略

测试分为五层。领域层测试验证状态迁移、数据校验、引文重建、复核前提和运行配置。存储与协议测试验证事务、幂等、租约、迟到结果、事件重放和外部资源边界。工具适配测试使用真实或受控夹具验证导入、SAST、恢复和宿主机运行脚本。端到端测试通过浏览器和真实控制服务、执行器验证导入、分析、审计、恢复和运行界面。正式验收测试使用合格外部软件，记录版本、哈希、构建、运行条件和结果。

![图 10 测试分层与验收边界](diagrams/09-test-layers.png)

*图 10：从领域机制测试到正式验收的测试分层。机制测试不能自动抵扣正式软件验收。*

机制测试通过不等于正式能力验收。最近一轮宿主机运行改造已记录 Rust 格式、静态检查、全量测试、Python 脚本测试、前端检查和浏览器宿主机运行流程；这些记录不能自动覆盖之后合入的恢复链路，后者与真实模型、真实工具仍需要在最新基线上完整复验。更广泛目标的 FUZZ 适配、完整自动利用和开源对比仍未闭合。

每个测试结论必须说明范围。组件测试只能支持组件结论，自写夹具不能抵扣闭源软件名额，工具调用成功不能证明漏洞成立，任务完成不能证明目标安全。

## 17. 风险、限制与未决问题

| 风险 | 当前表现 | 影响 | 缓解方向 |
| --- | --- | --- | --- |
| 动态观察误报 | 崩溃文本观察可能把普通日志当成异常复现，原生构建未启用插桩 | 动态结论可信度下降 | 使用结构化退出与异常证据，增加正反对照 |
| 阻塞输入与超时 | 写入标准输入发生在等待超时之前，大输出读取完成后才截断 | 单次时限可能失真 | 读写与等待共享时限，流式限量采集 |
| 配置与提示契约 | 验证配置允许部分非字符串参数，但执行器只接受字符串；提示中的占位符未全部展开 | 方案显示就绪但运行失败 | 共用校验与展开规则，删除未实现承诺 |
| 运行结果字段语义 | 执行环境摘要仍使用镜像字段名 | 报告读者可能误以为 Docker 镜像哈希 | 新增显式环境摘要字段，旧字段兼容 |
| 宿主运行副作用 | Job Object 不提供文件和网络隔离 | 目标可能写文件或占用资源 | 限制授权目标，固定输入，保留恢复计划 |

## 18. 备选方案与取舍

在隔离方式上，Windows Sandbox、容器和虚拟机可以提供更强边界，但增加安装、镜像、映射、性能和演示复杂度；课程没有强制要求，项目选择宿主机运行加进程回收，并明确它不是安全隔离。保留的替代路径是：需要更强隔离时，把执行器后端抽象为可替换的运行适配器，而不改动控制服务和数据模型。

在架构形态上，微服务和消息队列更利于扩展，但会引入部署、一致性和调试成本；单控制服务加执行器更适合单机原型。若未来需要多用户并发，可把 SQLite 替换为服务器数据库，把工作队列替换为独立调度，但模型边界、租约和证据规则仍然保留。

在模型策略上，可以让模型直接执行命令或读取文件，但这会破坏可审计性和安全性；当前选择声明式工具与配置，代价是扩展工具时必须显式增加适配器。在恢复策略上，可以下载或生成固定脚本，但难以适应不同保护特征；当前选择智能体规划加服务端落地，代价是流程更长，但每步都有真实结果和失败证据。

在验证策略上，可以只做静态审计，但无法满足动态测试要求；也可以直接追求完整利用，但证据链难以在课程周期内闭合。当前选择组件验证、异常复现和未复现分级的保守路径，并明确未运行状态。

## 20. 结论

AegisAudit 的详细设计可以用一句话概括：用一个单机控制服务和受控执行器，把不确定的模型推理转化成可校验、可回溯、可失败的软件分析流程。系统的价值不在于让模型“说得多”，而在于让每个结论都有来源、每个动作都有边界、每个失败都有记录。

当前实现已经覆盖导入、解析、规则扫描、智能体恢复、语义审计、独立复核、验证方案、宿主机验证、证据存储和报告导出，但仍是集成中原型。真正的后续工作不是继续增加模块数量，而是闭合动态观察、模糊测试、自动利用、正式样本和交付验证，并把已经暴露的契约与恢复问题修到可回归状态。
