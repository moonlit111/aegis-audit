### 1.3 程序单元与分析结果

```rust
pub struct UnitInput {
    pub key: String,        // 分析结果内的稳定键
    pub name, path, language: String,
    pub start_line: u32, pub end_line: u32,
    pub start_byte: u64, pub end_byte: u64,
    pub address: String,    // 二进制：0x... RVA
    pub code: String,       // 源码片段或伪代码
    pub quality: String,    // PARSED | PARTIAL | FAILED
    pub metadata: Value,    // 含 kind（module/function 等）
}

pub struct EdgeInput {
    pub source_key, target_key, target_name, kind, certainty: String,
    pub line: u32, pub address: String,
}

pub struct AnalysisResult {
    pub schema_version: u32,
    pub units: Vec<UnitInput>, pub edges: Vec<EdgeInput>,
    pub files: Vec<FileResult>, pub tools: Vec<ToolExecution>,
    pub warnings: Vec<String>, pub metadata: Value,
}
```

**`AnalysisResult::validate(&self, manifest) -> Result<(), String>` 算法**

```
1. schema_version 必须 == SCHEMA_VERSION
2. units.len() <= 50_000 且 edges.len() <= 500_000
3. 构建 manifest 文件映射 files[path] -> FileRecord
4. 遍历 units：
   a. key 非空且全局唯一（否则 "empty or duplicate program unit key"）
   b. path 必须存在于 manifest（否则 "references a file outside the snapshot"）
   c. language 必须与文件记录一致；quality ∈ {PARSED, PARTIAL, FAILED}
   d. 若 language == "binary"：address 必须以 "0x" 开头且可解析为十六进制
   e. 否则（源码）：
      - start_line != 0 且 end_line >= start_line
      - start_byte <= end_byte 且 end_byte <= file.size
      - end_byte - start_byte == code.len()   ← 拒绝伪造位置的核心断言
   f. 累计该 path 的单元计数
5. 遍历 files（覆盖记录）：
   - path 必须在 manifest 内且不重复
   - language 与清单一致
   - unit_count 必须等于第 4f 步统计值
   - status ∈ {PARSED, PARTIAL, FAILED, UNSUPPORTED, NOT_SOURCE}
6. covered.len() 必须等于 manifest.files.len()（否则"遗漏覆盖记录"）
7. 每条 edge 的 source_key 必须存在；target_key 非空时也必须存在
```

**调用方**：控制服务在接收执行器回报的结构分析时调用；失败即拒绝入库。

**`AnalysisResult::partial()`**：任一文件状态不在 `{PARSED, NOT_SOURCE}`、任一单元 `quality != "PARSED"`、或 `warnings` 非空，即判为部分结果（用于运行状态 `PARTIAL`）。

### 1.4 运行状态机

```rust
pub enum RunState {
    Queued, Running, WaitingExecutor, Cancelling,
    Completed, Partial, Failed, Cancelled, LimitReached,
}

impl RunState {
    pub fn terminal(self) -> bool;              // 5 个终态
    pub fn as_str(self) -> &'static str;        // SCREAMING_SNAKE_CASE
    pub fn can_transition(self, next: Self) -> bool;
}
```

**迁移表（`can_transition`）**

| 当前 | 允许的下一状态 |
| --- | --- |
| `QUEUED`, `WAITING_EXECUTOR` | `RUNNING`, `WAITING_EXECUTOR`, `CANCELLING`, `CANCELLED`, `FAILED` |
| `RUNNING` | `CANCELLING`, `COMPLETED`, `PARTIAL`, `FAILED`, `LIMIT_REACHED` |
| `CANCELLING` | `CANCELLED`, `FAILED` |
| 终态 | 仅允许 `self == next`（幂等），其余一律拒绝 |

**单元测试固化**：`cancellation_requires_a_distinct_reaping_phase` 断言 `RUNNING → CANCELLED` 非法、`CANCELLED → RUNNING` 非法。设计含义：**取消必须经过回收阶段**。

### 1.6 恢复计划（命令不可注入的关键）

```rust
pub enum RecoveryTool { Upx, Floss, Ghidra, IdaD810, BuiltinStrings }
pub enum RecoveryInput { Original, Unpacked }
pub enum D810Profile { Instructions, ControlFlow }

#[serde(deny_unknown_fields)]
pub struct RecoveryStep {
    pub tool: RecoveryTool,
    pub input: RecoveryInput,
    pub reason: String,
    pub profile: Option<D810Profile>,   // 仅 IdaD810 允许
}

#[serde(deny_unknown_fields)]
pub struct RecoveryPlan {
    pub assessment: String,
    pub evidence: Vec<String>,
    pub steps: Vec<RecoveryStep>,
    pub limitations: Vec<String>,
}
```

**为什么能挡住命令注入**：`RecoveryTool` 与 `RecoveryInput` 都是**封闭枚举**，且结构标注 `deny_unknown_fields`。模型若输出 `{"tool":"shell","command":"..."}`，反序列化阶段即失败——不存在"先解析成自由字符串再拼接"的环节。`RecoveryTool::capability()` 把枚举映射到执行器能力名：`upx` / `floss` / `ghidra` / `ida-d810` / `string-recovery`。

**`RecoveryPlan::validate()` 规则**

```
assessment 非空 且 <= 8192 字节
evidence 非空 且 <= 16 条
steps.len() <= MAX_RECOVERY_STEPS (8)
limitations.len() <= 16
evidence 与 limitations 中每条 <= 4096 字节
每个 step.reason 非空且 <= 4096；tool != IdaD810 时 profile 必须为 None
```

**单元测试固化**：`recovery_plan_rejects_commands_unknown_tools_and_unbounded_steps` 断言含 `command` 字段、含未知工具 `shell`、或步骤数超过 8 的计划全部被拒绝。

### 1.8 运行配置（`domain/runtime.rs`）

```rust
pub const WINDOWS_RUNTIME_ADAPTERS: &[&str] = &[
    "WINDOWS_PYTHON_CALL", "WINDOWS_NATIVE_SOURCE",
    "WINDOWS_ORIGINAL_PE32", "WINDOWS_ORIGINAL_PE64",
];

pub struct RuntimeConfig {
    pub mode: String,          // "VERIFY" | "FUZZ"
    pub adapter: String,       // NATIVE_SOURCE / PYTHON_CALL / ELF + WINDOWS_* 系列
    pub path: String,          // 快照内相对路径
    pub function: String,
    pub globals: BTreeMap<String, Value>,
    pub fixtures: Vec<RuntimeFixture>,   // { path, content }
    pub baseline: Invocation,            // { args, kwargs, stdin }
    pub probe: Invocation,
    pub observer: String,      // 默认 "SANITIZER"
    pub marker_path: String,   // 默认 "marker.txt"
    pub repeats: u32,          // 默认 2，范围 2..=5
    pub timeout_seconds: u32,  // 默认 5，范围 1..=15
    pub fuzz: FuzzOptions,
}
```

**关键方法**

| 方法 | 实现要点 |
| --- | --- |
| `scope()` | `mode == "FUZZ"` → `DYNAMIC_TESTING`，否则 `RUNTIME_VERIFICATION` |
| `target_scope()` | PYTHON_CALL → `COMPONENT`；NATIVE_SOURCE → `INSTRUMENTED_BUILD`；其余 → `ORIGINAL` |
| `fingerprint()` | `sha256(serde_json::to_vec(self))`，用于绑定配置版本 |
| `deadline()` | FUZZ：`budget_seconds + 240`；VERIFY：`(repeats+1)*(timeout_seconds+5) + 150` |
| `target_path(path)` | 非空、≤512 字节、不含 `\` `:` `\0` `\n` `\r`、每段非空且非 `.`/`..` |
| `identifier(name)` | 非空、≤100、不以 `__` 开头、字符仅 `[A-Za-z_][A-Za-z0-9_]*` |
| `validate()` | 见下 |

**`RuntimeConfig::validate()` 规则**

```
mode ∈ {VERIFY, FUZZ}
adapter ∈ 传统集合{PYTHON_CALL, NATIVE_SOURCE, ELF} ∪ WINDOWS_RUNTIME_ADAPTERS
target_path(path) 通过
fixtures.len() <= 16，globals.len() <= 16
序列化总大小 <= 128 KiB
repeats ∈ 2..=5
```

**设计边界**：`FUZZ_SCOPE` 与 `FuzzOptions` 已在领域层定义，但执行器分发路径只接受 Windows `VERIFY`，`FUZZ` 被显式拒绝（见第 10 节）。

## 2. 导入与解析模块

**位置**：`crates/application/src/{import.rs, source.rs}`

### 2.1 导入限制与路径安全

```rust
pub struct ImportLimits { /* 数量、单文件与总大小上限 */ }
pub struct SourceBundle { /* 规范化后的文件集合 */ }
```

| 函数 | 签名 | 实现要点 |
| --- | --- | --- |
| `relative_path(raw)` | `&str -> Result<String>` | 归一化分隔符；拒绝绝对路径、盘符、`..` 越界、空段 |
| `portable_path_key(path)` | `&str -> String` | 生成**大小写与 Unicode 归一化**后的可移植键，用于检测"同名不同写法"冲突 |
| `language(path)` | `&str -> &'static str` | 扩展名 → 语言标签（python/go/c/cpp/…），未识别返回非源码标记 |
| `unpack_source` | → `SourceBundle` | 解压 ZIP/目录，逐条应用限制，收集 `Exclusion{path, reason}` |
| `pack_directory` | → 字节流 | 浏览器打包目录 |
| `inspect_binary(bytes)` | `-> Result<Value>` | 识别 PE/ELF 头与架构，供快照 kind 判定 |

**安全检查清单（设计契约）**：相对路径合法性、符号链接、大小写/Unicode 冲突（借助 `portable_path_key`）、文件数量与大小上限。**每一条排除都必须写入 `exclusions` 并给出原因**——排除不是静默丢弃。

**Git 导入**：固定 `resolved_revision`（最终提交），**不执行 hooks、不运行安装脚本、不递归子模块**。

### 2.2 源码解析

`source.rs::analyze_sources(...)` 的流程：

```
1. 按 language 选择 Tree-sitter 语法
2. 逐文件解析，抽取：
   - 模块单元（kind = module）
   - 函数单元（kind = function，带 start/end line、start/end byte）
   - 语法分支（if/for/while/try 等，供语义审计参考）
   - 保守调用候选（call expression → EdgeInput）
3. quality 判定：完全解析 = PARSED；部分/含错误节点 = PARTIAL；解析失败 = FAILED
4. 输出 AnalysisResult{units, edges, files, tools, warnings, metadata}
```

**保守性原则**：动态分派、宏展开、跨模块解析结果不确定时，边写入 `certainty = "INFERRED"` 或留空目标，**不冒充确定边**。**不宣称全程序污点分析**。

支持的语法包（`Cargo.toml` 锁定）：`tree-sitter 0.25`、`tree-sitter-python 0.25`、`tree-sitter-go 0.25`、`tree-sitter-c 0.24`、`tree-sitter-cpp 0.23`。

### 2.3 二进制解析

由执行器调用 **Ghidra Headless 12.1.3**：导出函数、伪代码、入口/RVA、基本块、P-code、字符串与引用。产出映射到 `UnitInput`，`language = "binary"`，`address = "0x..."`。

**边界**：伪代码不是可直接编译的 C；地址映射**主要在函数级**；反编译失败与截断必须保留原始日志（写入 `ToolExecution.log_artifact_id`）。ELF 在 Windows 宿主仅做静态分析，**不原生执行**。

## 4. 保护识别与恢复模块

**位置**：`crates/application/src/{protection.rs, recovery.rs, deobfuscation.rs, ida_d810.rs}`

### 4.1 保护识别

```rust
pub fn signature(section_name: &str) -> Option<&'static str>;  // 节区签名匹配
pub fn entropy(data: &[u8]) -> f64;                            // 香农熵
pub fn assess(bytes: &[u8]) -> Result<Value>;                  // 综合评估
pub fn structure_summary(bytes: &[u8]) -> Result<Value>;       // 结构摘要
```

**识别输入**：PE 节区名与签名、节区熵值、入口点、导入表特征。

**`entropy` 算法**：对字节序列统计 256 个符号的出现频率 `p_i`，计算 `H = -Σ p_i · log2(p_i)`，返回比特/字节（0–8）。高熵常见于压缩/加密段，但**签名或高熵只是线索**：既不能证明保护已处理，也不能证明目标具备闭源资格。

### 4.2 恢复工具适配

```rust
pub const FLOSS_VERSION: &str = "3.1.1";
pub fn floss_path() -> Option<PathBuf>;
pub fn floss_spec(input: &Path, work: &Path) -> Result<ProcessSpec>;
pub fn floss_strings(raw: &Value, input: &[u8]) -> Result<d::RecoveredStrings>;
pub fn builtin_strings(raw: &Value, input: &[u8]) -> Result<d::RecoveredStrings>;
pub fn annotate(...);                       // 把恢复字符串注入伪代码注释
pub fn readable_code(result: &AnalysisResult, input_hash: &str) -> String;
```

| 工具 | 版本 | 处理 | 产物 |
| --- | --- | --- | --- |
| UPX | 5.2.1（固定摘要） | 解包 | 派生可执行文件 + 节区/入口映射 |
| FLOSS | 3.1.1 | PE x86/x64 模拟执行恢复字符串 | `RecoveredStrings` |
| 内建 | — | XOR/Base64 启发式候选 | `RecoveredStrings`（`tool=BuiltinStrings`） |
| Ghidra | 12.1.3 | 反编译 | 伪代码 + 结构 |
| IDA/Hex-Rays + D-810-ng | 使用者提供 | 微码按规则优化 | 优化前后伪代码 + 命中数 |

**`deobfuscation.rs`**：`patterns()` 给出混淆特征模式集；`assess(bytes)` 评估混淆程度；`recover(bytes, workdir)` 执行恢复。**恢复产物作为后续工具输入，不修改原始目标**。

**`ida_d810.rs`**：真实探测本机 IDA/Hex-Rays 安装（通过 `scripts/configure_d810.py` 配置），未探测到则不可用。D-810 命中数与优化前后伪代码**必须留痕**；**不能宣称通用解混淆**。

### 4.3 恢复编排

`recovery.rs` 负责把校验通过的 `RecoveryPlan` 落为执行步骤：

```
服务端：校验计划 → 创建 kind = "RECOVER" 的工作项
        payload = { step 序列, 输入 artifact_id, 工具能力要求 }
执行器：按步骤依次调用工具
        每步：下载输入 → 运行工具 → 上传派生产物 → 上报 ToolExecution
最终：  RecoveryResult（含 analysis / tools / observation / warnings）
服务端：校验 input/output 哈希与租约、产物归属 → 入库
        → 恢复产物并入 Corpus → 触发后续语义审计
```

**失败也是证据**：工具失败时记录退出码、日志产物、失败原因，运行进入 `FAILED` 或 `PARTIAL`。

```rust
pub struct Corpus {
    pub units: HashMap<String, d::ProgramUnit>,
    pub order: Vec<String>,                  // 可审计单元顺序（code 非空）
    pub edges: Vec<d::ProgramEdge>,
    pub target: Value,                       // 目标元信息
    aliases: HashMap<String, String>,        // 真实 id -> U0001
    identifiers: HashMap<String, String>,    // U0001 -> 真实 id
}
```

- `new(...)` 为每个单元分配别名 `U0001`、`U0002`…；`order` 只含 `code` 非空的单元。
- `references(value, to_model)`：递归遍历 JSON，把 `unit_id` / `source_id` / `target_id` / `audited_unit_ids` 在**别名 ↔ 真实 ID** 之间转换。**调模型前 to_model=true，收模型输出后 to_model=false**。这让模型只需处理短别名，降低幻觉引用错误 ID 的概率，也避免泄露内部 UUID。

### 5.2 七个只读工具（`Corpus::tool`）

| 工具名 | 参数 | 返回 | 约束 |
| --- | --- | --- | --- |
| `inspect_target` | — | 目标元信息 | — |
| `read_unit` | `unit_id` | 单元首段代码视图 | 默认 160 行，单次 ≤200 行，≤24000 字符 |
| `read_span` | `unit_id, start_line, end_line` | 指定行范围 | 同上 |
| `search_code` | `query` | 匹配行列表 | query 1–160 字节；最多返回 30 条后标 `truncated` |
| `query_graph` | `unit_id` | 相关边 | 最多 60 条；返回 `complete: false` |
| `scan_rules` | — | 内建词法线索 | 最多 100 单元；`semantic_proof: false` |
| `key_logic_candidates` | — | 关键逻辑候选 | 见 5.3 |

**未注册工具一律拒绝**：`_ => bail!("未注册的工具；只允许当前目标的只读查询")`。

**`view` 实现要点**：

```
1. 真实 id 解析；不存在 → 错误"程序单元不属于当前分析任务"
2. base = 二进制 ? 1 : unit.start_line
3. 行范围裁剪：first >= base 且 last - first <= 199
4. 逐行输出 "行号|内容\n"；累计超过 24000 字符即停
5. 返回 { unit_id(别名), path, name, language, artifact_id, address,
          mapping: 二进制 ? "FUNCTION_LEVEL_ONLY" : "SOURCE_LINES",
          start_line, end_line, unit_end_line, truncated,
          numbered_code, clues }
```

**`mapping` 字段**刻意区分源码行映射与二进制函数级映射——二进制没有源码行号，不能假装有。

**`focus` 实现要点**（模块级审计的委派）：当单元是模块且含子函数时，用占位行替换子函数体：

```
{行号}|[function U00xx: 函数名 — body assigned to its own audit task]
```

并返回 `delegated_functions` 与 `audit_scope` 提示"只审计未被委派出去的函数体之外的代码"。这避免了同一段代码被模块任务与函数任务重复审计、重复报告发现。

### 5.3 关键逻辑线索


`key_logic_candidates()` 汇总所有存在线索的单元。**命中只作为候选依据**：最终标签必须由"候选模式 + 调用关系 + 模型语义"共同支撑，不按函数名定性。

## 6. 多智能体编排模块

**位置**：`crates/server/src/agents.rs`

### 6.1 结构与职责

```rust
impl Store {
    pub async fn recover_audits(&self) -> Result<()>;                          // 启动时恢复中断审计
    pub fn spawn_audit_worker(&self, shutdown: CancellationToken) -> JoinHandle<()>;
    async fn next_audit(&self, shutdown: &CancellationToken) -> Result<()>;
    pub async fn drive_audit_with_model(
        &self, id: &str, model: &str, config: &d::AuditConfig,
        client: &dyn ModelClient, shutdown: &CancellationToken,
    ) -> anyhow::Result<()>;
    pub async fn finish_audit(&self, id: &str, error: Option<String>) -> Result<()>;
}

struct AgentContext<'a> {
    store: &'a Store, run_id: &'a str, model: &'a str,
    config: &'a d::AuditConfig, client: &'a dyn ModelClient,
    shutdown: &'a CancellationToken, corpus: &'a Corpus,
}
impl AgentContext<'_> {
    async fn execute(&self, role: &str, key: &str, input: Value) -> Result<d::AgentTask>;
    async fn conversation(&self, task: d::AgentTask, input: Value) -> Result<d::AgentTask>;
    async fn turn(&self, task: &d::AgentTask, request: &ModelRequest) -> Result<(ModelResponse, d::ModelCall)>;
    async fn cancelled(&self);
}
```

### 6.2 `drive_audit_with_model` 主流程

```
1. config.validate()
2. corpus = audit_corpus(id)
3. 事务内：run.summary["vulnerability_audit"] = "RUNNING"
            run.summary["audit_config"] = config
            run.summary["eligible_unit_count"] = corpus.order.len()
            audit_workflows.state = "RUNNING"
            追加事件 AUDIT_STARTED（total = corpus.order.len()）
4. 若 corpus.target["kind"] == "BINARY"：
   4.1 REVERSE.execute("REVERSE", "recovery",
         { program: catalog, tool_environment: recovery_context(id) })
   4.2 corpus = audit_corpus(id)          ← 重新载入，纳入恢复产物
   4.3 更新 eligible_unit_count
5. ensure !corpus.order.is_empty()
   （否则："没有可供语义审计的代码；逆向结果和解析缺口已保留"）
6. 进入后续角色流程（PLANNER → AUDITOR → REVIEWER → VERIFIER → REPORTER）
```

**要点**：REVERSE 的恢复产物**在审计前**合入语料库，形成"保护 → 恢复 → 审计"闭环；若恢复后仍无可审计代码，明确报错并保留逆向与缺口证据，**不伪造审计结果**。

### 6.3 `conversation`：校验-修复回路

```
输入：task（role, item_key）、input
1. corpus = audit_corpus(run_id)
2. input = corpus.references(input, to_model = true)     ← 真实 ID → 别名
3. tool_budget = (role == "PLANNER") ? min(max_tool_rounds, 1) : max_tool_rounds
4. messages = [
     system: system_prompt(role) + 工具预算说明,
     user:   input 序列化
   ]
5. 循环 for _ in 0..(tool_budget + 5)：
   a. 组装 ModelRequest{ model, messages, max_tokens: 16384,
                         reasoning_effort: repairs > 0 ? "disabled" : "high" }
   b. response = turn(task, request)  ← 记录 ModelCall（时间/用量/finish_reason）
   c. 提供商可重试错误（retryable）且尚未重试过 → provider_retried = true，
      sleep(2s)（可被 shutdown 中断）→ continue
   d. 若 response.finish_reason != "stop" → 判为无效（"模型输出未完整结束：{reason}"）
   e. action = parse_action(response.content)
   f. messages.push(assistant 消息)
   g. 分支：
      - Tool{name, arguments}：
          若 tools == tool_budget → 追加 user "No tool requests remain…" 并计数，
                                     本次请求不执行
          否则执行工具，结果作为 tool 消息回喂；tools += 1
      - 最终结果：由服务端校验
          校验失败 → repairs += 1，把**校验错误信息**回喂要求重出
          校验通过 → 落库（别名换回真实 ID），任务 SUCCEEDED
6. 超预算或无法收敛 → 任务标记失败，附最后错误
```

**关键设计**

| 机制 | 效果 |
| --- | --- |
| 工具预算硬上限 | 模型不能无限试探，成本可控 |
| 预算耗尽后的"收束指令" | 逼模型基于已有证据收尾，而非空转 |
| `finish_reason` 检查 | 截断输出不当作有效结论 |
| 修复回路 + 降低 reasoning_effort | 让模型专注修正格式，而非继续发散 |
| 提供商重试上限 1 次 | 避免放大成本 |
| 任务幂等（见 6.4） | 重试不重复消耗模型调用 |

### 6.4 任务幂等与状态

```rust
async fn execute(&self, role, key, input) -> Result<AgentTask> {
    let task = self.store.begin_agent_task(self.run_id, role, key).await?;
    if task.status == "SUCCEEDED" { return Ok(task); }   // 已完成直接复用
    let result = self.conversation(task.clone(), input).await;
    if let Err(error) = &result {
        self.store.stop_agent_task(task, &error.to_string(), self.shutdown.is_cancelled()).await?;
    }
    result
}
```

`begin_agent_task(run_id, role, item_key)` 以三元组建立唯一任务，是重试与恢复不重复消耗调用的基础。

### 6.5 六个角色与约束映射

| 角色 | 输入 | 输出 | 硬约束 |
| --- | --- | --- | --- |
| PLANNER | catalog + target | `Plan`（优先级列表） | 工具轮次压缩为 ≤1；只排序，不逐函数审计 |
| REVERSE | catalog + 工具环境 | `RecoveryPlan` | 工具/输入枚举，≤8 步，无命令字段 |
| AUDITOR | 单元代码视图 | `FindingDraft` + `AnnotationDraft` | 引文必须是真实代码与有效行范围 |
| REVIEWER | **独立的新上下文中原始代码** | `ReviewDraft` + 分项 assessments | 不继承审计对话；VALIDATED/REJECTED 有前置条件 |
| VERIFIER | 发现 + 可用运行条件 | `RuntimeConfig` 或"缺少条件"说明 | 不自行写入成功状态 |
| REPORTER | 已存证据 | `ReportOutput` | 不补写执行结果 |

## 7. 发现、复核与标注模块

**位置**：`crates/domain/src/audit.rs`、`crates/server/src/audits.rs`

### 7.1 引文校验：`evidence()` 算法

```rust
pub fn evidence(
    input: &[EvidenceInput],            // { unit_id, start_line, end_line, quote }
    units: &HashMap<String, ProgramUnit>,
) -> Result<Vec<EvidenceRef>, String>;
```

```
1. input 非空且 <= 16 条（否则"每条结论必须引用 1—16 处原始代码证据"）
2. 对每条：
   a. unit = units[unit_id]；不存在 → "证据引用了当前任务以外的程序单元"
   b. base = 二进制 ? 1 : unit.start_line
   c. 行范围检查：
        start_line >= base
        end_line >= start_line
        (end_line - base) < code 行数
        end_line - start_line <= 100
        quote.len() <= 8192
      任一不符 → "证据的行范围或引用文本无效"
   d. excerpt = code 第 [start_line-base ..= end_line-base] 行的原文
   e. 若 quote 非空：
        归一化比对（逐行 trim 后拼接）
        既不包含原 quote 也不包含归一化 quote
        → 拒绝，并把该范围的实际代码（截断 2200 字符）回喂给模型纠错
   f. 通过后生成 EvidenceRef：
        quote 采用**服务端按原始缩进截取的 excerpt**，不采用模型文本
```

**核心思想**：模型只被允许"指认位置"，引文内容由服务端从原始代码重建。这使"编造一行不存在的代码并配上一句结论"在结构上不可行。

**单元测试固化**：`line_citations_are_resolved_from_original_code_and_explicit_fabrication_is_rejected` 断言 `quote` 与原始行不一致时报错、行号越界时报错、正确引用时返回带原始缩进的原文。

### 7.2 Finding 校验：`FindingDraft::validate`

```
category ∈ {INJECTION, PATH_TRAVERSAL, AUTHORIZATION, MEMORY_BOUNDS}
severity ∈ {CRITICAL, HIGH, MEDIUM, LOW, UNKNOWN}
cwe == "UNKNOWN" 或 CWE-{1..5 位数字}
title, severity_reason, input_source, sink, missing_guard,
  preconditions, impact, recommendation 均非空且 <= 8192 字节
title.len() <= 300
evidence 中必须至少有一条 unit_id == self.unit_id   ← 主位置必须有证据
→ 调用 evidence() 完成引文校验并返回规范化 EvidenceRef
```

**`FindingDraft::fingerprint(snapshot, unit)`**：`sha256("{snapshot}:{path}:{address}:{location:?}:{category}")`，用于同一快照内的去重与稳定标识。

### 7.3 Review 校验：`ReviewDraft::validate_model`

```
1. 基础校验 validate()：
   verdict ∈ {VALIDATED, REJECTED, INCONCLUSIVE}
   rationale 非空且 <= 8192；counter_evidence / missing_information <= 8192
   evidence 校验
2. assessments.len() ∈ 3..=12
3. INPUT_CONTROL / REACHABILITY / DEFENSE_GAP 各**有且仅有**一项
4. 每项：
   check ∈ {INPUT_CONTROL, REACHABILITY, DEFENSE_GAP, EXTRA_PRECONDITION}
   status ∈ {SUPPORTED, REFUTED, UNKNOWN}
   rationale 非空且 <= 4000
   status != UNKNOWN 或 evidence 非空 → 必须调用 evidence() 校验
5. 交叉约束：
   verdict == VALIDATED 且任一 assessment 非 SUPPORTED
     → 拒绝："存在未知或被反证的必要攻击条件，不能判为 VALIDATED；
              请使用 INCONCLUSIVE 或 REJECTED"
   verdict == REJECTED 且无任一 REFUTED
     → 拒绝："REJECTED 必须至少有一项原始代码支持的 REFUTED 反证"
```

**设计含义**：把"漏洞是否成立"拆成"输入可控性 / 可达性 / 防护缺口"三个必须逐项表态的子问题，从结构上禁止"条件未知却宣布有效"。

**单元测试固化**：`unknown_attack_prerequisites_cannot_be_validated_or_silently_rejected`。

**兼容性**：`assessments` 字段对旧数据与人工作业可选（`#[serde(default)]`），仅对模型输出强制要求。

### 7.4 标注校验：`AnnotationDraft::validate`

```
tag ∈ {AUTHENTICATION, CRYPTOGRAPHY, REGISTRATION}
subtype（人工可空，非空时必须属于对应集合）：
  AUTHENTICATION -> {PASSWORD, SESSION, TOKEN}
  CRYPTOGRAPHY   -> {PASSWORD_HASH, HASH, SYMMETRIC, ASYMMETRIC, RANDOM}
  REGISTRATION   -> {ACCOUNT}
rationale 非空且 <= 8192
evidence 中至少一条 unit_id == self.unit_id
→ evidence() 校验
```

### 7.5 人工修订与冲突检测

- `SubmitReviewRequest` 携带 `expected_revision`；版本不符返回冲突错误；
- `UpdateAnnotationRequest` 同样带 `expected_revision`；
- 标注修订写入 `annotation_revisions` 历史表，保留原证据与修订轨迹；
- `Finding.review_status` / `verification_status` 由系统与人工动作共同维护，**不由模型直接设定**。

### 8.4 幂等：`requests` 表

```sql
CREATE TABLE requests (
  method TEXT NOT NULL, request_id TEXT NOT NULL,
  body_hash TEXT NOT NULL, object_id TEXT NOT NULL,
  PRIMARY KEY (method, request_id)
);
```

**处理逻辑**：创建类请求先查 `(method, request_id)`：

- 不存在 → 正常创建，记录 `body_hash` 与新建对象 id；

应用于 `CreateProject` / `CreateSnapshot` / `CreateRun` / `CreateReport` / `CreateRuntime` / `SubmitReview`。

## 9. 工作队列与租约

**位置**：`crates/server/src/store.rs`（`claim_work` / `heartbeat` / `progress` / `complete_work` / `expire_leases`）

### 9.1 `claim_work(executor_id)` 算法

```
1. 取单写锁，开事务，更新执行器 last_seen（touch_executor）
2. 若该执行器已有 RUNNING 或 EXPIRED 工作 → 返回 None（单执行器单租约）
3. 若存在 kind='RUNTIME' 且 (state='RUNNING' 或 (state='EXPIRED' 且 cleanup_confirmed=0))
   → 返回 None（保护宿主机：未确认清理阻塞所有执行器）
4. 取最多 200 条 state='QUEUED' 且 cancel_requested=0 的工作，按 created_at, id 排序
5. 逐条检查执行器能力是否覆盖该工作的 capability；不覆盖则跳过
6. 命中第一条：
   a. attempt = 新 UUID；token = "{uuid}.{uuid}"
   b. timeout_seconds = lease_timeout_seconds(kind, payload)
   c. UPDATE work_items SET state='RUNNING', executor_id, attempt_id,
        lease_hash = sha256(token), lease_expires = now + LEASE_SECONDS
   d. INSERT work_attempts(attempt_id, work_item_id, executor_id, lease_hash, started_at)
   e. 若关联 run：run.state = RUNNING（首次填 started_at），追加 RUN_STARTED 事件
   f. 构造 WorkLease{ work_item_id, attempt_id, lease_token(明文，仅此一次),
                      kind, snapshot_id, run_id, input_artifact_id,
                      payload(JSON), timeout_seconds }
   g. 提交事务，notify_waiters，返回 lease
7. 无可用工作 → 提交，返回 None
```

**要点**：数据库只存 `lease_hash`，明文 `lease_token` 仅在响应中返回一次；`attempt_id` 区分同工作项的多次尝试。

### 9.2 授权与迟到结果丢弃

```rust
pub async fn authorize_lease(&self, work, attempt, token) -> Result<String>;      // 返回 executor_id
pub async fn authorize_lease_on(conn, work, attempt, token) -> Result<String>;
pub async fn ensure_output(conn, id, work, attempt) -> Result<d::Artifact>;
```

`ensure_output` 要求产物必须满足 `artifacts.id = ? AND work_item_id = ? AND attempt_id = ?`，否则"结果引用了不属于当前工具尝试的产物"。**这切断了执行器用别的尝试（或别的运行）的产物来伪造结果的可能**。

### 9.3 `complete_work` 算法

```
1. outcome ∈ {COMPLETED, FAILED, CANCELLED, LIMIT_REACHED}
2. completion = sha256(json!([outcome, result_id, error, reaped]))   ← 内容指纹
3. 取写锁，开事务
4. 校验 work_attempts 中 (attempt, work, executor) 的 lease_hash == sha256(token)
   否则 → "工具尝试身份不匹配"
5. 若 work_items.attempt_id != attempt（说明已有更新尝试）：
     把该 attempt 标记 finished_at / outcome='STALE'，返回 Ok(false)   ← 迟到结果丢弃
6. 若 work_items.completion_hash 非空：
     与 completion 相同 → 返回已有结果（幂等）；不同 → "该工具尝试已提交不同的结束结果"
7. 否则落库：更新工作状态、写入产物关联、追加事件、按需推进 run 状态
```

**三重防线**：租约令牌 → 尝试身份 → 完成指纹。即使消息被重放、乱序或伪造，也不会污染状态。

### 9.4 租约超时：`expire_leases`

```
1. 取写锁，选出 state='RUNNING' 且 lease_expires < now 的工作
2. 对每条：
   a. work_items.state = 'EXPIRED'
   b. 若关联 run 且非终态：
      run.error = "执行器租约已失效，旧工具进程回收尚未确认；不会自动重复执行"
      若该工作是 recovery.running_work_id → 更新 recovery.status（CANCELLING 或 FAILED）
      若非 CANCELLING → run.state = FAILED，填 finished_at
      追加 LEASE_EXPIRED 事件
   c. 若为导入工作（无 run）→ snapshot.state = 'FAILED'，
      error = "导入执行器失联，进程状态未确认"
3. 提交；有变更则 notify_waiters
```

**设计取舍**：**超时不自动重跑**。原因是无法确认旧进程是否已终止，自动重跑会让宿主机上出现两份目标进程，违反资源与证据约束。宁可让运行失败并要求人工介入。

### 10.4 Job Object 进程管理（`windows_job.rs`）

### 10.5 结论分级与 `exploitation`

| 结论 | 含义 |
| --- | --- |
| 组件验证 | 目标函数被成功调用并产生预期观察 |
| 异常复现 | 观察到非预期行为（如崩溃、错误输出） |
| 未复现 | 探测输入未触发异常 |
| 错误 / 取消 / 未知回收 | 环境或进程状态未确定，**不得当作成功或失败** |

**边界**：崩溃不能推导任意代码执行；无完整利用证据时 `exploitation` 保持 `NOT_RUN`；`RuntimeResult.image_id` 在 Windows 上表示执行策略/版本组合摘要，**不是 Docker 镜像 ID**。

### 10.6 VERIFY 与 FUZZ 的当前边界

- 产品运行配置与执行器分发**只接受 Windows VERIFY**；`FUZZ` 被显式拒绝；
- `FuzzOptions` 与 `FUZZ_SCOPE` 已在领域层定义（`engine=MUTATION`、`input_mode=STDIN`、`max_cases=256`、`budget_seconds=30`、`random_seed=71413`），libFuzzer/TinyInst 为独立引擎实验；
- **尚未贯通 UI、配置、执行器与报告**，因此不能计作 R07 完成。

## 12. 执行器详细设计

**位置**：`crates/executor/src/{main.rs, client.rs, jobs.rs, recovery.rs, runtime.rs}`

### 12.1 主循环（`main.rs`）

```rust
struct Options { /* endpoint、令牌、数据目录、能力开关 */ }
struct Identity { /* executor_id、token */ }
struct Active { /* 当前租约、心跳句柄 */ }

async fn capabilities(options: &Options) -> (Tools, Vec<p::ToolCapability>);
async fn version(program: &str, arg: &str) -> Option<String>;
async fn runtime_recovery_completion(...);
async fn main() -> Result<()>;
```

**启动与循环**

```
1. 探测本机工具能力（Tree-sitter 由 Rust 内置；Ghidra/Semgrep/UPX/FLOSS/IDA 探测版本与可用性）
2. RegisterExecutor(name, platform, architecture, capabilities) → 获得 executor_token
3. 循环：
   a. ClaimWork → 无工作则等待（长轮询/退避）
   b. 按 lease.kind 分派：
      - 结构分析 / RECOVER → jobs.rs / recovery.rs
      - RUNTIME → runtime.rs（宿主机动态任务）
   c. 启动心跳任务（Heartbeat），响应 cancel_requested
   d. 执行中 ReportProgress 上报进度
   e. CompleteWork(outcome, result_artifact_id, error, processes_reaped)
4. 退出前：runtime_recovery_completion 确保旧运行任务回收或幂等重报
```

**能力上报**：只有 `available = true` 的能力才会匹配到对应工作项；工具缺失时该项工作不会分派给该执行器（可能一直排队，需人工处理）。

### 12.2 工具任务（`jobs.rs`）

| 工作类型 | 处理 |
| --- | --- |
| 结构分析（源码） | 下载快照 ZIP → 解包 → Tree-sitter 解析 → 上传 `AnalysisResult` |
| 结构分析（二进制） | 下载目标 → Ghidra Headless → 导出伪代码/结构 → 上传 |
| SAST | 下载源码 → Semgrep CE → 校验报告 → 上传 |
| RECOVER | 按步骤调用 UPX / FLOSS / Ghidra / IDA-D810 → 上传派生产物与 `RecoveryResult` |

**产物上传**：先上传字节获得 `artifact_id`，再把 id 写入结果结构。`ensure_output` 会在服务端核对该产物确实属于本次尝试。

### 12.3 恢复任务（`recovery.rs`）

按 `RecoveryPlan` 的步骤序列依次执行：每一步的输入只能是 `original` 或 `unpacked`（由上一步产物确定的路径），工具只能取自枚举。D-810 步骤携带 `profile ∈ {Instructions, ControlFlow}`。每步记录 `ToolExecution`（命令、版本、起止时间、退出码、日志产物）。

### 12.4 动态任务（`runtime.rs`）

```
1. 解析 payload 为 WindowsRuntimeConfig
2. 校验模式：仅 VERIFY 允许；FUZZ → 拒绝并回报明确错误
3. 准备临时目录与输入（哈希校验）
4. 在 Job Object 中按 baseline(1) + probe(repeats) 执行
5. 单次限时 timeout_seconds；支持取消
6. 收集 stdout/stderr/退出码 + 回收证明
7. 上传观察结果产物，CompleteWork(processes_reaped = 实际回收结果)
```

### 12.5 执行器安全边界（设计契约）

| 约束 | 实现 |
| --- | --- |
| 不持有模型密钥 | 执行器不接触 DeepSeek 凭据 |
| 不直连数据库 | 只能通过 RPC 领任务与回报 |
| 只执行声明式负载 | payload 是工具枚举 + 输入枚举，不是命令字符串 |
| 资源与回收 | Job Object + 单次限时 + 取消 + 临时目录 |
| 诚实回收 | 未确认终止不报 `processes_reaped = true` |

| D03 | 阻塞 stdin 不受声明的单次时限约束 | M7 超时 | 把 stdin 读取纳入统一超时与进程树终止 |
| D04 | 验证方案的参数类型与启动入口存在契约不一致 | M7 / 协议 | 统一 `RuntimeConfig` 与 `WindowsRuntimeConfig` 的字段语义 |
| D05 | `RuntimeResult.image_id` 语义重载（策略摘要 vs 镜像哈希） | M7 / 报告 | 拆分为显式命名的不相交字段 |
| D06 | FUZZ 路径定义完整但未接通 | M7 | 贯通 `FuzzOptions` → 执行器 → UI → 报告 |

**重要**：D01–D06 属于"机制已实现但行为不正确或不完整"，**不能通过调整文档措辞掩盖**；应作为测试返回项跟踪。
