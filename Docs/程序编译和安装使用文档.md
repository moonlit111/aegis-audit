# AegisAudit 程序编译和安装使用文档

本文档说明如何在本机把 AegisAudit 从源码编译起来、如何安装和运行便携包、如何配置模型连接、以及使用过程中需要注意的运行边界和排错方法。写作上以文字叙述为主，只在必须输入命令的地方保留命令片段。

当前产品支持 Windows 11 x64 平台。控制服务、前端界面、目标导入、静态分析、智能体恢复以及宿主机 VERIFY 都不需要 WSL、Docker 或沙箱环境。模型审计需要一份已经配置好的模型接口，可以是 DeepSeek 官方接口，也可以是任何兼容 OpenAI 协议的聊天接口；如果只做纯结构分析，也就是只看代码结构、不调用模型做语义审计，那么不需要配置模型。需要提醒的是，程序能启动、页面能打开，并不代表课程验收已经完成，验收状态请以课程进度文档为准。

---

## 一、文档说明

本文档面向两类使用者。第一类是开发者，希望从源码构建并调试；第二类是使用者，希望直接运行已经打包好的便携版。两条路径在第三章和第四章分别说明，第五章之后的内容对两者通用。

内容组织上，第二章讲环境与前置条件，第三章讲从源码编译与启动，第四章讲便携包的安装使用，第五章讲配置与使用，第六章讲宿主机运行边界，第七章讲排错与数据管理，最后一章是命令速查。如果你只想尽快把程序跑起来，可以直接看第四章的便携包部分；如果你想了解每一步在做什么，建议按顺序读。

需要先建立一个基本认识：AegisAudit 不是单个可执行文件，而是一个包含控制服务、执行器、前端页面和若干私有工具的组合。启动时实际上是拉起一个本地服务，然后通过浏览器访问，所有数据保存在本机的 SQLite 数据库和产物目录里。理解这一点对后面的目录结构和排错很有帮助。

## 二、环境与前置条件

从源码构建需要准备以下环境。操作系统是 Windows 11 x64。Python 需要 3.9 或更高版本，建议直接使用 `py -3` 启动器调用。需要 Git 用于拉取代码和导入源码目标。需要 Visual Studio 的 C++ 桌面开发工具以及 Windows SDK，因为 Rust 侧的原生依赖需要 MSVC 工具链来编译。所有这些都准备在 Developer PowerShell 里执行，普通 PowerShell 可能缺少编译所需的路径。

Rust 工具链的版本由仓库里的 `rust-toolchain.toml` 和 `Cargo.lock` 锁定，当前是 1.98.1。Node 与 pnpm 的版本由前端锁文件锁定，当前是 Node 24.20.0 与 pnpm 10.33.0。接口代码生成相关组件是 Connect Rust 0.9.0、Buffa 0.9.1、Buf 1.72.0。逆向相关的工具是 Java（Temurin）21.0.12.1+1 配合 Ghidra 12.1.3，私有 Windows Python 3.13.13 配合 Semgrep 1.176.1 Windows beta 版，以及 UPX 5.2.1、FLOSS 3.1.1、Zig 0.15.2。IDA、Hex-Rays 与 D-810-ng 属于本机商业软件，需要使用者自行提供，其中 D-810-ng 固定在提交 `2e59ab4ce18e5e82911880137d1285d95279981a`。

各工具的下载地址与摘要记录在 `tools/versions.json`、`tools/windows/versions.json` 和 `tools/reverse/versions.json` 里，语言依赖一律以锁文件为准。这些工具主要安装在仓库的 `.tools/` 目录下，Ghidra 的路径可以通过 `.tools/paths.json` 指向一个独立的 SDK 缓存位置。

关于引导脚本，`py -3 scripts/bootstrap.py` 默认会安装全部依赖，包括固定版本的 UPX 与 FLOSS。如果只做源码分析，可以用 `py -3 scripts/bootstrap.py --core-only` 跳过 Java 与 Ghidra，节省安装时间。项目提供的 `scripts/aegis.py` 是一个命令包装器，它会为子命令提供项目私有的 PATH、JAVA_HOME、代理设置以及已安装逆向工具的路径，不会修改全局的 shell 配置。这一点对干净环境很重要，它保证了项目的工具链不会污染系统环境。另外，Windows 下的 Git 会使用受校验的代理，同时禁用目标的 hooks、全局配置和凭据助手，避免导入不可信源码时执行意外代码。

关于路径的几点注意事项：Ghidra 可以处理中文路径和带空格的路径，但要避免 `%`、`!`、`&`、`|`、`<`、`>`、`^` 这类批处理特殊字符。项目目录不能包含以点号开头的路径段，因为那会与工具内部的路径处理冲突。执行器在分析时会自己在系统临时目录里创建 Ghidra 工程，所以不需要你手动准备工程目录。

## 三、从源码编译与启动

在 Developer PowerShell 中进入仓库根目录，依次执行以下四条命令。

```
py -3 scripts/bootstrap.py
py -3 scripts/manage.py build
py -3 scripts/manage.py doctor
py -3 scripts/manage.py start --open
```

第一条负责安装依赖，第二条编译，第三条做环境自检，第四条启动服务并自动打开浏览器。

编译默认产出 Release 版本。开发测试时可以用 `build --debug` 产出 Debug 版本，但要注意 `manage.py start` 会优先选择已经存在的 Release 程序，因此如果你刚改了源码、想验证新代码，不要因为看到旧程序在跑就误以为新代码生效了。需要停止和查看状态时使用 `py -3 scripts/manage.py status` 和 `py -3 scripts/manage.py stop`。

服务默认监听 `http://127.0.0.1:7331`。如果这个端口被占用，可以用 `start --port 7332` 换一个端口，但要注意换端口并不会自动隔离服务数据库，所以不要用这种方式同时启动两个写入同一个 `.data/server` 的实例，否则数据会互相干扰。需要做独立回归测试时，优先使用 `scripts/e2e.py` 这类自带临时服务和数据目录的脚本。另外，不要停止其他会话正在使用的服务。

如果需要做前端开发调试，可以单独启动 Vite 开发服务器。进入 `frontend` 目录后执行 `corepack pnpm install` 安装依赖，再执行 `corepack pnpm dev` 启动。默认地址是 `http://127.0.0.1:5173/`。Vite 会把 `/api` 和 `/rpc` 请求代理到 `http://127.0.0.1:7331`，所以即便只调试前端，也仍然需要先用 `manage.py start` 把控制服务和执行器启动起来；如果只启动 Vite 而没有启动后端，页面会提示无法建立本机会话。

## 四、便携包安装与使用

便携包的使用方式比源码构建简单得多。拿到完整解压的运行包之后，直接双击 `AegisAudit.exe` 即可。这个入口内部打包了启动运行时，并随目录一起提供了服务、执行器、前端以及指定的私有工具，它不是只复制一个 EXE 那么简单。因此普通使用者不需要安装 Rust、Node、Java、Git 或任何开发工具。

程序启动后会在系统托盘驻留，托盘菜单提供打开应用、模型配置、查看日志和退出这几个功能。需要特别注意的是，关闭浏览器标签页并不会停止正在运行的任务；只有从托盘退出，才会停止本次启动所拥有的服务和执行器。另外，不同目录被视为不同的安装实例，重复启动、端口冲突和进程恢复这些情况都由启动器自动处理，不需要手工干预。

便携包在命令行下也有几个有用的入口。执行 `.\AegisAudit.exe --stop` 可以停止服务，执行 `.\AegisAudit.exe --diagnostics .\doctor.json --non-interactive` 可以把环境诊断结果写入文件便于排查，执行 `.\AegisAudit.exe --configure-model` 可以直接打开模型配置。

如果你是打包者，构建与校验的入口命令是 `py -3 scripts/package.py --standalone-windows` 构建独立 Windows 包，`py -3 scripts/check_windows_package.py <本次ZIP路径> --output <不存在的验证目录>` 在独立目录里对本次 ZIP 做清单与重定位验证，`py -3 scripts/prepare_windows.py` 导出当前源码。最后这个命令会把当前源码导出，包含未忽略的未提交改动，同时排除本机数据和密钥；解压后、修改前可以用 `py -3 scripts/prepare_windows.py --verify` 检查清单是否完整。

有几点打包相关的纪律需要说明。运行包与源码包是分开管理的，新生成的 ZIP 必须使用它自己的哈希和验收结果，不能沿用旧包的验收成绩。当前发布物尚未签名，早期的本机重定位测试不能代表最新包或干净系统的验收结果。

## 五、配置与使用指南

### 5.1 模型连接配置

配置模型的方式是在网页的"执行环境"页面点击"配置模型连接"或"编辑模型连接"，然后填写接口类型、API 基础地址、模型标识和密钥，保存即可。保存这个动作本身不会调用模型；要真正验证连通性，需要点击"检测连接"，它会发起一次真实请求并记录服务商返回的用量。需要提前知道的是，安全审计过程中会把当前目标的代码片段和相关证据发送到你选定的模型服务，这是使用模型审计的前提。

如果使用 DeepSeek 官方接口，模式固定为直接连接 `https://api.deepseek.com`。如果使用自建服务或其他供应商，选择 OpenAI 兼容接口，地址填写到基础路径即可，例如 `https://example.com/v1`，程序会自动在其后追加 `/chat/completions`。远程地址必须使用 HTTPS，只有本机回环地址才允许使用 HTTP。地址中不能包含用户名、密码、查询参数或片段。

兼容模式在连接检测和实际审计中都会发送 `response_format: {"type":"json_object"}`，因此你所选用的接口和模型必须支持这个标准 JSON 输出参数。程序不会发送 DeepSeek 专用的思考参数，界面上的思考强度设置也不会被映射成其他供应商的专用参数。如果接口拒绝这些参数，程序会记录失败，不会静默降级，也不会额外发起没有计入预算的请求。

配置的存储方式是：网页配置以事务形式保存在 SQLite 里，密钥使用当前 Windows 用户的 DPAPI 加密，页面不会回显已经保存的密钥。有几点使用约束：存在正在进行的审计（包括排队中、等待执行器中、取消中）或连接检测期间，不能修改配置；更换接口地址或接口类型时，必须重新填写该接口的密钥，或者先移除已保存的密钥，避免把旧接口的凭据发送到新地址；如果其他窗口修改过配置，需要重新打开编辑器读取最新版本。

除网页配置外，也可以通过隐藏输入配置官方 DeepSeek 接口，命令是 `py -3 scripts/configure_model.py`。初始化之后，服务与命令行、便携版托盘使用同一份 SQLite 配置。首次启动之前，命令行仍然会写入兼容的 `model.json` 和加密的 `deepseek.token`；如果网页上没有配置，服务会读取这些文件。跨 Windows 账户或跨机器时无法解密，需要重新配置。有一点安全纪律必须遵守：不要把密钥放在命令行参数、源码、浏览器 localStorage 或日志里。执行器不接收模型密钥。

服务端还支持环境变量作为回退配置，优先级低于已保存的配置。`AEGIS_MODEL_ENDPOINT` 在本地未指定基础地址时使用，默认是官方 DeepSeek 地址。`AEGIS_MODEL` 在本地未指定模型时使用，默认是 `deepseek-v4-flash`。`AEGIS_MODEL_API_KEY` 在没有保存密钥时使用，它仅绑定 `AEGIS_MODEL_ENDPOINT` 指定的地址；如果未指定地址则绑定官方地址。`DEEPSEEK_API_KEY` 是官方 DeepSeek 模式下的最后密钥回退，不用于其他地址。网页会显示实际的凭据来源。移除已保存的密钥之后，匹配地址的环境变量仍然会生效，这个操作不会删除环境变量。修改服务进程的环境变量需要重启服务。最后要说明的是，连接检测只验证接入是否正常，不代表模型审计效果已经验收。

### 5.2 报告与导出

任务页面可以导出 JSON、HTML、Markdown 或 PDF 四种格式的报告。任务还在运行时也可以导出阶段报告。报告历史会记录数据截至时间、导出时的任务状态和报告类型；此后的复核或标注变更不会改写已经导出的文件，这一点对留档和取证很重要。

PDF 的生成方式是使用本机的 Edge 或 Chrome 做离线排版，可以通过环境变量 `AEGIS_PDF_BROWSER` 指定浏览器的可执行文件路径。程序会为每次排版建立独立的临时配置，不使用操作员自己的浏览器资料。如果机器上没有安装可用的浏览器，页面会给出明确错误，其余报告格式仍然可以正常使用。

### 5.3 逆向工具与动态验证

固定版本的 UPX 与 FLOSS 由引导脚本自动安装，不需要手工处理。IDA 与 Hex-Rays 属于本机商业软件，需要自行安装之后再进行探测，相关命令是 `py -3 scripts/install_reverse_tools.py`、`py -3 scripts/configure_d810.py --ida-dir '<IDA 安装目录>'`、`py -3 scripts/manage.py runtime` 以及 `py -3 scripts/manage.py doctor`。其中 `runtime` 负责准备 UPX 与 Zig，`doctor` 会输出各工具的真实探测结果。D-810 的依赖需要按照逆向交接文档单独安装。同样要强调，工具存在不等于正式闭源软件验收通过。

当前产品的 VERIFY 由 Windows 宿主机运行器执行，FUZZ 通道尚未接入产品。历史遗留的 Linux 容器方案以及 TinyInst、libFuzzer 的实验结果不能当作当前产品的能力，也不要为了跑旧回归而重新安装 Docker 或 WSL。

### 5.4 局域网演示

如果需要在局域网内做演示，需要先理解一个限制：控制服务只接受来自本机的操作员会话，在建立会话时会校验来源地址，Host 与 Origin 也只信任绑定地址，因此不能直接把 7331 端口暴露给局域网。

正确做法是在同一台机器上运行一个反向代理对外监听，然后转发回 `127.0.0.1:7331`。命令是 `node tools/windows/lan-proxy.js --port 8080 --password <口令>`，前提是先用 `py -3 scripts/manage.py start` 把应用启动起来。

代理的行为是这样的：启动后会打印可用的局域网地址，例如 `http://10.21.244.155:8080/`；浏览器首次访问时会弹出账号口令框，用户名随便填，口令就是启动时 `--password` 的值；转发时只改写 Host 与 Origin 为 `127.0.0.1`，流式事件、文件上传和产物下载都原样透传；如果不加口令，同网段任何人都能打开工作台，因此只限于受控网络短时使用；演示结束后结束该 node 进程即可，应用本身不受影响。

这里的安全边界需要明确：工作台没有多用户体系，能访问它就等于能以当前 Windows 账号导入并执行目标程序，因此演示结束请务必关闭代理。

## 六、宿主机运行边界

这一章要回答一个常见疑问：做这个课题是否必须使用沙箱。答案是当前产品采用宿主机执行，可以不依赖沙箱。课程并没有规定必须使用沙箱，产品已经采用了宿主机执行的方式。但采用宿主机执行并不意味着可以忽略风险，相反，需要把三种情况分清楚。

第一种情况是控制服务、前端、目标导入、Tree-sitter 分析、Ghidra、Semgrep、UPX 静态解包、模型审计与报告生成。这些工作已经直接运行在宿主机上，它们不会启动被分析的目标程序，因此不需要沙箱。

第二种情况是人工确认过的自写正常程序，或者可控的测试夹具。这类目标可以由宿主机的 VERIFY 运行器执行，但仍然需要固定输入、设置超时并进行进程回收。

第三种情况是不熟悉的旧闭源程序、模型生成的验证脚本、漏洞触发输入，以及安装器、服务、驱动这类目标。这些即使本身不是恶意软件，也可能误写文件、启动子进程、修改系统设置或耗尽资源。在本机执行之前，必须明确这些副作用以及相应的恢复办法。

需要特别指出的是，"不分析恶意软件"这个前提能缩小风险范围，但不能保证漏洞触发输入、构建脚本或生成的 PoC 没有副作用。工作目录限制和环境白名单也不能阻止以同一个用户身份读取其他文件；Job Object 提供的是资源限制，不是文件或网络隔离。

产品侧的实现方式是：服务端要求 `windows-host` 能力，执行器使用 Job Object、独立临时目录和环境白名单来执行目标，结果必须记录 `WINDOWS_HOST`，不能伪装成沙箱、容器或断网证明。本地后端应当使用普通权限运行，配备独立临时目录、固定的目标与输入哈希、环境白名单、Job Object 资源限制与超时取消，并记录正常输入与重复验证的结果。结果必须标明实际的本地执行环境，不能伪造沙箱会话或断网证明，也不应该因为省略了沙箱就默认以管理员身份运行。这些要求是运行正确性和可追溯性方面的要求，不是要求重新引入沙箱。

执行之前的检查清单是：确认目标架构、确认入口、确认输入、确认预期副作用，并且不要为了图省事而以管理员身份运行。

## 七、排错与数据管理

排错时首先要知道各类数据在哪里，以及哪些可以动、哪些不能动。

服务数据库和证据存放在 `.data/server/aegis.sqlite` 以及 `blobs/` 目录下。备份时要两者一起备份，并且先正常停止服务再备份，否则可能会漏掉 WAL 里的未落盘数据。

本机凭据存放在 `.data/server/*.token`。这些文件属于本机凭据，不提交、不展示、不打包分发。

执行器的活动任务与回收记录存放在 `.data/executor*/active.json`。遇到执行器停止领取任务这类现象时，正确的处理方式是先查看 `active.json` 和进程回收状态，不要直接删除记录来绕过恢复逻辑；必要时按最新基线复跑端到端测试。

应用日志与独立测试证据分别在 `.data/logs/` 和 `.data/verification/` 下，排查问题时优先看这两个目录。

几个常见情况的处理建议：`doctor` 退出码为 0 并不代表所有功能都可用，仍然需要逐项查看各工具的能力输出；执行器停止领取任务时，先查 `active.json` 和进程回收状态，不要删除记录绕过恢复；升级或分发时，退出后先备份数据，分发原始构建 ZIP，不要把已经使用过、带有凭据的目录重新压缩后分发出去。

另外还有几类"看起来失败其实不是"的情况需要知道。Windows 下文件的临时占用有时会导致状态写入失败，产品已经做了有限重试和原子替换，不会删除旧检查点。如果看到执行器因为文件访问冲突而退出，先确认进程和工具是否已经回收，再看是否需要重新领取任务。FLOSS 在极少数情况下会被启动探测判为不可用，原因是原版本探测的超时只有 5 秒且丢弃了失败原因；现在 FLOSS 的超时已经放宽到 30 秒，并且会记录超时、启动失败和退出失败的区别，界面上也会区分"未安装"和"已找到但探测失败"这两种状态。如果看到这类提示，不要直接判定 FLOSS 缺失。
