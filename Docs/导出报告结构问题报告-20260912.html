AegisAudit 导出报告的结构审查

对 crates/application/src/report.rs 及其上下游（PDF 打印、存储生命周期、proto 契约、前端导出）的结构性审查，共 25 项问题，其中 3 项严重。

审查对象
JSON / Markdown / HTML / PDF 四种导出格式
审查方式
7 维度并行阅读 + 对抗性复核 + 真实产物实证
原始结论
40 条，17 条被复核推翻或降级
证据基线
代码逐行核对；PDF 实测用 Edge 152 / Chrome

结论：当前报告结构不成立。问题不在渲染细节，而在三处根本错位——报告把内部实现当成交付内容（JSON 直嵌领域模型，连模型的 provider 请求 ID 和原始输出一起交付）；四种格式不是同一份文档（Markdown 缺严重度依据，HTML 的发现章节挂错标题）；以及交付物缺了它自己承诺的章节（无执行摘要、无风险汇总、"覆盖缺口"退化成原始 JSON 转储）。

项目自己的设计契约在 Docs/详细设计报告.md:995-1005 声明了七章结构与"严重等级及理由"的字段要求，实现与之偏离——这不是没有标准，是没有对齐标准。

结构问题之外，本次审查推翻了 17 条看起来合理的初始结论（见第五节）。其中几条出自我此前的口头汇报，一并更正。

02交付物结构：缺了它自己承诺的章节

设计契约要求七章：概览 / 漏洞清单 / 证据链 / 修复建议 / 人工修订 / 覆盖缺口 / 运行范围。实际输出是九节，名称与边界都对不上。

P-01

没有执行摘要：REPORTER 的结论、建议与局限被埋在 JSON 转储里

审计链最后一环 REPORTER 的输出被写进 run.summary["audit_narrative"]，而三个渲染分支没有任何一行读它。它唯一的可见位置是"覆盖与错误"章节里的原始 JSON 代码块——一个语义完全错误的章节名下。

audits.rs:518-519 run.summary["audit_narrative"] = result.clone(); grep -rn audit_narrative → 仅命中上面这一行 report.rs 内 0 命中

影响交付物缺少执行摘要这一必备章节。客户必须先读懂一张单元表、再解析 JSON，才知道这次审计得出了什么。REPORTER 提示词里为保证读者向表述而做的约束（不把候选当结论、不把组件验证当已利用）在报告中失去落点。

建议在 H1 之后插入固定章节 ## 执行摘要，取 audit_narrative 的三段：summary → 段落，recommendations → 有序列表，limitations → 无序列表；并从 run.summary 转储中移除该键，避免同一段文字出现两次。

P-02

第一屏是程序单元表，没有摘要、目录或结论区

HTML/Markdown 拼出 h1、四行松散元数据后直接进入表体，行数没有上限、没有计数、没有截断。

report.rs:291-298 h1 + 元数据 + <table> 一次拼出 report.rs:299-308 for unit in units { … } ← 无行数上限 store.rs:1343-1348 SELECT data FROM program_units WHERE run_id=? ← 无 LIMIT 实测（本机 Edge 152 / Chrome 以同一套 REPORT_STYLE 打印）： 4000 个单元 → 400 页 再加 600 行原始观察 JSON → 412 页

影响一个真实 run（数千单元）导出的 PDF 里，发现章节的物理页码可以超过 400。读者与评审无法快速判断严重度分布与复核完成度。

建议在单元表之前插入执行摘要与风险汇总；单元表加标题与计数、超过 200 行截断并注明"其余 N 个见 JSON 报告"；空集合时不输出空表。

P-03

没有风险评级汇总；发现既不按严重度排序、也不带条目 ID

报告按数据库原始顺序输出发现，全文没有任何"共 N 个 CRITICAL / M 个 HIGH"的统计。严重度只是一个印在标题行里的词。

audits.rs:193 SELECT data FROM findings WHERE run_id=? ORDER BY created_at,id report.rs:197-199 字段序列：标题 / cwe / 严重度 / 复核 / 验证 / … ← 无 finding.id，无 fingerprint

影响客户无法一眼判断风险面（有没有 CRITICAL、几条已被反证）；条目没有稳定 ID，整改跟踪、与界面 ListFindings 对账、同一目标前后两次报告的差异比对都无法做。

建议新增 ## 风险汇总 表（严重度 × 候选数 / VALIDATED / REJECTED / INCONCLUSIVE / 未复核）；按 CRITICAL→UNKNOWN 稳定排序；每条标题改为 ### F-<id 前 8 位> · <severity> · <title>。

P-04

"覆盖缺口"退化成 run.summary 的全量 JSON 转储

契约要求这一章写"未解析文件、部分解析单元、被排除项、未覆盖范围"。实现是整份 run.summary 原样打印——含 exploitation、recovery、审计预算等与覆盖无关的字段。

report.rs:399-403 <h2>覆盖与错误</h2><pre>{run.summary 全量 JSON}</pre><p>{run.error}</p> 契约 Docs/详细设计报告.md:1004 | 覆盖缺口 | 未解析文件、部分解析单元、被排除项、未覆盖范围 | 实测：600 行原始 JSON 单独占 12 页 PDF

影响覆盖缺口是"这份审计没看到什么"的举证，现在被埋在一个未分节、未解释的机器 JSON 里，评审无法据此判断审计范围是否足够。

建议拆成三节固定字段：## 覆盖范围 / ## 未覆盖范围与局限性（逐条列 FAILED 任务与 run.error）/ ## 运行范围（补 adapter、observer、repeats、timeout、回收记录）。人类可读格式一律不再出现 run.summary 原始 JSON。

P-05

HTML 的安全发现章节，在文档结构上落进了"逆向与解混淆"

发现章节的 <h2> 是无条件输出的，紧接着就是 recovery 的 <h2> 加一段与安全发现无关的导语；而 findings 循环只输出 <section><h3>，annotations 连标题都没有。

report.rs:326 body.push_str("<h2>发现、复核与关键逻辑</h2>"); ← 无条件 report.rs:327-328 if run.summary["recovery"].is_object() { "<h2>逆向与解混淆</h2><p>以下记录包含智能体计划、 实际工具状态、输入输出哈希与产物引用。</p>…" report.rs:331 "<section><h3>{title}</h3>…" ← 只有 h3 report.rs:360-368 注解只输出 <p>，无标题

影响PDF/HTML 里最重的"发现"章节没有自己的章节标题，在 PDF 书签与大纲里看不到它，视觉上被读成反向工程记录的附属内容。同一报告导出成 Markdown 又是另一套层级，团队无法用章节路径稳定引用。

建议固定唯一章节序列由两个分支共用；把无条件 h2 改为"findings 或 annotations 非空时才输出"；HTML 补出独立的"关键逻辑与人工修订"标题，与 Markdown 的 report.rs:225 同名同序。

P-06

章节顺序把过程记录排在结果之前

实际顺序是：程序单元表 → 审计策略与优先级 → 逆向与解混淆 → 发现与复核 → …。读者要先读完一整张单元表和一段规划文本，才看到第一条发现。

建议改为结果在前、过程在后、原始数据入附录：结论摘要 → 发现与复核 → 关键逻辑与人工修订 → 修复建议 → 覆盖与缺口 → 运行验证 → 自动利用证据 → 逆向与解混淆 → 审计策略 → 程序单元 → 证据产物 → 附录。

03四种格式不是同一份文档

Markdown 与 HTML 是两份逐段手写、各自演化的渲染代码（report.rs:150-288 与 289-413）。字段集合与章节树已经漂移。

P-07

Markdown 缺"严重度依据"，违反契约的"严重等级及理由"

report.rs:335（HTML） …<p>严重度依据：{}</p>… escape(&finding.draft.severity_reason) report.rs:197-199（Markdown）字段序列为 标题 / cwe / severity / review_status / verification_status / input_source / sink / missing_guard / preconditions / impact / recommendation ← 无 severity_reason 契约 Docs/详细设计报告.md:1000 | 漏洞清单 | 标题、类型、CWE、严重等级**及理由**、主位置 |

影响人工审阅 Markdown 报告时看不到定级依据，无法判断 CRITICAL/HIGH 是否被论证过。验收记录里 Markdown 常是唯一被转成 docx 分发、或唯一归档的阅读件——分发出的交付物缺字段。

建议两分支共用一张字段表 fn finding_fields(&FindingDraft) -> [(&'static str, &str); N]，各自只负责转义与包装，不允许再手写字段清单。注：两种格式都还漏了 category。

P-08

Markdown 把换行折叠成空格，多行字段与代码引文不可读

md() 在转义后执行 .replace(['\n','\r'], " ")，所有经它的字段都被压成单行——包括引文。而引文是多行代码片段，domain 层专门注释要求保留原始缩进。

report.rs:440 for character in escape(text).replace(['\n', '\r'], " ").chars() { crates/domain/src/audit.rs:124 // Preserve the original indentation and complete cited lines in the canonical evidence. report.rs:422,425（HTML 侧不受影响） p,li{…white-space:pre-wrap} pre{white-space:pre-wrap;…}

影响模型产出的多行 impact / preconditions / recommendation（每条上限 8192 字节）变成没有换行的长文；源码证据引用（最多 100 行）丢失全部分行与缩进语义。同一 run 导出 HTML 与 Markdown，可读性差一个数量级，而 UI 把两者并列成等价选项。

建议拆成 md_inline()（表格单元格用，换行转 <br>）与 md_block()（正文用，逐行转义但保留 \n）；引文改为独立代码块，围栏长度按内容里最长反引号串动态选取。

P-09

同一个 run.state 在一份报告里有两种拼写

report.rs:294 / 155 "状态：{:?}" → Running / WaitingExecutor / Partial report.rs:129 / 118 run.state.as_str() → RUNNING / WAITING_EXECUTOR / PARTIAL

影响同一页上"状态：WaitingExecutor"和"导出时任务状态 WAITING_EXECUTOR"并存。验收里"JSON 的状态与 RPC 核对一致"只覆盖 JSON；HTML/Markdown 的状态无法与数据库对账，第三方解析报告的读者也无法匹配文档化的 SCREAMING_SNAKE_CASE 状态集。

建议统一为 run.state.as_str()；HTML 侧补 data-run-state / data-interim 机器可读属性。

P-10

同一条利用证据，两种格式给出强度不同的结论

report.rs:268-270（Markdown） 证明记录的输入可在授权目标上稳定复现观察到的结果 report.rs:394-395（HTML） 该证据证明最小输入可稳定触发观察到的内存安全异常

影响对 INJECTION / PATH_TRAVERSAL / AUTHORIZATION 类发现，HTML 的"内存安全异常"是超出证据的断言。同一审计的两份交付物口径不一致，在评审与举证场景会被质疑。

建议两种格式共用一句与类别无关的措辞。

P-11

复核的攻击条件判定与复核证据，两种格式都不打印

模型复核被强制分别给出 INPUT_CONTROL / REACHABILITY / DEFENSE_GAP 三项，且 VERDICT=VALIDATED 要求三项全部 SUPPORTED——这是定级门槛。报告只打印 verdict 与 rationale，从不打印 assessments；也不打印复核引用的原始代码。

crates/domain/src/audit.rs:244-283 if self.assessments.len() < 3 || self.assessments.len() > 12 { … } if self.verdict == "VALIDATED" && self.assessments.iter().any(|a| a.status != "SUPPORTED") { … } report.rs:217-219 只打印 revision / actor / verdict / rationale / counter_evidence / missing_information

影响读者看不到判定 VALIDATED 的各攻击条件是否被原始代码支持、反证引用了哪段代码。仅凭报告无法复核一条发现。

04JSON 格式是内部实现的 dump

ReportDocument 直接引用六个领域结构，于是 JSON 报告的内容契约等于内部实现。

P-12

交付物里带着模型的 provider 请求 ID、提示词版本与原始输出

report.rs:19 / 146 pub audit: &'a AuditEvidence, → serde_json::to_vec_pretty(&document)? crates/domain/src/audit.rs:370-379 pub struct AuditEvidence { pub findings, pub reviews, pub annotations, pub model_calls: Vec<ModelCall>, ← provider_request_id / prompt_version / pub tasks: Vec<AgentTask>, latency_ms / token 用量 pub runtime, ← 每个 agent 任务的原始模型 JSON 输出 } 实测样本 .data/verification/agent-recovery/native-report.json audit.model_calls[0].provider_request_id = "e17013c5-dfd3-4f7d-8dd3-66611f10717f" audit.model_calls[0].prompt_version = "audit-12-human-references"

影响一份本应只含审计结论与证据的交付物，暴露了内部调用编排、提示词版本、模型服务请求 ID 与未标注的原始模型文本。HTML/Markdown 把 recovery 与 observation 包进代码块并说明来源，JSON 分支没有等价的可信度标记——消费方无法区分"目标证据"与"模型自述"。

建议把 ReportDocument 从"引用领域模型"改为显式白名单投影：删掉 audit 字段，替换为 ReportFinding / ReportReview / ReportTask{role, status, …}（去掉 result 与 id）等；所有保留模型产出的字段统一附 "trust": "UNTRUSTED_MODEL_OUTPUT"。

P-13

coverage 是 run.summary 的克隆，同一文档里重复了两次

run 自己带着 summary，而 coverage 又是它的 clone()。字段名叫 coverage，装的却是任务状态、模型用量、工具观察与审计叙事。

report.rs:133 / 135 run, … coverage: run.summary.clone(), 实测：两份各 12,819 字节，占该报告 76,374 字节约 33% 其中 coverage.recovery 单项 10,993 字节

影响按字段名取"覆盖率"会拿到一个含 25 个异构键的对象；同一事实两个可独立更新的真相来源，体积平白膨胀三分之一。

建议删除 coverage，改为受控的 ReportCoverage 结构体；run.summary 其余部分拆成各自命名的顶层节，并让 run 不再携带 summary，使其在整份文档中只出现一次。

P-14

checks 与 coverage 对同一组状态各写一份，且可以互相矛盾

checks 的五个状态里有三个是渲染期实时派生的；coverage 里的同名状态是 run.summary 的原始值，而写入端只把 exploitation 回写进 source run。

report.rs:88-89 fuzzing_status / runtime_status ← 由 audit.runtime 记录派生 report.rs:135 coverage ← run.summary 原始值 crates/server/src/runtime.rs:742 source.summary["exploitation"] = json!(exploitation_status); ← source run 唯一被回写的状态 结果：同一份 JSON 里 checks.runtime_verification = COMPLETED 而 coverage.verification 仍是 NOT_RUN

影响"是否做过动态验证/模糊测试"这个关键结论在文档里有两个可能互相矛盾的值；报告正文的提示语用的是派生那一份，JSON 读者若取 coverage 会拿到未初始化的占位值。

P-15

单元对象：code 恒为空串，metadata 却是全量内部反编译数据

store.rs:1352 unit.unit.code.clear(); ← 只清值，字段还在 store.rs:1256 unit.unit.metadata = json!({"kind": …}); ← 列表接口会裁剪，报道路径没有 实测样本（我核对过）units[0] 是扁平结构，无 unit 包装： code = '' metadata = {address_space, analysis_engine, analysis_input_artifact_id, analysis_input_sha256, basic_blocks, blocks_truncated, decompile_error, image_base, original_instruction_mapping, pcode, pcode_truncated, pseudocode_mapping, rva, signature}

影响一个名叫 code 却永不含代码的字段；同时 basic_blocks、pcode 等引擎内部溯源随单元数线性膨胀。三处读路径（报告 / 单元列表 / 调用图）的裁剪口径互不相同。

建议与 store.rs:1256 对齐裁剪 metadata；改用显式投影 ReportUnit，用 code_sha256 + code_bytes 取代空 code 字段，保留可校验性。

P-16

schema_version 恒为 1，且全仓无人校验

report.rs:126 schema_version: 1, grep -rn schema_version → 无任何针对 ReportDocument 的读取点 既有脚本只按 checks 的键名取值： check_auto_exploit.py:204 / analyze_candidates.py:33 / audit_candidates.py:137

影响版本字段是装饰品——写死、无消费方、无迁移路径。而既有脚本直接按键名取值，任何结构变更都会静默打断验收脚本。顶层另外还缺 report_id、生成器版本、统计汇总、plan。

05生命周期与对外契约

P-17

历史报告文件被当成审计证据，导致报告不可复现

产物查询把本 run 的历史报告也纳入"证据产物"，而取产物发生在本次报告落盘之前——于是第 N 份报告必然列出前 N-1 份报告文件。

store.rs:1297 run_artifacts 查询含 OR a.id IN (SELECT artifact_id FROM report_exports WHERE run_id=?) store.rs:1355 let artifacts = self.run_artifacts(run_id).await?; ← 先取 store.rs:1389-1392 stage_bytes(…); insert_artifact(…); ← 后落盘 store.rs:1390 文件名恒为 aegis-report-{run_id}.{extension}

影响同一快照点、同一格式导出两次会得到不同字节与不同 sha256，因此无法用哈希证明报告未被改写、无法做两版 diff；审计读者会把 aegis-report-xxx.html 误当成审计证据；同 run 所有报告同名，正文列表里出现多行同名条目。

建议查询里排除报告产物；报告自身产物移入独立的"报告导出历史"章节；命名改为带时点与报告 ID。

P-18

失败的导出不留痕；没有删除/重新生成；分页会漂移；孤儿 blob 不回收

PDF 渲染失败直接 store.rs:1373-1381 以 ? 返回 → 无 requests 行、无 report 行、无 run_event pdf.rs:36-38 浏览器缺失时 context(…) 直接失败 proto:247-251 ReportService 只有 CreateReport / GetReport / ListReports store.rs:1314 ORDER BY created_at DESC,id DESC LIMIT ? OFFSET ? ← 只增列表上的 offset 分页 store.rs:248-254 stage_bytes 先写 blob，insert 失败则留下无引用文件，全仓无清理路径

影响历史页无法区分"从未导出过 PDF"和"试过但失败"；翻页期间新导出会造成重复/漏项；磁盘占用只增不减。

建议失败导出写一条 run_event；增加 DeleteReport / RegenerateReport；分页改 keyset（用最后一条的 created_at+id 作游标）；补孤儿 blob 回收入口。

P-19

报告条目本身拿不到内容指纹，历史页在下载前无法展示或校验

proto/audit/v1/audit.proto:124-133 message Report { id, run_id, format, artifact_id, created_at, snapshot_state, interim, snapshot_at } ← 8 个字段，无哈希/大小 report.rs:126 ReportDocument.schema_version 只存在于下载文件内部，Report 消息读不到

注下载响应头已经带了 x-aegis-sha256（web.rs:441-444），执行器客户端也已在用它校验（crates/executor/src/client.rs:73-78）——所以"无法校验"不成立。真正缺的是协议层：历史页在用户点击下载之前，拿不到大小、指纹或 schema 版本，也无法判断文件是否仍存在。

建议Report 消息补 sha256 / size_bytes / media_type / document_schema_version；历史页显示指纹前缀与大小。

P-20

报告自身没有身份与版本标识，PDF 的 /Title 恒定

report.rs:291 <title>AegisAudit 分析报告</title> ← 常量，Chromium 写入 PDF /Title report.rs:427 @page{ … @bottom-right{content:counter(page) " / " counter(pages) …} } pdf.rs:57 --no-pdf-header-footer ← 主动关掉浏览器页眉页脚 实测（Edge 152.0.4191.66）：每页内容流末尾的文本 run 编码为 "1 / 4"…"4 / 4"， 绘制色 #64748b 与 @page 的 color 一致；去掉 margin box 后该 run 消失 （33,716 → 32,181 字节）——页码确实生效

影响页脚只有页码，不含 run/项目/报告版本。同一 run 每次导出、不同 run 的导出，PDF 文档标题完全相同；正文里的任务 ID 只出现一次，单独传阅某一页无法溯源。人类可读格式也都不输出 schema_version。

局限页码依赖 Chromium 的 CSS Paged Media margin box 支持，而没有任何测试覆盖这个依赖——pdf.rs:98 的测试 HTML 既没有 @page 也没有 counter()。运行环境不支持时，交付物会静默变成几百页无页码的 PDF。

06版式、可打印性与前端

P-21

打印版式把页数放大一倍以上

report.rs:422-423 table{width:100%;border-collapse:collapse;table-layout:fixed} th,td{…overflow-wrap:anywhere} ← 4 列在 A4 上均分 172px，路径逐字符断行 实测同一张 4000 行单元表： table-layout:fixed（现网样式） = 400 页 / 6.35 MB 仅改为 auto = 182 页 / 6.01 MB （10 行/页 → 22 行/页） report.rs:331-334 "<p>静态结论范围：…</p>" 在 <section> 之外 → PDF 里视觉上归属上一条 findings report.rs:425 pre 无 break-inside 控制、无高度上限 → 跨页断裂

影响页数被版式放大一倍以上，直接加剧 P-02 的"发现被埋"；"静态结论范围"作为每条结论的适用范围声明归属错误，在安全报告里属于举证归属错误。

P-22

下载文件名与确认弹窗承诺的名字不是一回事

前端把显示名写在 link.textContent 上，下载交给 link.download = ''——按规范文件名取响应头的 Content-Disposition，即服务端的 artifact 名。前端从不把这个名字传给服务端（CreateReportRequest 只有 request_id / run_id / format）。

ReportExport.svelte:48-51 link.href = artifactUrl(report.artifactId); link.download = ''; ← 空值 = 用服务端文件名 link.textContent = `${snapshotName} · ${reportName(report)}`; ← 只用于弹窗显示 store.rs:1390 stage_bytes(&bytes, &format!("aegis-report-{run_id}.{extension}"), mime) web.rs:432-436 Content-Disposition: attachment; filename*=UTF-8''{artifact.name}

影响客户拿到的是 aegis-report-0f3a9c21.html——没有项目名、没有格式、没有导出时间。同一 run 导出"阶段报告"和"结果快照"两份 HTML，落盘文件名完全相同，浏览器只能加 " (1)"。而弹窗里展示的是一个文件系统里根本不存在的名字，用户按它去找文件必定找不到。

建议让一个名字贯穿到底：CreateReportRequest 增加 file_stem，前端构造 {快照名}-{格式}-{时间戳}，Report 回传 file_name，弹窗与下载共用它。

07加固建议（当前不可达）

以下三条经复核确认当前无法触发，作为纵深防御与编码卫生保留。复核推翻了它们最初的"安全缺陷"定性。

P-23

两处未走 escape() 的插值

report.rs:294 "状态：{:?}" → run.state（未 escape） report.rs:384 "范围：{}" → record.config.target_scope()（未 escape）

复核结论不是"安全靠数据类型巧合"——是类型级保证。RunState 是 Copy 枚举，九个变体都不携带数据（crates/domain/src/lib.rs:59-71），{:?} 不可能输出 <meta。target_scope() 是 &'static str。分支内其余动态插值全部走了 escape()。

建议仍值得统一为 escape(run.state.as_str())，理由是消除未来变体加数据时的静默回归；并加一条渲染出口断言，拦住 <script / <a / <form 等渲染器自己从不生成的标签。

P-24

PDF 打印进程没有出站阻断

报告 HTML 的 CSP 不含 form-action（meta 也投递不了 navigate-to），而 PDF 是把这份 HTML 交给本机 headless 浏览器以 file:// 渲染，参数里没有任何阻断出站的开关。

report.rs:291 default-src 'none'; style-src 'unsafe-inline'; base-uri 'none' pdf.rs:48-62 参数里没有 --host-resolver-rules / --proxy-server （也没有 --disable-web-security 等危险开关 —— 这点是好的）

复核结论影响链的前提取自一个不存在的注入路径（见 P-23）。而且分析员用本机浏览器打开 HTML 这一最易触达的场景，在 HTTP 层已被兜住：下载路由同时投递 Content-Disposition: attachment、nosniff 与 Content-Security-Policy: sandbox（web.rs:432-448），无 allow-* token 的 sandbox 会把文档丢进不透明源并禁用脚本。

建议仅保留这一条低成本加固：pdf.rs 参数补 --host-resolver-rules=MAP * ~NOTFOUND（报告是纯本地自包含 HTML，不引用外部资源，阻断域名解析不影响排版）。

警告复核同时指出，最初提出的 ensure!(!html.contains("<meta")) 断言会让每一次 PDF 导出失败——report.rs:291 生成的报告恒定含两个 meta。不要照做。

P-25

产物下载的 media_type 没有白名单

web.rs:320-325 上传端透传 media_type（仅校验长度 ≤100 与 header 合法性） web.rs:416-420 下载端用它落 CONTENT_TYPE report.rs:413 报告 HTML 也以 text/html; charset=utf-8 走同一条路由

复核结论不可触发。防护不止 attachment 一层——nosniff 与 CSP: sandbox 在同一 handler 里无条件设置。且 media_type 并非攻击者可控：所有执行器上传都是字面常量（recovery.rs:107、jobs.rs:206/510 等），唯一由调用方决定的取值是操作者从本机磁盘自选文件时浏览器给出的类型，而 /api/uploads 需通过 localhost 与 Origin 同源校验加 operator 会话。

建议作为编码卫生保留：给上传的 media_type 加白名单（拒绝 text/html、image/svg+xml），并把报告产物拆到独立路由 /api/reports/{id}/content，让"报告"与"任意上传产物"不再共用一条下载路径。

08复核推翻的结论

以下条目在初读时都完全成立，复核用代码逐条证伪。列出来是为了避免有人照着错的方向去改——其中若干条出自我此前的口头汇报。

幂等键不含快照点，会把旧时点报告当新导出交付推翻 3 次。重试复用同一 requestId 是本仓库显式规定并被测试锁死的契约（run-actions.spec.ts:329：reuse the request after a lost response）；且快照时点在四处可见，"用户无从察觉"为假。
组件卸载 abort 后服务端仍会落盘，造成看不见的重复报告因果链写反了。axum/hyper 在客户端断开时 drop handler future，abort 恰好落在"报告还没写库"的窗口里——这正是本仓库对长任务一律显式 spawn 的原因（model.rs:107、agents.rs:125）。
下载路由不校验，协议不提供内容指纹x-aegis-sha256 响应头已经存在（web.rs:441-444），且已有的一等消费者就在用它：crates/executor/src/client.rs:73-78。
报告正文与文件名都不携带导出时间前半句错误。report.rs:110-123 的提示语就是"… · 数据截至 {} · …"，且写进了 Markdown（:157）与 HTML（:297）正文。
md() 是比 escape() 更窄的转义器方向说反了。md() 的第一步就是 escape(text)，它是 超集。换行折叠的问题成立，覆盖面的问题不成立。我先前也复述错了这一条。
两处裸插值让安全依赖"数据类型巧合"是类型级保证，不是巧合。RunState 是 Copy 枚举、九个变体均不携带数据；当前不存在任何注入路径。
CSP 不覆盖导航，PDF 浏览器无出站阻断＝可 SSRF前提是一个不存在的注入路径；且浏览器场景已被 HTTP 层的 CSP: sandbox 兜住。附带的那条修复（拒收含 <meta 的 HTML）会让每次 PDF 导出失败。
产物下载的防线只剩硬编码的 attachment同一 handler 无条件还设了 nosniff 与 CSP: sandbox；media_type 也非攻击者可控（执行器上传全是字面常量）。我先前称其为"残余风险"，也说重了。
PDF 导出必然撞上 15s deadline，且后端仍会排版并落盘pdf.rs:65 的 45s 是杀进程上限而非耗时估计，--virtual-time-budget=1000 是刻意求快，try_acquire() 拿不到槽位是立即失败而非排队。更关键的是 rpc.rs:531-545 是内联 await、没有 spawn——断开即取消，进程树被内核终止、临时目录一并删除，既无报告行也无产物。按原建议把文案改成"服务端可能已生成报告"，会把用户引向一份不存在的报告。
报告 JSON 里 units[].unit.code 为空、units[].unit.metadata 全量JSON 路径错误。ProgramUnit 用了 #[serde(flatten)]，序列化后字段摊平到顶层，不存在 unit 包装——实际是 units[].code / units[].metadata（我实测样本确认）。metadata 泄漏与空 code 的实质成立，见 P-15。
plan 解析失败会让"审计策略"整章静默消失不可达。finish_agent_task 首句即校验结果，PLANNER 分支用同一个 Plan 反序列化、失败不落库；Plan.approach 必填且写入时强制非空。

09方法与局限

  • 已实证：PDF 的页数、页脚页码与 /Title 是用本机 Edge 152.0.4191.66 与 Chrome、以与 pdf.rs 一致的参数真打印并解析内容流得到的；JSON 结构用 .data/verification/agent-recovery/native-report.json 实测核对。
  • 未实证：报告正文的四种格式没有跑完整的端到端导出比对，"章节集合不一致"等结论由逐行读代码得出。验证方式是写一个覆盖全部字段分支的渲染对照测试，断言四种格式出现的字段名集合相同。
  • 审查范围：7 个维度（JSON 契约、Markdown 渲染、HTML/PDF 渲染、生命周期与存储、前端 UX、交付物完整性、不可信内容注入）共 40 条原始结论；对抗性复核对其中大部分做了 2–3 个独立视角的证伪尝试，17 条被推翻或降级。
  • 已知盲区：报告的可复现性（同一 run 两次导出的字节是否一致）、超大 run 的渲染性能、报告与下游工单系统（Jira / DefectDojo / SARIF）的互操作、报告的访问控制（谁能下载别人的报告）——这些问题没有独立的维度覆盖。
  • 一件事：如果只做一项改动，先给报告加执行摘要与风险汇总（P-01 / P-02 / P-03）。它不需要改数据模型、不影响任何既有测试，却直接把"这份报告能不能被读懂"从否变成是。JSON 的契约改造（P-12）优先级同样高，但它要动 proto 与前端，适合排在第二位。
证据引用格式为 文件:行号，全部指向审查时的 fix/snapshot-audit-workflow 分支工作区。复核意见以对抗性证伪为目标，倾向推翻而非确认——被推翻的结论列在第八节，不代表它们指向的代码位置不存在，只代表原始定性不成立。
