# AegisAudit 测试分析报告

本文档是 AegisAudit 0.2.0 的测试分析报告，用于课程"设计实现类"第 1 题的交付。写作目标是尽量把测试内容讲清楚，因此全篇以文字叙述为主，只在必要处保留命令片段，不使用装饰性排版。

## 一、报告说明

### 1.1 测试范围与口径

本报告覆盖 AegisAudit 在 2026 年 9 月 10 日至 9 月 11 日之间完成的三类测试：对四个自研闭源受控对象的完整测试、对项目自身工程质量的自动化测试，以及在真实开源代码上进行的对照池评测。

在展开之前必须先讲清楚三条口径，否则后面的数字会被误读。

第一条口径是"测试对象"与"验收对象"的区别。本报告第三章的四个受控对象（ParcelDrop、RowVault、PermitLedger、TextRelay）是我们自己编写、自己编译、自己设定缺陷的样例，它们的作用是证明系统的挖掘、验证和利用闭环确实能跑通，而不是证明系统能在真实世界的软件上发现问题。课程要求的六项正式软件（两种开源大模型软件、两种加壳闭源软件、两种混淆闭源软件）已全部通过验收（6/6），其中两款开源大模型软件的证据见第四章。本报告第三章的四个受控对象仍不占正式名额，只用于证明挖掘、验证与利用闭环确实能跑通。

第二条口径是"任务状态"与"漏洞结论"的区别。系统在运行审计任务时会记录一个任务级状态，取值为 COMPLETED、PARTIAL 或 CANCELLED。这个状态只表示任务本身跑完了还是被中断了，它不表示目标软件安全或不安全。真正代表漏洞结论的是每一条发现的复核状态，取值为 VALIDATED（复核成立）、INCONCLUSIVE（证据不足，不能定性）或 REJECTED（复核驳回）。一个 PARTIAL 的任务完全可能包含 VALIDATED 的发现，一个 COMPLETED 的任务也完全可能一条漏洞都没找到。展示或引用结果时必须分清这两层。

第三条口径是"未命中"与"安全"的区别。审计覆盖率是有限度的，一条路径没被审计到、一个单元没有被成功分析，都不能推出"这里没有漏洞"。本报告中凡是"零命中"的结论，都同时标注了覆盖率，例如"修复版 0 条命中，覆盖 1/91"。这种写法是为了明确证据强度：覆盖率越低，"未发现"就越不能等同于"不存在"。

### 1.2 材料分类与来源

本报告的数据来自项目内的几个固定位置。对照池评测的完整材料在 `evaluation/materials-20260911/` 下，其中 `00-工作汇总与展示清单.md` 是总入口，`01-源码对照/` 存放每一对的有洞版源码、修复版源码和标准答案 diff，`02-运行结果报告/` 按批次存放报告与原始审计 JSON，`03-其他验证/` 存放离线复判记录与构建启动证据，`04-利用验证/` 存放三个可复现的利用验证案例。对照池与漏洞的汇总口径在 `evaluation/reference/` 下的 `pair-pool-results.md` 与 `vulnerability-inventory.md`。四个受控对象的定义在 `evaluation/targets/protected-tools.json`。工程测试的结论与历史证据在 `Docs/测试与验收方案.md`。

需要说明的是，本报告引用的每一个结论都能回溯到原始产物。每个批次目录下都保留了原始审计 JSON（`*-audit.json`）、人读报告（`*-report.md` 与 `*.html`）以及判定与用量摘要（`summary.json`）。如果对某条结论有疑问，可以拿原始 JSON 重新核对，也可以不连服务、不花模型费用地做离线复判。

## 二、被测系统概述

### 2.1 系统定位与功能

AegisAudit 0.2.0 是一个基于大模型多智能体的软件漏洞挖掘与验证工作台。它要解决的问题是：面对一个只有二进制或只有源码片段、没有漏洞说明的目标，系统能不能自己规划分析路径、自己调用逆向和静态分析工具、自己从代码里提出漏洞假设、自己独立复核这些假设，最后自己设计验证方案并执行、归档证据。

系统的技术栈是 Rust 加 Axum 与 Tokio 承载控制服务，Svelte 5 加 TypeScript 承载前端界面，前后端之间用 Connect RPC 通信，持久化用 SQLite（通过 SQLx），接口定义用 Buf 与 Buffa 做代码生成，源码侧的语法分析用 Tree-sitter。整个调用链是：浏览器界面发起请求，经 Connect RPC over HTTP 进入 Rust 控制服务，控制服务读写 SQLite 与产物存储、并向执行器队列派发任务，执行器负责真正运行 Tree-sitter、Ghidra、Semgrep 和宿主机验证工具，而多智能体审计本身由控制服务调用大模型完成。

### 2.2 多智能体角色分工

系统的审计流程由六个角色协作完成，每个角色承担不同的职责，彼此的输出通过结构化的数据契约传递。

PLANNER 负责在看完全局信息后制定分析计划，决定先看哪些文件、先做哪些工具动作。REVERSE 负责逆向与恢复，对于加壳或混淆的目标，它会执行脱壳、字符串恢复、反编译等步骤，把不可读的二进制还原成可以阅读的伪代码。AUDITOR 是核心的语义审计角色，它在一个个审计单元上工作，每个单元对应一段代码或一个函数，AUDITOR 要在其中找出可疑的缺陷并给出证据行。REVIEWER 负责独立复核，它对 AUDITOR 提出的候选逐条检查，要求所有成立的必要条件都有证据支撑，只有这样才能把候选定为 VALIDATED，证据不足则定为 INCONCLUSIVE，推理有误则定为 REJECTED。VERIFIER 负责把复核成立的发现转化成可执行的验证方案，也就是一份能真正运行的测试配方。REPORTER 负责汇总并生成最终报告。

这套分工的关键在于审计与复核是分离的：提出假设的人不能自己批准自己的假设，必须由另一个角色在有证据约束的规则下重新判断。这一点在第四章和第六章的若干案例中反复发挥作用。

### 2.3 首版支持的四类缺陷

系统首版重点支持四类缺陷，分别对应注入、路径遍历、认证与授权、内存越界。选择这四类的原因之一是它们都能用"文件输入到进程执行再到标记观察"这一条统一的路径来验证：给目标一个特定的输入文件或命令行参数，运行它，然后观察是否出现了不该出现的文件、进程是否以异常状态终止、受限资源是否被越权导出。这样验证侧不需要为每种缺陷单独设计一套基础设施。

具体到判定词汇，"注入"类通常会观察目标是否额外执行了攻击者给出的命令或额外创建了文件；"路径遍历"类观察工作目录之外是否出现了被写入的文件；"认证与授权"类观察在凭据或角色不合规的情况下是否仍然完成了受限操作；"内存越界"类观察进程是否以内存访问违例之类的原生异常状态终止。

## 三、四个自研测试样例

本章是报告的主体。四个样例是我们自己编写的闭源受控对象，成对冻结为 1.0.0 缺陷版与 1.0.1 修复版，两个版本只有缺陷相关的那一处差异，其余代码完全一致。这种成对冻结的做法让每一组对照都是干净的：如果系统在 1.0.0 上复现了缺陷而在 1.0.1 上没有复现，那么差异必然来自那一处改动，而不可能来自环境漂移或代码重构。

### 3.1 设计思路

设计这四个样例时遵循了四条原则。

第一条是每个样例只承载一类缺陷，不做复合。这样当系统报出结果时，我们可以明确知道它命中或错过了什么，不需要在多个候选原因之间做归因。

第二条是缺陷必须由文档化的命令行接口触达，不能依赖未公开的内部状态。每个样例的调用方式都写在其接口定义里，任何拿到二进制的人按文档操作就能复现，不需要额外信息。

第三条是修复版必须是真的修好了，而不是简单地关闭功能。例如路径遍历的修复是把传入的名字压平成一个扁平的文件名，而不是拒绝所有导入请求；命令注入的修复是改成直接复制文件，而不是禁止用户传入文档名。这一点很重要，因为如果修复方式是"关掉功能"，那么修复版的行为差异就可能来自功能缺失而非缺陷消失。

第四条是保护处理要真实。加壳组的两个对象用 UPX 5.2.1 做实际加壳，混淆组的两个对象用 XOR 编码字符串并插入不透明谓词，`admin`、`cmd.exe /d /c type `、`relay.txt` 这类关键常量在出厂二进制里都不以明文出现。这样系统的逆向与解混淆环节才有真实的工作要做。

### 3.2 四个对象的定义

ParcelDrop 编号 P1，属于加壳组，保护方式是 UPX 5.2.1 实壳。它的功能是把一个指定名字的文档导入到一个扁平收件目录里，如果目标文件已存在则不覆盖。它的接口是 `ParcelDrop.exe INBOX ENTRY_NAME PAYLOAD_FILE`，三个参数分别是要导入到的收件目录、导入后使用的条目名、要导入的源文件。缺陷版 1.0.0 会把用户传入的条目名原样拼接到收件目录路径后面；修复版 1.0.1 会在导入前把条目名压平成一个单独的扁平文件名，去掉其中的目录成分。它承载的缺陷类型是路径遍历。

RowVault 编号 P2，同样属于加壳组，保护方式是 UPX 5.2.1 实壳。它的功能是读取一个记录文件里的标签字段并输出。它的接口是 `RowVault.exe RECORD.rv`，只接收一个记录文件。记录文件的格式是开头三个字节的 ASCII 字符串 RV1，接着一个长度字节，然后是标签内容，支持的标签最长 32 字节。缺陷版 1.0.0 会直接信任文件里存的那个长度字节，不管它写成多少；修复版 1.0.1 会把超过支持宽度的标签截断。它承载的缺陷类型是内存越界。

PermitLedger 编号 O1，属于混淆组，保护方式是 XOR 编码字符串加不透明谓词。它的功能是依据一个配置好的账户文件做认证，然后显示状态或导出受限记录。它的接口是 `PermitLedger.exe ACCOUNT USER PASSWORD ROLE ACTION RECORD OUTPUT`，其中 ACCOUNT 和 RECORD 属于运维配置项，由操作方事先准备好；真正由请求方提供的只有 USER、PASSWORD、ROLE 和 ACTION。缺陷版 1.0.0 在做受限导出授权判断时，用的是请求方自己声明的那个 ROLE；修复版 1.0.1 改成用账户文件里实际存储的角色来做判断，并且在请求未被授权时什么也不输出就结束。它承载的缺陷类型是认证与授权。

TextRelay 编号 O2，同样属于混淆组，保护方式是 XOR 编码字符串加不透明谓词。它的功能是把一份文档收集到工作目录下的 relay.txt 里。它的接口是 `TextRelay.exe DOCUMENT`，只接收一个文档名。这里的 DOCUMENT 语义上是一个数据文件名，不是一个命令。缺陷版 1.0.0 会把这个名字交给命令解释器处理；修复版 1.0.1 改成直接复制这个指定文件。它承载的缺陷类型是命令注入。

### 3.3 逐个样例的详细分析

#### 3.3.1 ParcelDrop（P1）：路径遍历

ParcelDrop 的正常功能很单纯：给一个收件目录、一个想使用的条目名、一个源文件，程序把源文件复制进收件目录，用条目名命名。设计者显然想让它像邮局的投递口一样，只往里放东西，不涉及目录之外。

缺陷出在条目名的处理上。1.0.0 版本把用户给的 ENTRY_NAME 直接拼接到 INBOX 后面构成完整目标路径。如果 ENTRY_NAME 写成 `..\escaped.txt`，拼接后得到的路径在解析时会先进入 INBOX 再退回上一级，最终落点在工作目录根，也就是越出了收件目录。这不是理论推演，实测中正常输入 `seed.txt` 会安静地落在 `inbox\` 里面，而 `..\escaped.txt` 确实把文件写到了工作目录根，`..\..\deep-escape.txt` 甚至能连跳两级写到工作目录之外。

1.0.1 的修复做法是在导入之前把条目名压平成一个单独的扁平文件名，也就是说不管传入的字符串里带多少层 `..` 和分隔符，最终只会用到最后那一段作为文件名。这样仍然保留了"可以自定义条目名"的功能，只是去掉了名字里隐含的目录结构。修复后同样的 `..\escaped.txt` 输入只在收件目录内产生一个名为 `escaped.txt` 的文件，不再越出边界。

从工具链角度看，ParcelDrop 出厂时被 UPX 5.2.1 加了壳，识别结果为 HIGH 置信度。系统的处理过程是先把壳脱掉，解包后体积从 3072 字节变为 4096 字节，节区恢复正常，导入表从 5 项增加到 16 项。脱壳之后才能读到真实的导入信息，静态检查在解包镜像里找到 `CopyFileW`、`CreateDirectoryW`、`GetFileAttributesW`，与"复制文件到目录"这个语义完全吻合。这一步很重要，它说明系统分析的是脱壳后的真实代码，而不是加壳的外壳。脱壳产物与原始加壳文件之间保留了派生映射，两个哈希都记录在案。

#### 3.3.2 RowVault（P2）：内存越界

RowVault 读取记录文件并输出其中的标签。记录格式是固定的三段结构：前三个字节是 ASCII 的 RV1，接着是一个长度字节，然后是长度字节所声明的那么多字节的标签内容。程序声明支持的标签最长 32 字节。

缺陷出在长度字节的可信度上。1.0.0 版本读文件时直接信任文件里写的那个长度字节，不做上限检查，然后按这个长度去准备缓冲区并读取内容。如果伪造一个记录文件，把长度字节写成 0x60，也就是 96，程序就会按 96 字节来操作，而实际解析出的标签远不到这个长度，于是发生越界写。实测中给 96 字节标签的记录文件，进程以 0xC0000005 也就是内存访问违例终止，两次运行结果一致。

1.0.1 的修复是从根源上限制宽度：读取时如果标签超过支持的 32 字节就截断。修复后同样的 96 字节标签不再导致进程异常终止，而正常输入仍然照旧工作。

一个值得记录的细节是边界位置。为了确认"越界"到底发生在哪里，验证时额外做了一个边界探针：32 字节的标签正常退出并正确输出，33 字节的标签同样触发崩溃。这就把边界精确地钉在了 32 字节这个位置上，与程序文档里声明的支持宽度完全一致，说明我们找到的机理与实现是一致的，而不是碰巧让程序崩了一个不相干的地方。

RowVault 同样用 UPX 5.2.1 实壳，脱壳后的静态检查找到 `VirtualAlloc`、`VirtualFree`、`GetSystemInfo`，这三个导入与"按可变长度分配缓冲区再释放"的行为相符，为越界路径提供了旁证。

#### 3.3.3 PermitLedger（O1）：认证与授权

PermitLedger 是一个带权限模型的小工具。它读取一个账户文件，账户文件的格式是每行三个字段 `user|password|role`。程序支持三种动作：做认证并显示状态、按凭据导出受限记录、以及普通的 status 显示。ACCOUNT 参数指向账户文件，RECORD 指向要导出的记录，OUTPUT 是输出文件名，这些都属于运维配置；请求方提供的是 USER、PASSWORD、ROLE 和 ACTION。

缺陷出在授权判断的依据上。1.0.0 版本在做受限导出时，判断依据是请求方自己声明的 ROLE。也就是说，一个真实角色只是 guest 的账户，只要在命令里声明自己是 admin，导出就会被授权。实测中用一个真实角色为 guest 的账户配合自报的 `ROLE=admin`，程序退出 0 并且真的生成了 `exported.txt`。对照之下，正确凭据配合账户文件里存储的 guest 角色时程序退出 4 表示拒绝，错误口令退出 5，status 动作退出 0 但不输出——这些负向对照都符合预期，说明程序本身并不是"什么都放行"，而是恰好在这一个判断点上用错了依据。

1.0.1 的修复是把授权依据换成账户文件里实际存储的角色，并且在请求未被授权时安静结束、不产生输出。修复后同样的自报 `ROLE=admin` 请求不再能导出受限记录。

这个对象属于混淆组，处理方式是 XOR 编码字符串加不透明谓词。这样一来，`admin` 这类关键常量在出厂二进制里不以明文出现，静态字符串搜索不能直接读到它，必须经过解混淆或透过伪代码分析才能还原语义。系统在混淆前的参考构建里确认 `admin` 是明文常量，而出厂文件中该常量不可明文检索，两者对照说明保护处理确实生效。从导入表看，出厂文件导入了 `lstrcmpA` 与 `CopyFileW`，与"比较凭据字符串后复制记录"的行为一致。

#### 3.3.4 TextRelay（O2）：命令注入

TextRelay 的功能是把一份文档收集到工作目录下的 relay.txt。接口只有一个参数 DOCUMENT，语义上就是一个数据文件名。正常使用下，程序把 DOCUMENT 指向的文件复制成 relay.txt，不涉及任何命令解释。

缺陷出在这个名字最终被谁处理。1.0.0 版本把 DOCUMENT 直接交给命令解释器，也就是说名字里如果含有 `&`、`|`、`>` 这类命令解释器元字符，就会被当作命令的一部分执行。实测中把文档名写成 `doc.txt & copy doc.txt injected.txt`，程序除了正常的 relay.txt 之外，还额外生成了一个 injected.txt，证明注入的命令确实被执行了。为了排除"只是碰巧生成了一个文件"的解释，验证时又用 `doc.txt & copy /y doc.txt arbitrary.txt` 跑了一遍，另一条命令同样被执行，说明这是命令解释器级别的注入，不是某个特定字符串的特例。

1.0.1 的修复是彻底改变实现方式：不再把名字交给命令解释器，而是直接复制指定文件。这样命令元字符就只是普通字符，不再有特殊含义。修复后同样的注入输入只产生 relay.txt，不再出现注入文件。

TextRelay 与 PermitLedger 同属混淆组，采用相同的 XOR 加不透明谓词处理。出厂文件里 `cmd.exe /d /c type ` 和 `relay.txt` 这两个关键字符串都不以明文出现，而在混淆前的参考构建里它们是明文，这组对照同样说明保护生效。出厂文件导入了 `CreateProcessW` 和 `GetSystemDirectoryW`，这两个导入与"启动命令解释器执行命令"的行为相符，本身也是缺陷机理的佐证。

### 3.4 测试过程与结果

#### 3.4.1 静态语义审计

对四个对象的静态审计走的是产品自身的多智能体通道。系统先导入二进制，扫描出可审计单元，然后启动 PLANNER、REVERSE、AUDITOR、REVIEWER 等角色依次工作。审计过程中，模型只能看到反编译后的代码和工具产物，看不到源码，也看不到我们预设的答案，属于盲测。

静态审计的结论如下。P1 的路径遍历被复核为 VALIDATED，也就是说 REVIEWER 认定"条目名未经约束直接拼接进目标路径"这条候选的所有必要条件都有证据支撑。P2 的内存越界在静态侧被定为 INCONCLUSIVE，原因是静态分析看到的是长度字段被信任这个事实，但"长度字段被写大之后是否真的会越界"需要运行才能确认，静态证据不足以把必要条件全部补齐；这个判定是保守的，而运行侧随后给出了确定结论。O1 的授权缺陷被复核为 VALIDATED，并且严重度被评为 HIGH。O2 的命令注入同样被复核为 VALIDATED，严重度为 HIGH。

四个对象的审计状态分别是 P1、P2、O1 为 RUN_STATE_PARTIAL，O2 为 RUN_STATE_COMPLETED。调用量分别是 P1 审计 2 个单元用了 18 次调用，P2 审计 2 个单元用了 26 次调用，O1 审计 6 个单元用了 84 次调用，O2 审计 6 个单元用了 65 次调用。这里要再次强调，PARTIAL 是任务级状态，代表审计流程没有把所有计划单元都跑完，它不否定其中已经产生的 VALIDATED 结论。

#### 3.4.2 运行验证（缺陷版与修复版对照）

静态审计只能给出"这里有可疑之处"的判断，真正确定缺陷存在并确认修复生效，靠的是运行验证。运行验证使用宿主机执行器，观察方式是标记文件或原生异常状态，而不是简单看退出码。

判定结果是：四个对象的 1.0.0 缺陷版全部 REPRODUCED，四个对象的 1.0.1 修复版全部 NOT_REPRODUCED。也就是说，每一个缺陷在缺陷版上被两次探针观察到，在修复版上同样两次探针都没有被观察到，而正常输入在两侧都成功。这个"缺陷版复现、修复版不复现、正常输入两侧都通"的三段式对照，是缺陷真实存在且修复真实生效的最强证据形式。

具体的观察判据是：P1 用 `ENTRY_NAME = ..\escaped.txt`，观察工作目录根是否出现 `escaped.txt`；P2 用长度字节为 0x60 的记录文件，观察进程是否以 `C0000005` 终止；O1 用已认证凭据加自报 `ROLE=admin`，观察受限记录是否被导出为 `exported.txt`；O2 用文档名 `doc.txt & copy doc.txt injected.txt`，观察是否出现注入生成的 `injected.txt`。

#### 3.4.3 自动利用证据

当运行验证判定为 REPRODUCED 时，系统会进一步产出可直接复用的利用证据包，不需要人工整理。每个证据包包含三份产物：一份证据 JSON，记录目标与配置的哈希、使用的适配器、观察方式、探针参数、多次试验结果以及影响与限制；一份复现配方，记录重建测试环境所需的夹具和观察规则；一份复放脚本，它只重建自己的测试目录，然后用记录下来的参数运行目标。

四个对象的利用证据都完成了独立复放，复放结果是每项 2/2 REPRODUCED。P1 的效果是工作目录根出现越出 INBOX 的 `escaped.txt`；P2 的效果是进程以 `C0000005` 终止且两次一致；O1 的效果是受限记录被导出为 `exported.txt`；O2 的效果是注入命令生成 `injected.txt`。

复放脚本只使用归档的脚本、配方和目标二进制，脱离产品数据库独立运行，这保证了证据的可迁移性：即使拿到另一台机器上，只要目标二进制一致，按配方也能重放同样的结果。需要说明的影响边界是，这些证据记录的是在授权本地目标上观察到的效果，包括目录外写入、越界写导致终止、越权导出、命令被执行，不应当外推为任意代码执行或远程利用。

#### 3.4.4 漏洞真实性核验

为了正面回答"这些漏洞到底是不是真的"，我们用了一个不读取产品配方的最小验证器，重新驱动四个出厂二进制。这个验证器做三类探测：负向对照，也就是正常输入下程序应该表现正常；利用输入，也就是应该触发缺陷的输入；以及有边界可言的边界探针。另外还对静态导入做了核对。

核验的详细结果如下。P1 的负向对照是正常导入，退出 0，文件落在 `inbox\` 内，没有逃逸文件；利用输入 `..\escaped.txt` 把文件写到工作目录根，`..\..\deep-escape.txt` 连跳两级写到工作目录之外；静态佐证是解包镜像导入 `CopyFileW`、`CreateDirectoryW`、`GetFileAttributesW`。P2 的负向对照是 32 字节标签，退出 0 并正常输出标签；利用输入是 96 字节标签，进程以 `0xC0000005` 终止；边界探针是 33 字节标签同样崩溃，说明边界就在 32 字节；静态佐证是解包镜像导入 `VirtualAlloc`、`VirtualFree`、`GetSystemInfo`。O1 的负向对照是正确凭据配合存储角色 guest 导出会被拒绝、退出 4，错误口令退出 5，status 退出 0 无输出；利用输入是正确凭据加自报 `ROLE=admin`，退出 0 并生成 `exported.txt`；静态佐证是出厂文件导入 `lstrcmpA` 与 `CopyFileW`，且 `admin` 常量在混淆前的参考构建里是明文。O2 的负向对照是普通文档名，退出 0 生成 `relay.txt`，没有注入文件；利用输入是 `doc.txt & copy doc.txt injected.txt` 生成注入文件，再用 `doc.txt & copy /y doc.txt arbitrary.txt` 证明另一条命令同样被执行；静态佐证是出厂文件导入 `CreateProcessW` 与 `GetSystemDirectoryW`，且 `cmd.exe /d /c type ` 在参考构建里是明文。

这 13 项检查全部通过。这里要解释一下为什么静态检查读的是"审计实际分析的那张镜像"而不是直接读出厂文件：加壳会把大部分导入表隐藏起来，所以加壳的两项读的是 UPX 解包副本；混淆的两项只有字符串被编码、导入表本身仍可读，所以可以直接读出厂文件。这样安排保证了静态佐证与系统的实际分析对象是同一份东西。

#### 3.4.5 独立动态模糊测试

产品的 FUZZ 通道只接受预构建的 libFuzzer 目标，而这四个出厂 PE 不是插桩构建，因此我们对它们单独做了一轮独立变异模糊测试。做法是给每个对象准备一个种子语料，用字典驱动的字节和结构变异进行输入变异，每个对象配一条明确的安全断言作为命中判据，命中之后按签名去重、用 delta debugging 缩减、再复放两次。

四个对象的测试结果如下。P1 的安全断言是工作目录里出现 inbox 之外的文件，执行 1503 次，在第 1294 次变异时命中，缩减后的输入只有 4 个字节 `..\r`，复放 2/2 命中。P2 的安全断言是进程以内存访问违例终止，执行 1503 次，在第 514 次变异时命中，缩减后的输入是 37 字节的记录，其长度字节为 33，复放 2/2 命中。O1 的安全断言是用调用方自报角色完成受限导出，执行 1504 次，在第 6 次变异时就命中，缩减后的输入就是 `admin` 这个词，复放 2/2 命中。O2 的安全断言是目标额外创建了文件，也就是注入命令生效，执行 1503 次，在第 1266 次变异时命中，缩减后的输入是 4 个字节 `>q&t`，复放 2/2 命中。

P2 这一条尤其能说明问题：模糊测试完全没有被告知任何长度阈值，却自己变异出了一个"长度字节等于载荷长度"的合法记录，然后撞上了越界写。这说明越界路径在正常的输入空间里就能被随机变异触达，不需要知道内部细节。

关于这轮模糊测试的边界需要说明清楚：它是在宿主机上运行的独立模糊测试，没有覆盖反馈机制，所以上面那些数字是执行次数，不是边覆盖；安全断言是我们按"程序应当保持的安全性质"写出来的，命中只能证明该性质被违反，不等于可以远程利用；产品自身的 FUZZ 通道是另一条路径，用的是 libFuzzer 加崩溃去重、缩减和复放。

#### 3.4.6 智能体自提方案的验证

前面几节的验证配方都是我们写的。为了再验一层"系统自己提出的方案能不能用"，我们把智能体在审计过程中自己保存的 VERIFIER 配方原样交给产品执行。这一轮跑在演示库的副本上，不动演示数据。

结果是两部分。P1 的智能体配方是探针 `inbox, ..\escaped.dll, seed.txt`，观察标记文件 `escaped.dll`，这个输入与归档 PoC 的输入不同，属于智能体自己想出来的；执行结果为 REPRODUCED，并且系统自动归档了 PoC。O2 的智能体配方是 `doc.txt & echo canary>marker.txt & echo done`，执行结果同样为 REPRODUCED 并自动归档 PoC。

另外两项没有通过，但原因是数据不自洽而不是漏洞不存在。P2 的配方里，探针 `probe.rv` 两次以 `C0000005` 崩溃，但基线文件 `baseline.rv` 只有 20 个字节，不满足程序要求的"长度字节等于文件长度减 4"这个格式约束，导致正常输入也失败，运行侧因此判为 ERROR。O1 的配方里，账户夹具只写了 `user|pass` 两个字段，而程序要求 `user|password|role` 三个字段，三次运行都退出 2，同样判为 ERROR。

把这两类结果分开看很重要：四项缺陷本身都已经由独立验证器和归档 PoC 证实，P2 和 O1 暴露的是 VERIFIER 生成夹具时的质量问题，也就是提示词与配方校验还有已知缺口。这一条已经记录在案，不当作通过处理。

### 3.5 数据汇总

把本章的主要数字汇总如下，全部可以在对应批次的 `summary.json` 中核对。

构建批次为 `protected-tools-20260911-r3`，保留编译器版本、UPX 5.2.1、每个产物的 SHA-256 以及 `upx --best`、`upx -t`、`upx -d` 的操作记录。缺陷版 SHA-256 的前 12 位分别是：P1 ParcelDrop `d3f3f58a3492`，P2 RowVault `3829dc94641d`，O1 PermitLedger `36b9d0fffad6`，O2 TextRelay `102264e72e45`。

### 3.6 归档形态与复现方式

四个对象按"一个软件一个项目"的方式组织，每个对象都有独立的审计目录，里面保留原始审计 JSON、三种格式的报告（JSON、HTML、Markdown）、模型调用量与 token 用量、执行产物哈希，以及上面提到的利用证据三件套。

整个批次可以在仓库根目录用以下命令重建与复核。构建并冻结成对产物用 `py -3 scripts/build_protected_tools.py --batch protected-tools-20260911-r3`。不经模型、直接在宿主机核对完整性、实壳或混淆证据与缺陷修复行为矩阵用 `py -3 scripts/verify_protected_tools.py --batch protected-tools-20260911-r3`。导入四个闭源二进制做真实模型审计、并在同一配置下对照缺陷版与修复版用 `py -3 scripts/audit_protected_tools.py --batch protected-acceptance-20260911-r1`。独立复放归档的利用证据用 `py -3 scripts/verify_pocs.py --batch protected-poc-20260911-r2`。重新驱动出厂二进制做真实性核验用 `py -3 scripts/verify_vulnerabilities.py --batch protected-tools-20260911-r3`。用智能体自己的配方做验证用 `py -3 scripts/verify_agent_plans.py --batch agent-plan-20260911`。独立变异模糊测试用 `py -3 scripts/fuzz_protected_tools.py --batch fuzz-20260911-r2 --iterations 1500`。

### 3.7 范围与限制

本章的四个对象是本次课程准备的受控二进制。说它们"真实存在缺陷"，指的是缺陷确实存在于出厂二进制里、可以由文档化的命令行触达、利用确实生效，而不是说它们是真实世界的 CVE。它们的影响范围限于本地，包括目录外写入、越权导出、以调用者权限执行命令、内存安全崩溃，任意代码执行没有证明，远程可利用性也没有证明。

静态发现是由模型从反编译代码独立得出的，我们没有提供源码，也没有提供答案。但在归档 PoC 这一层上，运行探针的参数是由验收脚本给出的，产品负责执行、判定和归档；只有 P1 与 O2 两项是智能体自行提出方案并跑通的。这个区别在评估"自主发现能力"时需要注意。

还有一个已知问题需要记录：在四次恢复链里，FLOSS 步骤被记为 FAILED。原因是执行器的 `save_strings` 在字符串集合为空时仍会上传一个 0 字节的文本产物，而服务端的 `/api/uploads` 接口明确拒绝空文件，返回 400。同一派生镜像上 UPX 解包与 Ghidra 反编译都成功了，所以这个失败没有被改写成成功，也没有影响缺陷结论；修复方向是空集合时跳过文本产物，或者写入一份占位说明。

## 四、两个大模型测试样例

### 4.1 选型口径

课程要求两类开源大模型软件各一种，这一章的两款软件就是该名额的落点，也是六项正式名额中先完成闭环的两项。

第一款是 llama-cpp-python。它是 llama.cpp 的 Python 绑定，让调用方可以直接在 Python 里加载 GGUF 模型并完成对话推理，是本地跑大模型最常用的入口之一。第二款是 FastChat。它是一个面向聊天模型的训练、部署与评测平台，本报告涉及的是它给浏览器用的那一层 Gradio 对话界面补丁。

选这两款不是因为知名度，而是它们同时满足三个条件：是真实世界里有人在用的软件；有精确的漏洞版本与修复版本可以成对冻结；缺陷位置能在源码层面被明确指认，而不是靠事后推测。第一款对应公开的 CVE-2024-34359，第二款对应上游对 Gradio 消息渲染的一次修复。

输入构造沿用第七章对照池的同一套做法。把"安全修复提交"当作标准答案，父提交是有漏洞的版本，该提交本身是已修复的版本。每个版本打成单文件 ZIP，两个包使用同一路径、同一配置。整个审计过程盲测，只把源码喂给系统，不提供 CVE 编号、公告内容或修复提交信息。

### 4.2 llama-cpp-python：聊天模板的 Jinja 注入

第一款的目标文件是 `llama_cpp/llama_chat_format.py`。

先解释它为什么会出问题。调用方使用这个库时，可以从外部加载一个 tokenizer 配置，配置里带一个 chat template，用来把对话结构渲染成模型认识的提示词格式。问题在于这个模板是 Jinja2 模板，而 1.0.0 版本是用普通的 `jinja2.Environment` 去渲染它的。普通环境不设任何沙箱，模板里可以访问 Python 对象的属性、调用方法，因此一份被控制的 tokenizer 配置等价于一份能在主机上求值的代码。这属于模板注入，也就是 SSTI，对应 CWE-1336。

系统在盲测条件下报出了这条结论，给出的位置和上游修复提交改动的行是同一处。上游的修复动作是把 `jinja2.Environment` 换成 `ImmutableSandboxedEnvironment`，这个替换在文件里一共三处，分别落在 `hf_tokenizer_config_to_chat_formatter`、`Llava15ChatHandler` 和 `chatml_function_calling`。系统对模板渲染面的判断与这三处一致，这条发现在独立复核环节被判为 VALIDATED。

漏洞版的审计状态是 RUN_STATE_PARTIAL，审计了 20 个程序单元，该快照的可审计单元总数为 91，即覆盖 20/91，共 273 次模型调用。这一轮的复核分布是 VALIDATED 7 条、INCONCLUSIVE 4 条、REJECTED 3 条，另有 1 条保持未复核。VALIDATED 的几条集中在模板注入、`image_url` 引发的服务端请求伪造、以及函数名与消息字典未经校验就进入提示词构造这几类上。

修复版的审计同样是 RUN_STATE_PARTIAL，覆盖 20/91，共 281 次模型调用。这里有一个值得展开的结果。修复版里与 Jinja 模板相关的三条发现全部被判为 REJECTED，这说明沙箱替换之后这条路径确实不再成立，系统的复核跟着撤销了原先的结论。但修复版仍然报出了 9 条 VALIDATED，集中在图片 URL 缺少协议与主机白名单、`data:` URL 与远程图片下载都没有大小上限、空字符串图片地址让切分函数陷入死循环、以及调用方提供的通配模式直接进入 `fnmatch` 匹配这些位置。换句话说，上游修掉的是那一条 CVE 的路径，同一个文件里的其他缺陷依然存在。这一点本身就是有价值的结论：它说明"修复版零命中"这种表述必须谨慎，而这里恰好是修复版有命中，并且命中得比漏洞版更多。

利用验证这一层用的是组件级 PoC。同一段恶意模板在漏洞版上渲染时，模板里的代码真的被执行了，并写出一个标记文件，文件内容就是主机 `whoami` 命令的输出。换成修复版，同一段载荷被沙箱拒绝，抛出 `SecurityError: access to attribute '__class__' of 'tuple' object is unsafe.`，标记文件没有生成。这个对照把结论从"发现"推进到了"可复现"：判据不是退出码或一行日志，而是标记文件到底有没有出现。

这个 PoC 的边界要说清楚。它是组件级的，目标文件保持源码原样，只对重型依赖用桩替身，具体说就是 llama_cpp 的 C 扩展部分被替换掉，因为验证模板渲染这条路径并不需要真的把推理跑起来。载荷本身无害，只写一个标记文件，不联网、不破坏。

### 4.3 FastChat：Gradio 消息渲染的 HTML 注入

第二款的目标文件是 `fastchat/serve/gradio_patch.py`。

FastChat 的浏览器界面借用了 Gradio 的聊天组件，并在上面做了一层自己的补丁类。缺陷出在渲染消息的那段代码上：用户消息被直接拼进一段 `<pre>` HTML 里，中间没有任何转义；助手消息那一侧走的是 `markdown2`，而它使用默认配置，原始 HTML 同样不会被清洗。两条路径都允许消息内容里的 HTML 与脚本原样进入页面，也就是消息注入，最终表现为 XSS。

系统对漏洞版报了 4 条 VALIDATED 的发现，全部属于注入类，分别指向 postprocess 未转义拼进 HTML 模板、`_process_chat_messages` 用 `markdown2` 默认配置渲染、以及 postprocess 把用户消息直接拼进 `<pre>`。漏洞版这一次跑到完全结束，状态是 RUN_STATE_COMPLETED，覆盖 7 个可审计单元中的全部 7 个，共 67 次模型调用。

修复版的状态是 RUN_STATE_PARTIAL，覆盖 6/7，共 60 次模型调用。上游的修复动作很小，就一行：在拼接之前给用户消息加上 `nh3.clean`，用 nh3 这个白名单清洗库过一遍。修复版的审计报出 3 条，其中 1 条保持未复核、2 条为 INCONCLUSIVE。这一条在修复版里没有被重新确认为 VALIDATED，但真正重要的是它也没有被判成"已经修好了"，系统把"这里可能还有问题"这个判断留了下来。

利用验证用的是真实 Chrome。把两个版本的渲染产物分别放进浏览器打开，看页面标题有没有被消息里注入的脚本改写。漏洞版的结果是两侧都被改写：用户消息侧的标题变成 XSS-USER，助手消息侧变成 XSS-ASSISTANT。修复版的结果是用户消息侧守住了，标题保持原样，注入被 nh3 的白名单拦下；但助手消息侧的标题仍然被改成 XSS-ASSISTANT。也就是说上游只修了一半，用户侧补上了，助手侧那条 `markdown2` 路径没有动。

这正是系统在修复版审计里自己报出来的那件事，实测把它坐实了。对一门以验证为核心的课程来说，这个结果比"修复版干净"更有说服力：系统不只判断漏洞是否存在，还对修复的完备性给出了可核对的判断。

这里还要更正一处早期表述。非字符串消息在渲染时会抛 TypeError，这个行为在漏洞版和修复版上都存在，两版的区别只是异常文本不同。它属于两个版本共有的既有缺陷，不是修复引入的新问题。早期的归因把它写成"修复引入新缺陷"是不成立的，本报告以利用验证的记录为准，第八章与第七章的相关表述同步更正。

这一条的 PoC 同样是组件级：Gradio 的基类用桩替身，只保留与消息渲染相关的逻辑；载荷只改页面标题，不联网、不破坏。

### 4.4 结果汇总与复现方式

两款软件跑在同一套配置下：单次审计最多 20 个可审计单元、最多 300 次模型调用、最多 8 轮工具调用、总时限 3600 秒、单次模型调用时限 240 秒、推理强度设为 high。批次名为 `open-source-two-20260911`。

从"是否命中答案"这个问题看，两对都命中了官方修复提交的改动行，位置与机理一致。从"修复版是否还报"这个问题看，两款给出了不同的结果：第一款是修复版拦住了那条 CVE 路径，但同一文件另有 9 条 VALIDATED；第二款是上游修复不完整，助手侧仍可注入。这两种结果都不能写成"修复版安全"，都必须连同覆盖率一起表述。

审计过程的原始证据、逐对象的 JSON、HTML 与 Markdown 报告、源码对照的 diff、以及两个 PoC 的脚本与物证，都保存在 `.data/verification/open-source-two-reports/` 下。批次的启动与收集摘要写在 `.data/verification/source-audits/open-source-two-20260911/summary.json`。

复现命令是在服务与执行器都已启动的前提下，于仓库根目录执行：

```powershell
py -3 scripts/audit_source_targets.py --batch open-source-two-20260911 `
    --project "llama-cpp-python · Jinja 模板注入" --project "FastChat · Gradio 消息 XSS"
```

### 4.5 范围与限制

这一章的两款软件是真实世界的开源项目，与第三章的四个受控对象性质不同，因此可以计入课程要求的正式名额。但结论仍然有明确的适用范围。

审计覆盖的是源码客体，走的是语义审计通道，没有做动态执行。两款软件的验证都停在组件级 PoC，只证明模板求值与消息渲染这两条路径确实可达、确实产生了可观察的效果，并没有把目标软件完整跑起来做端到端利用。第一款没有证明从"能执行模板代码"到"在部署环境中拿到代码执行"的完整链条；第二款没有证明注入脚本能在真实部署的会话里窃取凭据或劫持操作，只证明了脚本会执行。任意代码执行与远程可利用性都没有证明。

覆盖率的数字必须一并读出。两对的修复版覆盖率都远低于全量，第一款只覆盖 20/91 个单元，第二款是 6/7。因此"修复版有命中"是可信的负面结论，而"某一处没有命中"不能反推为那一处安全。

最后一点与第七章的口径一致：评测全程虽然盲测，但这两款软件的 CVE 都是公开信息，存在已经进入模型训练数据的可能，所以盲测只能说明"没有在提示里给答案"，不能证明模型从未见过。

## 五、机制回归夹具

除了上面四个受控对象，项目里还有一批自制夹具，用于回归验证系统各条机制本身是否正常工作。夹具与第三章的受控对象性质不同：受控对象是成对冻结的正式对照，夹具只是机制测试的输入样例。项目里所有夹具目录的说明文件都明确标注了"不是课程正式样本"，本报告沿用这个口径。

四类缺陷夹具位于 `tests/fixtures/audit/`，分为 source 与 fixed 两版。漏洞版在注入、路径遍历、认证与授权、内存越界四类上各有一条被复核为 VALIDATED，修复版 0 条 VALIDATED。最近一次批次的用量是 107 次调用、321049 tokens。这组夹具的作用是确认"四类缺陷都能被审计通道识别"这个最基本的能力，它的输入规模小、缺陷位置明确，因此结论很好读，但它不能替代真实软件上的验证。

动态执行夹具位于 `tests/fixtures/runtime/`，用于验证 Python 调用、原生 PE32 与 PE64 目标在宿主机执行器上的正常调用、超时和取消行为。另有一组夹具用于验证 UPX 正常输入与损坏输入两种情况下的处理，确认正常解包会保留原始与派生映射、损坏输入会失败而不会冒充成功，以及验证 FLOSS 在受控环境中恢复字符串并保留产物。

还有一组夹具用于验证字符串恢复与解混淆机制：Ghidra 侧能恢复一条常量 XOR 字符串并把记录写入分析元数据，Rust 侧的重复密钥 XOR 与 Base64 恢复目前主要作为辅助模块和机制测试。代码级混淆与动态密钥恢复明确不支持，这一点在报告里如实标注。

关于夹具的定位再说一句：老师没有要求支持所有保护算法，但要求用合格的真实闭源软件来证明处理、挖掘和利用能力。因此夹具只能证明机制通了，不能抵扣正式名额——这一点在第一章的口径里已经说明，这里再强调一次。

### 6.4 已确认的问题

在工程测试过程中确认了三个问题，这里如实记录，并同时说明它们的当前状态。

第一个是本地模拟服务的请求会受到代理干扰。命令环境从 Windows 设置引入了 HTTP 与 HTTPS 代理，但没有补充回环地址的排除项，导致默认包装命令下两个模型传输单元测试返回 HTTP 502；为测试进程设置 `NO_PROXY=localhost,127.0.0.1,::1` 之后整个 Rust 工作区通过。这里访问的是本地模拟服务提供方，不是真实模型接口。建议保留已有排除项并补充本地地址，或让模拟服务测试显式不使用代理，而真实模型请求继续遵循其代理配置。

第二个是动态能力判定的粒度过粗。执行器以"Python 与 Zig 同时可用"来判断 `windows-host` 能力，而调度逻辑让 Python、原始 PE 和 FUZZ 共用这一项能力，结果是只有 Python 就绪时，本来不依赖 Zig 的适配器也领不到任务；界面上的创建按钮也没有结合执行器能力提前解释缺项。这是代码检查发现的安装限制。当前已经补齐 Zig，动态浏览器用例也已经通过，所以它不是当前的阻塞项。

第三个是两处功能说明与实现不一致。安装文档仍然写着"FUZZ 仍未接入产品"，实现方案仍然写着 Python 不支持 globals 与 kwargs，而现有代码与通过的浏览器用例与这些表述不符。处理方向是统一能力说明，并保留实际的支持边界。

## 七、对照池评测

前面第三章的四个对象是我们自己造的对照。为了检验系统在真实开源代码上的表现，我们另外做了一轮对照池评测。这一轮使用的对照来自真实开源仓库的历史提交，因此更接近真实场景，但同样要受第一章三条口径的约束。

### 7.1 评测方法

评测集是怎么来的：我们把"安全修复提交"当作标准答案，具体做法是认定父提交就是有漏洞的版本、该提交本身就是已修复的版本。对六个通用开源仓库（llama-cpp-python、FastChat、ollama、DeepSeek-Coder、DeepSeek-V3、DeepSeek-Coder-V2）约 7900 个非合并提交，用安全关键词加 diff 防护型改动双通道筛选，得到 312 条候选；再对 deepseek 的 agent 仓库 `deepseek-harness` 的 9612 个非合并提交改用架构决策记录反查，因为关键词法在该仓库上失效，得到 223 条候选。然后人工逐条读 `git diff`，判定"父提交确实有该缺陷、该提交确实修掉它"，核实出 15 对，其中 9 对来自通用仓库、6 对来自 harness。同时留档了 9 条误报样例用于报告精度，实测精度约为三分之一。这个精度是我们自己公布的，不美化。

15 对里有 6 对是 harness 的 TypeScript 代码，而系统的源码通道目前不支持 ts 与 tsx，因此本轮评测只做 9 对，也就是 3 对 Python 加 6 对 Go。这 9 对按文件规模分三阶段推进，小文件不超过 200 行，中等文件 200 到 1300 行，大文件超过 1300 行。

输入构造上，每一对都构造两个输入包，分别取自 `git show <有洞提交>:<文件>` 和 `git show <修复提交>:<文件>`，打成单文件 ZIP，两个包使用同一路径、同一配置。之所以钉死成单文件，是为了避免大仓库把审计预算耗尽，那样会造成"没检出"的假象。

判定用四分列，不合并：命中，指类别匹配且复核通过为 VALIDATED 且引文覆盖目标文件；有候选未成立，指有发现但没有通过复核，例如 INCONCLUSIVE；未检出，指已经审计过但零发现；未覆盖，指目标文件下没有任何成功的 AUDITOR 任务，这一列不算安全。在此之上还有更严的一档叫"命中改动点"，指的是通过复核的证据行正好落在 git diff 的改动行上。最终的 PASS 判据是：有洞版本命中了改动点，并且修复版本 0 条命中改动点。

评测全程盲测，审计输入只有源码本身，不喂 CVE 编号、不喂公告、不喂修复提交信息。每个 run 的原始审计 JSON、三种格式报告、模型调用量与 token 用量都留档。

这一轮还新增了两个工具能力。一个是离线复判，用 `scripts/check_pair_pool.py --rejudge` 不连服务、不花模型费用，直接按"git diff 改动行与复核证据行取交集"重算全部批次判定，本轮 11 个批次的重算结果与在线判定一致。另一个是挖掘收窄，用 `scripts/mine_security_commits.py --strict` 针对大仓库压缩噪声，实测 harness 上最噪声的通道从 1245 条压到 13 条，总候选从 2462 条降到 1230 条，而六个通用仓库上原有的 9 对对照全部保留，零损伤。

另外还做了一项附带验证：harness 的有洞版本可以构建和启动。漏洞版提交 `19c772f4` 在本地 clone 之后，用 pnpm 11.7.0 与 Node 24.15 安装、构建成功，`dsh web` 启动后在 `127.0.0.1:3080` 返回 HTTP 200，仅监听回环，验证之后已经关停。这为后续把它作为课程开源大模型名额候选打下了环境基础，审计侧仍然需要 ts 通道支持。

### 7.2 评测结果

9 对的结果按对逐一说明如下。

p01 是 llama-cpp-python 的 `llama_chat_format.py`，91 个单元，类别是注入。漏洞包命中了改动点，有 2 条，覆盖 19/91；修复包有候选未成立，覆盖 1/91。判定为 PASS。命中的内容是"未沙箱化的 Jinja2 渲染远程 `chat_template` 自带模板造成 SSTI 风险"，以及"未沙箱化的 Jinja2 渲染 `tokenizer_config` 的 `chat_template` 自带模板"，这正是公开 CVE-2024-34359 的修复点。

p02 是 llama-cpp-python 的 `llama.py`，61 个单元，类别是内存越界。漏洞包有候选未成立，覆盖 6/61；修复包连接失败没有跑。这一对被截断，不可判定。

p03 是 FastChat 的 `gradio_patch.py`，7 个单元，类别是注入，命中改动点，覆盖 7/7；修复包也命中改动点，有 2 条。判定为非 PASS，但含金量很高，因为它暴露了上游修复的问题：一条是"助手或模型消息经 `markdown2` 渲染前未净化，注入原始 HTML 造成 XSS"，说明上游修复不完整；另一条是"用户消息直接传入 `nh3.clean`，非字符串类型会抛未捕获异常"，早期被归为修复引入的新缺陷，后经利用验证更正为两版共有的既有缺陷，详见 8.2 节与第四章。

p04 是 ollama 的 `readline/history.go`，10 个单元，类别是认证与授权。漏洞包有候选未成立，覆盖 8/10；修复包有候选未成立，覆盖 10/10；两侧都 0 条 VALIDATED。候选其实精确指向了 `0o666`，三项必要条件也都是 SUPPORTED，但因为 `EXTRA_PRECONDITION` 为 UNKNOWN，也就是 umask 与多用户环境这类前提无法确定，全部被压成 INCONCLUSIVE。模型甚至主动给出了反证，说"umask 为 0o077 时风险不成立"，然后被规则按住。这一对不是能力问题，是规则口径问题。

p05 是 ollama 的 `llm/server.go`，17 个单元，类别是内存越界。漏洞包有候选未成立，覆盖 14/17；修复包连接失败。这一对同样是截断，不可判定。

p06 是 ollama 的 `server/download.go`，19 个单元，类别是内存越界。漏洞包命中了改动点，覆盖 5/19；修复包有候选未成立，覆盖 2/19。判定为 PASS，但带覆盖缺口备注。命中的内容是"HEAD 请求的 Content-Length 未校验导致 Parts 为空并越界 panic"，机理与标准答案完全一致。

p07 是 ollama 的 `server/images.go`，30 个单元，类别是路径遍历。漏洞包命中改动点，覆盖 4/30；修复包也命中改动点，有 2 条，覆盖 5/30。判定为非 PASS，但发现了上游修复不彻底：修复后的 `realpath(mfDir, from)` 在改动点处仍然存在被复核成立的遗留问题，也就是路径归一化之后仍然没有做目录边界约束，绝对路径或符号链接的落点仍然交给 `os.Open`。

p08 是 ollama 的 `auth/auth.go`，5 个单元，类别是认证与授权。漏洞包有候选未成立，覆盖 5/5；修复包有候选未成立，覆盖 5/5。标准答案主张的那一条被 REJECTED，但同一个文件里 `NewNonce` 未校验长度导致超大值 panic 的问题被 VALIDATED，这是一个真实的拒绝服务缺陷，只是类别不同，所以不计命中。

p09 是 ollama 的 `llama/runner/image.go`，10 个单元，类别是内存越界。漏洞包命中类别但不在改动点，覆盖 5/10；修复包同样命中类别但不在改动点，覆盖 10/10。两侧各有 2 条 VALIDATED，内容都是 `hashImage` 锁外共享哈希对象导致的数据竞争，这是真实缺陷，但不是目标（零长度校验），也不在改动点上。

合计下来是 PASS 2 对、非 PASS 5 对、截断 2 对。可判定的是 7 对。直接命中 git diff 改动点的有 4 对，分别是 p01、p03、p06、p07。发现上游修复不彻底的有 2 对，分别是 p03 和 p07。找到目标之外其它真实缺陷的有 2 对，分别是 p08 和 p09。整个评测环节共 1724 次模型调用、9276614 token，其中包含被截断批次的真实消耗，另有 3 次调用的用量未知，如实标注。

### 7.3 系统性发现

对照池评测除了给出逐对结果，还暴露了五个系统性的问题，这些副产品同样有价值。

第一个是权限、umask、TOCTOU 这一类缺陷在"源码快照就是全部输入"的口径下无法被判定为成立。复核规则要求所有必要条件都有证据，而这类缺陷依赖运行环境前提，比如 umask 取值、是否多用户环境，这些前提在源码快照里根本无从确定，于是 ReviewDraft 的校验规则就会把整条候选压成 INCONCLUSIVE。p04 就是实证。评测口径需要为这类缺陷单列一档，比如"前提外置型"，否则这类真实缺陷永远计 0。

第二个是服务端的健壮性缺陷。`agents.rs` 里 AUDITOR 的调用是 `context.execute("AUDITOR", ...).await?` 直接上抛，意味着单个审计单元的模型响应校验失败就会中止整轮。本轮实测到的三类错误分别是 `missing field audited_unit_ids`、`证据的行范围或引用文本无效`、`invalid type: sequence, expected a str`。对比之下 VERIFIER 的循环是显式 catch 的。另一个同类问题是 REVIEWER 把带 UNKNOWN 前提的候选判为 VALIDATED，被校验规则正确拒绝之后同样中止整轮。这个缺陷的影响面很大：本轮 12 个失败任务分布在 9 个批次里，8 个批次的覆盖率数字是由这个缺陷决定的。最典型的例子是 p03 首轮漏洞包，1 个任务失败就导致 0/7 单元、整轮零产出，这个结果被记录为"未覆盖"而不是"检不出"。这是最值得优先修的一项。

第三个是运行方差。同一个输入两轮跑出来的结果可以不同，p03 修复包首轮 0 条通过、重跑 2 条就是例子。因此单轮结果不能下死结论，结果文档和判据都要保留两轮口径。

第四个是"修复包零命中"的证据强度受覆盖率限制。p01 修复包只覆盖 1/91，p06 修复包只覆盖 2/19，p01 漏洞包覆盖 19/91。表里的 PASS 必须以"覆盖缺口备注"的形式带上，不能写成"修复版安全"。

第五个是本轮的截断说明，这属于基建问题而不是能力问题。当天 17:51:05 到 20 分之间，三个在跑的漏洞包 run 被 CancelRun，涉及 p05、p01、p02；17:51:30 到 32 分之间三个驱动各自启动修复包 run；17:53 到 54 分之间全部实例被整体关停，五个 server 加五个 executor，p05 与 p02 的修复包因此连接失败。所有批次原样保留，不重跑、不改写。

### 7.4 利用验证

对照池评测给出了静态层面的结论，为了把这些结论推进一步，我们另外做了三个利用验证案例，从"检出"走到"利用证明"。

第一个是模板注入到任意代码执行，对应 p01。同一段恶意的 chat_template 输入，在漏洞版里渲染期真的执行了代码，写出了主机命令输出；在修复版里被沙箱拒绝，抛出 SecurityError。这就把"CVE-2024-34359 的修复点确实被定位到"从静态结论变成了可观察的行为差异。

第二个是 XSS 浏览器执行证明，对应 p03。用真实的 Chrome 打开两个页面，漏洞版页面标题被注入的脚本改写，修复版保持干净；而助手消息那一侧在修复版里仍然被改写。这同时证实了两件事：用户侧的 XSS 确实存在并且修复有效，助手侧的"修复不完整"也被实测坐实。不过这里要对 p03 的另外一条结论做一次修正：利用验证发现"非字符串消息导致崩溃"这条其实不成立，因为漏洞版同样会抛 `TypeError`，也就是说这是既有缺陷而不是修复引入的，原先的归因有误，以利用验证的记录为准。

第三个是 Go 四缺陷的组件级复现，对应 p06、p07、p08、p09。做法是原样源码加依赖替身。p06 的 panic 栈直接钉到 `download.go:175`；p07 实测"修复后仍然能越出模型目录"；p08 用组件级调用确认缺少校验；p09 用 Go 的 race detector 抓到了 `hashImage` 这一处竞争点。这一组里既有对审计结论的确认，也包含两处对审计结论的修正。

三个案例都可以一键复现，入口是 `evaluation/materials-20260911/04-利用验证/` 下的 `run_all.cmd` 与 `run_all.py`，手动复现的步骤、环境依赖、预期输出和常见问题写在同目录的 `复现操作说明.md` 里。

关于本章的展示口径还要提醒一点：报告标题里的运行状态，比如 Cancelled 或 PARTIAL，是任务级运行状态，代表本轮部分批次被实例关停或预算中止截断，它不是审计结论。结论应当以每条发现的复核状态为准。展示 p01 时可以直接翻到报告里"未沙箱化的 Jinja2 环境"那一节，那里有完整的证据行、反证与复核推理。

## 八、结论

### 8.1 已经成立的内容

在正式软件验收方面，课程要求的三类各两项共六项名额已全部完成，其中两款开源大模型软件的证据见第四章。

在自研受控对象上，四个对象的缺陷都完成了完整闭环。静态审计方面，P1 路径遍历、O1 认证与授权、O2 命令注入被复核为 VALIDATED，P2 内存越界在静态侧保守地定为 INCONCLUSIVE。运行验证方面，四项缺陷版全部 REPRODUCED、四项修复版全部 NOT_REPRODUCED。利用证据方面，四项都归档了证据 JSON、复现配方和复放脚本，独立复放每项 2/2 成立。真实性核验方面，13 项检查全部通过，包括负向对照、利用输入和边界探针。独立模糊测试方面，四项都能在没有被告知阈值的情况下由随机变异触达缺陷，并完成去重、缩减与复放。智能体自提方案验证方面，P1 与 O2 的智能体配方直接跑通并自动归档 PoC。

在工程测试方面，Rust 工作区、Python unittest、Svelte 检查、协议生成、原生 UPX、原生 Semgrep、原生 FLOSS、真实智能体恢复链、两轮浏览器端到端以及后端 smoke 都通过，`doctor` 显示 9 项可用能力，IDA 与 D-810 在配置后也通过真实探测。真实工具链 UPX 到 FLOSS 到 Ghidra 的串行链路在自制夹具上跑通并保留了产物映射。

在对照池评测方面，9 对真实开源对照里 7 对可判定，4 对直接命中改动点或类别，2 对发现上游修复不彻底，2 对找到同文件其它真实缺陷，2 对 PASS，其中包括踩中公开 CVE-2024-34359 的修复点。11 个批次的离线复判与在线判定一致。

### 8.2 未完成的内容与限制

对照池评测只测了语义审计通道，规则引擎 Semgrep 对那 9 个目标基本不命中，所以结论不能写成"整条工具链的检出率"。评测全程盲测，但公开 CVE 可能已经存在于模型训练数据里，因此盲测不能证明模型从未见过。未覆盖不等于安全，任务完成不等于安全，修复版零命中也不等于修复版安全，凡是零命中的结论都带覆盖率备注。p05 与 p02 两对因为实例关停被截断，如实记录、不重跑、不补算。

对照池的利用验证里还发现 p03 的一条归因需要修正，也就是"非字符串崩溃"属于既有缺陷而非修复引入，以利用验证记录为准。受控对象的恢复链里 FLOSS 步骤被记为 FAILED，原因是空字符串集合仍上传 0 字节产物而被服务端拒绝，这是已知的实现缺口。
