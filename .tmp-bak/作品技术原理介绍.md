## 1. 作品定位与设计目标

### 1.1 要解决的问题

传统软件漏洞挖掘高度依赖人工经验：逆向工程需要分析师逐个函数阅读反编译代码，静态扫描工具产出大量需要人工二次判定的告警，而"是否真的可利用"往往缺乏可核验的证据。大语言模型的出现让"用自然语言理解代码语义"成为可能，但直接把模型接进审计流程会引入三个新问题：

1. **模型会编造结论**——它可能引用不存在的代码、给出无法复现的漏洞，而传统工具链无法自动发现这种"幻觉"；
2. **模型看不到真实二进制**——加壳、混淆会破坏语法结构，模型直接阅读被保护的产物得不到有效语义；
3. **结论无法追溯**——如果报告的每一条发现都不能回溯到"哪份文件、哪一行、由哪次工具调用和哪次模型调用得出"，那么这份报告在工程上不可信。

### 1.2 作品的设计主线

AegisAudit 的技术原理围绕一条主线展开：

> **把"不可信的大模型"放进一个"可验证、可追溯、不可篡改"的工程约束里。**

具体表现为三条设计原则：

| 原则           | 含义                                           | 对应机制                                          |
| ------------ | -------------------------------------------- | --------------------------------------------- |
| **控制与执行分离**  | 模型只负责"判断"，不负责"操作"；真实工具与目标程序由执行器在受控边界内运行      | 控制服务独占数据库写入，执行器通过协议领任务、交证据                    |
| **证据不可变**    | 导入即形成不可变快照，原始产物与派生产物分离，任何结论必须引用快照内真实存在的代码与产物 | 快照 / 产物按内容哈希保存，引文校验拒绝伪造与越界                    |
| **模型输出必须校验** | 模型提交的结构化结果在入库前由服务端做契约校验，模型不能自行声明成功           | 恢复计划校验、引文校验、状态机约束、`exploitation` 保持 `NOT_RUN` |

### 1.3 范围边界（做什么、不做什么）

- **支持**：Python / Go / C / C++ 源码，PE x86/x64 与 ELF x86_64 静态分析；首版漏洞范围为注入、路径遍历、认证/授权、内存越界四类。
- **动态侧**：Windows 宿主机 **VERIFY**（组件观察与异常复现）与 **FUZZ**（预构建 libFuzzer，含崩溃签名去重、`-minimize_crash` 缩减与最小输入两次复放）两条产品链路；受限自动利用闭环以 `CVE-2016-5180` 为样例跑通（崩溃 PoC，不等同任意代码执行）。
- **宿主**：Windows 11 x64 单机、单操作员；不要求 WSL、Docker 或 Windows Sandbox，动态验证直接在宿主机运行。
- **不做**：多用户账号与团队共享、完整渗透攻击链、分布式执行平台。ELK 类微服务集群、向量数据库等均不在设计内——单机工作流下控制服务 + SQLite + 静态前端已经足够。

## 2. 技术栈解析

本节对作品涉及的每一项关键技术作简要介绍（是什么、解决什么问题、在本作品中的角色），便于不熟悉相关技术的读者理解后文。**后文出现同名技术时不再重复介绍。**

### 2.1 基础平台与语言

**Rust**

Rust 诞生于 2010 年，最初由 Mozilla 主导开发（用于 Servo 浏览器引擎），2015 年发布 1.0 稳定版，其后由独立的 Rust 基金会维护，并已成为 Linux 内核、Windows 内核组件、Android 底层与 Chromium 中官方可用的语言之一。它是一门**编译为原生机器码的系统级编程语言**：没有虚拟机、没有垃圾回收（GC），却能同时给出"内存安全 + 线程安全"的编译期保证。

Rust 的核心机制是**所有权（ownership）模型**：每一块堆内存有且仅有一个所有者，所有者离开作用域即释放内存；值的传递默认是"移动（move）"而非浅拷贝；借用（borrowing）分为不可变借用 `&T` 与可变借用 `&mut T`，编译器通过借用检查器（borrow checker）保证"同一时刻要么多个只读、要么一个可写"，从而在编译期消除数据竞争。生命周期（lifetime）标注则让"引用不会比其指向的数据活得更久"这一性质被编译器验证，因此 Rust 中不存在悬垂指针与 use-after-free。

在此基础之上，Rust 的类型系统进一步把工程约束编码进类型：

- **枚举（enum）与模式匹配**让"一个值只能是若干状态之一"成为类型事实，`match` 强制穷尽所有分支——该处理的情况不可能被遗漏；
- **`Option<T>` / `Result<T, E>`** 把"可能为空"与"可能失败"从隐式的空指针、异常，变成必须显式处理的返回值，编译器不允许静默忽略错误；
- **`Send` / `Sync` trait** 把"该类型能否跨线程传递/共享"变成编译期可检查的属性；
- **newtype 与零开销抽象**允许用类型区分语义（如"已校验的哈希"与"任意字符串"），且不带来运行时开销。

**在本作品中的角色**：AegisAudit 的控制服务（`server`）与执行器（`executor`）全部使用 Rust 编写，项目为 `edition 2024`、最低工具链 `rust-version = 1.88`。Rust 在这里不只是"性能选择"，而是**把"证据链不可伪造"这一安全目标转化为类型约束的载体**：任务状态机被建模为枚举，非法状态转换在代码层面无法表达；证据引文被建模为"哈希 + 定位"的不可变结构；进程生命周期被绑定到显式的类型所有权上。作品对并发与错误处理的高要求（多智能体并行、工具调用可能失败、模型输出不可信），恰好落在 Rust 的强项上。

**Tokio**

Tokio 是 Rust 生态中最主流的**异步运行时**，2016 年开源，现由 Tokio 项目组维护，也是 Rust 官方异步生态的事实标准。它解决的问题是：当程序大量时间花在"等待"上（等网络响应、等磁盘 IO、等子进程结束）时，用"一个线程处理一个连接"的传统模型会因线程数暴涨而耗尽内存与调度开销。

Tokio 采用**事件循环 + 任务调度器**的多线程工作窃取（work-stealing）架构：`async fn` 被编译为状态机，遇到 `.await` 时若结果未就绪，当前任务会把控制权交还调度器而不阻塞线程；待 IO 就绪（由操作系统的就绪通知机制 epoll / kqueue / IOCP 触发）后，任务被重新唤醒执行。据此，单进程可轻松管理成千上万个并发任务。Tokio 还提供一整套异步原语：定时器、`mpsc` / `broadcast` / `watch` 通道、`Mutex` / `RwLock`，以及**取消原语 `CancellationToken`**（用于安全地中止一组协作式任务）。

**在本作品中的角色**：Tokio 是整个系统的"心跳"。它驱动控制服务的 Connect RPC 端点、审计工作流的主协程、**工作项租约（lease）的过期回收**、事件流的推送，以及执行器侧的工具进程调度与超时。作品的取消语义（用户中止一次审计运行）依赖 Tokio 的取消机制逐级传播——这与第 4 章讲的"状态机必须先进入 `CANCELLING` 才能终止"形成"运行时取消 + 业务状态约束"的双重保险。

**Axum**

Axum 是由 Tokio 项目组官方维护的 Rust **Web 框架**（2021 年发布），构建在 Tokio 运行时与 hyper HTTP 库之上。它的设计哲学是"以类型组合代替宏魔法"：路由（`Router`）把"HTTP 路径 + 方法"映射到处理函数，**提取器（extractor）**从请求中解析出类型化的参数（路径参数、查询参数、JSON 体、请求头、共享状态），处理函数只需声明它"需要什么"，框架负责在编译期校验这些提取器能否组合，返回类型则被 `IntoResponse` trait 约束为合法的响应。

Axum 的另一关键特性是**与 Tower 中间件生态无缝集成**：超时、限流、追踪（tracing）、压缩、CORS 等横切关注点都以可复用的中间件层（layer）形式叠加，无需侵入业务代码。因为直接构建在 hyper 之上，Axum 不依赖特定传输细节，既能处理标准 HTTP/1.1，也能处理 HTTP/2 与 WebSocket / 流式响应。

**在本作品中的角色**：Axum 是控制服务（`server`）的 HTTP 门面——它同时承载 Connect RPC 的各服务端点（普通请求与**服务端推送的事件流**）以及前端静态资源的分发。由于 Connect RPC 本质上是"用普通 HTTP 承载 RPC"，Axum 的路由与提取器模型与之天然契合，无需为 RPC 引入独立框架；事件流则直接复用 Axum 的流式响应能力。

**TypeScript / Node.js 工具链**

TypeScript 由微软于 2012 年发布，是 JavaScript 的**静态类型超集**：任何合法的 JavaScript 都是合法的 TypeScript，而 TypeScript 额外增加了静态类型标注、接口、泛型、枚举以及现代语言特性（可选链、装饰器等）。它由 `tsc` 编译器在**构建期**做类型检查，之后把类型信息完全擦除、输出标准 JavaScript，因此运行时不引入任何类型开销，也不改变 JS 的运行时语义。TypeScript 的价值在于"把一整类低级错误从运行时前移到编辑/构建时"：调用不存在的字段、传错参数类型、忘记处理 `null`，都会在写代码时被 IDE 与编译器直接报错。

Node.js 是让 JavaScript 脱离浏览器运行的服务端运行时（基于 V8 引擎与 libuv 事件循环）。在本作品中，Node.js 不承担产品运行时职责，而是作为**前端构建与协议代码生成的工程环境**（Vite、TypeScript 编译器、Buf 的 JS 插件等都在 Node 上运行）。

**在本作品中的角色**：前端源码（`frontend/src/`）与由 `.proto` 生成的 RPC 客户端均为 TypeScript。因为**前后端共享同一份 Protobuf 契约**，生成的前端调用代码天然带有与后端一致的消息类型定义——若契约变更导致前端代码不匹配，`tsc` 会在构建期直接报错，这正是"契约即类型、漂移即编译失败"的实现方式。

### 2.2 前后端契约

**Protocol Buffers（Protobuf）**

Protocol Buffers 由 Google 在 2001 年前后内部开发、2008 年对外开源，是一种**语言无关、平台无关的接口描述语言（IDL）与序列化机制**。它要替代的是 JSON/XML 这类"字段名以文本重复出现"的格式：在 Protobuf 中，开发者用 `.proto` 文件定义消息（`message`，即结构化数据）与服务（`service`，即一组 RPC 方法），字段用**紧凑的整数标签（field number）** 而非字符串名标识。

其编解码原理是：每个字段被编码为"标签 + 线型（wire type）+ 值"，字段名不出现在二进制中，数值用 varint 等变长整数编码，因此同样的数据比 JSON 体积更小、解析更快。更关键的是它的**兼容性规则**：只要不改动已有字段的编号与线型，就可安全地新增字段、弃用旧字段，新旧版本程序可互相通信——这使 Protobuf 成为长期演进系统里稳定的"契约载体"。

**在本作品中的角色**：`proto/audit/v1/audit.proto` 是整个系统的**唯一契约源**。它定义了 **8 个 service / 35 个 RPC**（覆盖项目管理、导入、运行调度、工作项领取、发现提交、人工复核与标注、报告历史、模型设置、验证方案建议等），浏览器、控制服务与执行器三方都从这一份 `.proto` 生成各自语言的类型化客户端/服务端代码。其价值在于"**一份 schema，多端一致**"：契约以文件形式固化并纳入版本控制，从根本上消除了"前后端各自手写解析逻辑导致漂移"的风险。

**Connect RPC**

Connect RPC 由 Buf（Protobuf 工具链背后的公司）主导开发，2022 年开源，后捐赠给云原生计算基金会（CNCF）。它要解决的痛点是：gRPC 虽然性能好、契约强，但强依赖 HTTP/2 与特定的分帧（framing）约定，导致**浏览器无法直接调用**（需 gRPC-Web 代理）、`curl` 等普通 HTTP 工具也难以调试。

Connect 的设计要点是**极简的协议映射**：一个 Connect 调用就是一次普通 HTTP `POST`，URL 路径即"`/{包名}.{服务名}/{方法名}`"，请求体就是序列化后的消息（默认仍是 Protobuf 二进制，也支持 JSON），因此浏览器、`curl`、任何标准 HTTP 客户端都能直接发起调用与调试。同时，Connect 的**同一个服务端能同时应答三种协议**——Connect、gRPC 与 gRPC-Web——因为它按请求的 `Content-Type` 探测协议并做适配，从而在不牺牲 gRPC 互操作性的前提下获得"普通 HTTP 即可用"的便利。此外 Connect 还内置对**流式 RPC**（服务端流、客户端流、双向流）的支持。

**在本作品中的角色**：Connect RPC 是**浏览器 ↔ 控制服务 ↔ 执行器**的统一通信方式。之所以选它而非 gRPC：作品的部署目标是 Windows 11 **单机**，前端直接由 Rust 服务提供静态资源、并在同一进程内调用 RPC，不需要 gRPC 的代理/网关；而普通 HTTP 的形态让整个系统的联调与排障成本大幅降低。作品的**普通请求与服务端推送的事件流共用同一份 `.proto`**，实现"一次定义、请求与流皆可"。

**Buf**

Buf 是 Protobuf 的现代工具链，定位是"更好的 `protoc`"。原生 `protoc` 的工作方式是"逐个插件、逐个文件手工传参"，缺少统一的项目配置，也几乎不提供规范检查。

Buf 的改进主要有三：其一，用 `buf.yaml` 描述模块（schema 的集合）与依赖，用 `buf.gen.yaml` 声明**代码生成的目标语言、插件与输出目录**，整个生成过程被一份可提交、可复现的配置固定下来；其二，提供 `buf lint` **规范检查**（字段命名、枚举零值、包命名等风格与兼容性规则）与 `buf breaking` **破坏性变更检测**（对照旧版本 schema 判断本次改动是否会破坏既有客户端），把"契约演进"也纳入可自动化的质量门禁；其三，内置 Buf Schema Registry（BSR）用于跨团队共享与版本化 schema。

**在本作品中的角色**：作品用 `buf.yaml` / `buf.gen.yaml` 固定生成配置，通过 `scripts/codegen.py` 统一生成 Rust（服务端/执行器）与 TypeScript（前端）代码，并校验生成物**不被人手修改**——这保证了"契约文件是唯一真相"，任何契约变更都必须从 `.proto` 出发重新生成，而非在生成代码上打补丁。

### 2.3 存储

**SQLite**

SQLite 由 D. Richard Hipp 于 2000 年发布，是世界上部署最广泛的数据库引擎。它最本质的特点是**"数据库即一个函数库"**：SQLite 不是独立运行的服务进程，而是被链接进程序的库，整个数据库（表、索引、触发器）存放在**单个跨平台文件**中。程序通过函数调用访问数据，没有网络往返，也没有独立的数据库服务器需要安装与运维。

尽管体积轻量，SQLite 却实现了完整的 SQL 子集，并严格保证 **ACID 事务**（原子性、一致性、隔离性、持久性）与外键约束、触发器等关系型能力。它采用**写者独占**的并发模型：允许任意多个读者并发，但同一时刻只有一个写者；通过 WAL（Write-Ahead Logging）日志模式可让读与写并行，显著提升并发体验。这套模型使 SQLite 特别适合**单机、单写者**的应用，也是它成为嵌入式与桌面应用首选的原因。

**在本作品中的角色**：SQLite 是控制服务的**唯一事实来源（source of truth）**，保存项目、导入快照、审计运行、工作项、发现、模型调用记录等全部状态。作品采用"**控制服务独占数据库写入**"的策略：执行器不直接连接数据库，而是通过 RPC 向控制服务"领任务、交结果"，因此写者天然唯一，彻底规避了 SQLite 的并发写瓶颈与一致性问题。配合事务，任何一次"状态推进 + 证据落库"都是原子的。

**SQLx**

SQLx 是 Rust 的**异步 SQL 数据库访问库**，支持 PostgreSQL、MySQL、SQLite 等。它与"ORM（对象关系映射）"路线相反，坚持**"写原生 SQL"**：开发者直接书写 SQL，而不是用对象操作被翻译成 SQL，因此不会出现 ORM 常见的"隐式 N+1 查询""生成的 SQL 难以预料"等问题，对性能与可读性都更可控。

SQLx 最有价值的特性是**编译期 SQL 校验**：通过 `query!` / `query_as!` 等宏，编译器会（在构建时）连接一个真实数据库（或读取预先离线准备的元数据），对照实际的表结构检查 SQL 中的**列名是否存在、类型是否匹配、参数个数是否正确**。这样，"把 `user_id` 拼成 `userid`"这类错误会直接变成编译错误，而不是运行时才炸的查询失败。此外 SQLx 提供**异步连接池**（基于 Tokio）、显式事务 API，以及**版本化迁移（migration）**机制——迁移脚本按序号依次执行并记录到数据库，使 schema 演进可复现、可审计。

**在本作品中的角色**：SQLx 实现控制服务的存储层。作品把 schema 演进固化为 `migrations/0001` 至 `0006` 六个版本化迁移脚本（含模型设置密文表），数据库结构从零到当前形态完全由迁移脚本决定。因为 SQL 的列名与类型在编译期就被校验，存储层与 schema 不会悄悄脱节——这与"契约文件唯一真相"的思路一致。

**内容寻址存储（Content-Addressable Storage）**

传统文件系统是"按名字寻址"（location-addressed）：文件放在哪个路径由人指定，同一份内容可能在不同路径下存了多份，且文件被改名或搬移后难以判断它还是不是原来那一份。内容寻址存储则**以数据内容的哈希值（本作品用 SHA-256）作为对象的唯一标识**：路径即哈希，例如某份产物存为 `blobs/ab/cd/abcd...ef`。

这一设计天然带来三个性质：

1. **去重**——相同字节内容哈希必然相同，因此只存一份，多份引用共享同一底层对象；对反复导入的同一文件以及大量相同的中间产物，可显著节省空间；
2. **完整性校验**——读取时重算哈希并与标识比对，任何损坏或被篡改都会立刻暴露，是篡改检测（tamper-evidence）的天然基础；
3. **不可变**——对象一旦以某哈希写入就不会被修改（改了哈希就变了），因此"快照"可以真正不可变。

**在本作品中的角色**：CAS 是"**证据不可变**"设计原则的实现载体。作品对**导入的原始产物、工具派生产物、模型调用的输入与输出**等一切字节对象都按内容哈希保存。由此，一条发现所引用的"某份文件的某段代码/伪代码/字符串"，最终都锚定到一个哈希对象上——只要内容有一丝变化，哈希就会不同，引文校验随即失败。这把"证据可追溯、不可伪造"从流程约定变成了**数据结构层面的强制约束**。

### 2.4 源码与二进制解析

**Tree-sitter**

Tree-sitter 由 Max Brunsfeld 开发、2018 年随 Atom 编辑器一同发布（现由 GitHub 维护），是一个**解析器生成器 + 增量解析库**。它的三个设计目标非常明确：**足够通用**以解析任意编程语言；**足够快**以支持编辑器"每按一次键就重解析"；**足够健壮**以在代码存在语法错误时仍能给出（部分）可用的语法树。

技术上，Tree-sitter 基于 **GLR 解析算法**（广义 LR，可处理存在冲突的文法），并为语言定义者提供一套 DSL（`grammar.js`）来描述文法。其最突出的是**增量解析**能力：解析结果是一棵**具体语法树（concrete syntax tree）**，每个节点带有精确的字节范围与位置；当源码被编辑时，它只重解析发生变化的部分并复用其余子树，因此即使面对大文件也能保持交互级速度。此外，Tree-sitter 的运行时是**纯 C11、零外部依赖**，可被嵌入任意语言（作品所用的 Rust 绑定即是一例），生成的解析树还能通过查询（query）语言做结构化匹配。

**在本作品中的角色**：作品用 Tree-sitter 解析 **Python / Go / C / C++** 四类源码客体，抽取模块、函数、精确位置（行/列/字节范围）、语法分支（条件、循环、异常处理等结构）以及**保守的调用候选**。之所以选它而非直接用编译器前端：它跨语言统一、无需完整构建环境即可解析、容许残缺代码，非常适合"未知质量的外部代码"这一审计场景。抽取结果构成源码侧的结构化事实基础，供后续模型审计与引文校验使用。

**Ghidra**

Ghidra 是美国国家安全局（NSA）开发并于 2019 年公开的**开源软件逆向工程（SRE）套件**（Apache-2.0 许可），被广泛视为商业工具 IDA Pro 的开源对标品。它集成了反汇编、反编译、脚本化分析与插件体系。

Ghidra 的技术核心是**"中间表示驱动"的架构无关设计**：

- 它用 **SLEIGH 处理器描述语言**为每种指令集（x86/x64、ARM/AArch64、MIPS、PowerPC、RISC-V、6502 等）定义语义，把机器码**提升（lift）为与硬件无关的中间表示 P-code**；
- 所有分析（数据流、类型推导）与**反编译**都建立在 P-code 之上，再由内置的 C++ 反编译器做数据流简化（常量传播、死代码消除、表达式重组等），最终输出类 C 伪代码。

这种"先提升到 IR、再在 IR 上分析"的做法，使新增一种架构的成本主要落在 SLEIGH 描述而非重写全部分析逻辑，也让反编译质量更稳定。Ghidra 另一项对自动化至关重要的能力是**无头分析器（Headless Analyzer）**：它把 GUI 中可交互执行的整套分析流程搬到命令行，可在无图形界面的服务器上以脚本批量处理二进制——这正是自动化审计流水线所需的形态。

**在本作品中的角色**：作品用 **Ghidra Headless**（版本 12.1.3）对 PE / ELF 目标做反编译，导出函数边界、伪代码、入口与 RVA（相对虚拟地址）、基本块、P-code、字符串及其交叉引用等结构化事实。这些内容进入 CAS 作为不可变产物，并向模型提供"可阅读、可引用"的伪代码视图。需强调的是：Ghidra 的无头批量流程是"静态 + 提升 + 反编译"，它本身**不执行目标程序**，因此不构成动态分析或沙箱。


### 2.5 静态扫描与保护处理

**Semgrep**

Semgrep（名字取自 "**sem**antic gr**ep**"）是一款**开源静态应用安全测试（SAST）工具**，其社区版引擎 Semgrep CE 采用 LGPL 2.1 许可，由 r2c（今 Semgrep Inc.）创建。它要解决的核心矛盾是：传统基于正则表达式或文本匹配的扫描**不理解语法**，容易漏报（代码换个写法就匹配不上）与误报（只是注释或字符串里出现关键词）。

Semgrep 的机制是**"语义模式匹配"**：先把源代码解析为语法树，再把规则中"看起来像源代码的模样"编译为语法树模式，据此做结构化匹配。其模式语言提供了几个关键机制——**省略号 `...`** 表示"此处可匹配任意若干节点"、**元变量（metavariable）`$X`** 表示"捕获任意表达式并在同一规则内保持一致"，以及 `metavariable-regex`、`metavariable-comparison` 等用于约束捕获内容。这使得规则能识别语义等价的多种写法，而不依赖字面文本。

Semgrep 的规则以 **YAML** 文件承载（`rules`、`patterns`、`message`、`severity`、`languages` 等字段），可离线执行；默认**完全本地运行、代码不外传**，对审计闭源代码与企业内网环境尤为友好。

**在本作品中的角色**：作品用 **Semgrep CE 1.176.1** 对源码客体做静态规则扫描。但必须强调其定位：Semgrep 命中在作品中被当作**"候选线索"而非结论**——扫描结果进入模型审计的上下文与证据池，供模型与后续校验环节参考。任何命中都不会自动升级为"已确认漏洞"，是否成立仍须经过模型论证与引文/契约校验（见第 4 章）。这是作品控制误报、防止"工具说了算"的关键分工。

**UPX**

UPX（Ultimate Packer for eXecutables）于 1998 年首次发布，是一款**开源可执行文件压缩器/加壳器**，支持 Windows PE、Linux ELF、macOS Mach-O 等二十余种可执行格式。它最初的目的很单纯——**压缩程序体积以节省磁盘与下载流量**。

UPX 的工作方式是：把原可执行文件的代码与数据段以 UCL 等压缩算法压缩，附加一段极小的自解压存根（stub），运行时由存根把原始映像在内存中**原位解压**再跳转执行，因此解压过程几乎不额外占用内存。它同时内置了对自己打包文件的**解包能力**（`upx -d`）。正因为打包-解包对称且易于获取，UPX 成为恶意软件作者廉价有效的"入门级壳"——虽然它不具备加密或强混淆，但足以让依赖字符串与节区结构的朴素分析失效。

**在本作品中的角色**：作品使用**固定版本 UPX 5.2.1** 对检测到的加壳目标做解包，并完整保留**原始文件、派生产物、内容哈希与节区/入口映射**。这里体现的是"不可变快照"原则：解包产物只作为**后续分析的输入**，**绝不就地修改原始目标**——原始字节仍以 CAS 对象保留，派生关系被显式记录，任何结论都能回溯到"基于哪次解包得到的哪份产物"。

**FLOSS**

FLOSS（FLARE Obfuscated String Solver）由 Mandiant（原 FireEye 的 FLARE 团队）开源，Apache-2.0 许可，定位是**"强化版 `strings`"**。它针对的问题是：恶意样本几乎从不把域名、URL、注册表键、命令等敏感字符串以明文常驻文件，而是**构造或解码后才在内存中出现**。

传统 `strings` 只能提取文件中连续可见的静态字符串，对上述手段完全失明。FLOSS 的做法是**静态定位 + 模拟执行**：先扫描文件找出可疑的解码例程（异或、加法、RC4、自定义变换等），再对这些例程做轻量级模拟执行，从而恢复四类字符串——

1. **静态字符串**：直接存在于文件中的明文字符串；
2. **栈字符串（stack strings）**：运行时被逐字节（或逐字符）写到栈上的字符串；
3. **紧循环字符串（tight strings）**：由紧凑循环构造、任何时刻都不会完整出现在内存中的字符串；
4. **解码字符串（decoded strings）**：经异或、RC4 或自定义例程解码后得到的字符串。

后三类是 `strings` 无论如何都看不到的，也恰恰是样本隐藏 C2 地址与持久化配置的常见位置。FLOSS 输出的是"字符串 + 其所在位置/构造方式"的可追溯结果。

**在本作品中的角色**：作品用 **FLOSS 3.1.1** 对 **PE x86/x64** 目标做字符串恢复，其结果被写入伪代码注释并作为证据进入 CAS，供模型在理解保护样本时使用（"这个函数在解码一个 URL"往往比原始字节更有语义）。作品另内置了 **XOR / Base64 启发式**作为候选补充，覆盖 FLOSS 未命中的简单编码。与 UPX 同理，FLOSS 只做静态分析、不执行目标。

**D-810-ng**

D-810-ng 是一款 **IDA Pro 插件的"下一代"版本**（前身为社区知名的 D-810 去混淆插件，`ng` 意为 next generation），由安全研究者维护。它在 **Hex-Rays 反编译器的微码（microcode）层**做去混淆——这一点是其技术关键：微码是 Hex-Rays 从汇编提升出来、尚未生成最终类 C 伪代码的中间表示，在这一层做变换，意味着改动会**贯穿地影响后续所有优化与最终伪代码**，而非在伪代码文本上做脆弱的字符串替换。

它针对真实世界的混淆器（如 Obfuscator-LLVM、Tigress、Hodur/PlugX 等）提供两类核心能力：

- **指令级优化**：化简 **MBA（Mixed Boolean-Arithmetic，混合布尔算术）** 表达式（例如 `(a+b)-2*(a&b)` 等价于 `a^b`，但前者无法被肉眼或模式匹配直接看穿）、常量折叠、不透明谓词（opaque predicate，恒真/恒假但写法复杂的分支）消除；
- **控制流去平坦化（control-flow deobfuscation）**：把被"分发器 + 状态变量"打乱的控制流（control-flow flattening）还原为自然的顺序/分支结构。

值得强调的是其**正确性保证方式**：MBA 化简规则以专用 DSL 描述，并用 **Z3 定理证明器**验证化简前后**语义等价**，因此化简是"可证明正确"的，而不只是"看起来对"的模式替换。使用它需要**商业版 IDA Pro 与 Hex-Rays 反编译器**。

**在本作品中的角色**：作品将 D-810-ng 作为**可选（optional）** 能力接入，而非必需依赖——因为 IDA/Hex-Rays 是商业软件，不能要求评测环境必有。是否启用由"使用者本机真实探测"决定：只有检测到可用的 IDA 环境才走该路径，且 **D-810 的命中数与优化前后的伪代码都必须留痕**（进入 CAS 与报告）。作品明确**不宣称具备通用解混淆能力**——它只在有 IDA 的前提下提供一层增强，且其效果以真实留痕为准。

### 2.6 动态验证

**Windows Job Object**

Job Object（作业对象）是 Windows 内核提供的一种**进程组管理机制**，通过 `CreateJobObject` 等 Win32 API 使用。它把若干进程"绑定"到一个 Job 上，由内核统一施加**资源限制**（CPU 配额/亲和性、内存上限、句柄数、进程数等）与**行为约束**（例如禁止子进程逃逸出该 Job）。

它对本作品最有价值的一点是 **`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`**：一旦设置了这一限制，当 Job 的句柄被关闭（无论是程序正常退出还是异常崩溃），内核会**自动终止 Job 内的所有进程**。这解决了 Windows 上长期困扰自动化系统的一个难题——父进程退出后，其派生的子进程/孙进程可能"逃逸"成为孤儿并继续占用资源或执行危险操作。把整个进程树绑到一个 Job 上，就能保证"一次验证运行结束后，其所有子孙进程必然被回收"，这是**可靠进程回收**的标准做法，也常被称为"Windows 上的进程树围栏"。

**在本作品中的角色**：作品的**宿主机验证运行器（VERIFY 阶段）** 用 Job Object 管理目标进程树，据此提供**超时、取消与回收证明**：超时到点即整体终止；用户取消时随 Job 关闭清理；运行结束后可给出"已确认无残留子进程"的证据。但必须划清边界——**Job Object 只负责资源与进程回收，不提供文件系统与网络隔离，它不是沙箱**。作品的动态验证是"在宿主机上运行"，防护等级以《测试与验收方案》的描述为准，绝不能被表述为"隔离执行"。

**libFuzzer / TinyInst**

**libFuzzer** 是 LLVM 生态中的**覆盖率引导模糊测试（coverage-guided fuzzing）引擎**，随 Clang 一同分发。它的形态是"in-process（进程内）"：模糊测试逻辑被编译进目标程序内部，由一个 fuzz 入口反复调用被测函数；它依赖**编译期插桩**（Clang 的 `-fsanitize=fuzzer` / SanitizerCoverage）在运行中采集代码覆盖，再用**变异（mutation）** 策略在反馈引导下不断生成能探索到新路径的新输入，从而高效发现内存越界、断言失败等缺陷。

**TinyInst** 由 Google 开源，是一款**轻量级动态二进制插桩工具**：它能在**不重新编译**的前提下对既有二进制插桩并收集覆盖信息，常用于 Windows 目标（含闭源程序）的模糊测试。与 libFuzzer 的"源码插桩"互补，TinyInst 让"没有源码的二进制"也能被覆盖率引导。

**在本作品中的角色**：**libFuzzer 已接入产品链路**——当运行 `mode=FUZZ` 时，执行器只接受 `WINDOWS_LIBFUZZER_PREBUILT`（预构建 libFuzzer 目标），并按崩溃签名去重、调用 `-minimize_crash` 缩减、用最小输入两次复放。**TinyInst** 仍在评估中（其覆盖输出不能替代完整模糊测试，因此不作为产品能力宣称）。这体现了作品"把设计目标与已完成能力严格区分"的总体原则：已经贯通的写清楚，仍未闭环的显式标注边界。

**Zig（`zig cc`）**

Zig 是一门由 Andrew Kelley 创建、2016 年公开的现代系统编程语言，其设计目标是"成为更好的 C"——无隐式控制流、无隐藏内存分配、编译期代码执行（comptime），以及内置的可选类型（Optional）与错误联合（Error Union）。

但它在本作品中被使用的是它的**另一个身份**：`zig cc` / `zig c++`。Zig 把 Clang/LLVM 打包进自己的发行版，并把 **musl/glibc 头文件与各平台 C 运行时（libc）** 一并内置，因此 `zig cc` 可以作为**一个零外部依赖、开箱即用的 C/C++ 编译器与交叉编译工具链**：无需在目标机上预装完整编译环境，就能把 C/C++ 源码构建为目标平台的可执行文件。这让它成为自动化系统中"可靠获得一个可移植编译器"的实用方案。

**在本作品中的角色**：作品用 `zig cc` 把**源码客体**（C/C++）构建为可执行文件，从而让"只有源码的 C/C++ 项目"也能进入需要可执行目标的分析流程。当前构建使用 **`-O0`（不做优化）**。需要特别澄清一个表述边界：范围标签虽写作 `INSTRUMENTED_BUILD`，但作品**不能据此声称已启用 ASan（AddressSanitizer）插桩**——`-O0` 与"是否插桩"是两回事，实际能力以真实编译命令行与产物为准，这也是作品"描述必须与证据一致"原则的一个具体体现。

### 2.7 前端

**Svelte（Svelte 5）**

Svelte 由 Rich Harris 于 2016 年创建，是一款**"编译器优先（compiler-first）"的前端框架**。它与 React、Vue 的根本差别在于**响应式发生在"构建期"而非"运行期"**：传统框架把一套运行时库（虚拟 DOM、依赖追踪引擎）发送到浏览器，在运行时比对虚拟 DOM 树来决定更新哪些真实 DOM；Svelte 则在**构建阶段**把每个组件**编译**为直接操作真实 DOM 的原生 JavaScript 代码——没有虚拟 DOM，没有通用响应式运行时，因此产物更小（省去框架运行时）、更新更细粒度（编译器精确知道哪个状态变化会影响哪段 DOM）。

Svelte 5（2024 年发布，是本作品所用版本）引入了 **runes** 这一新的响应式原语：`$state`（声明可响应状态）、`$derived`（派生值）、`$effect`（副作用）、`$props`（组件属性）。它们**形似函数调用、实为编译器指令**——编译期被改写为细粒度更新，并且首次可以**脱离 `.svelte` 组件**在普通的 `.svelte.js` / `.svelte.ts` 模块中使用（如把审计状态机封装为一个独立可测的响应式模块）。这一版还改进了事件处理与类型支持，与 TypeScript 配合良好。

**在本作品中的角色**：作品用 **Svelte 5 + TypeScript** 从零构建单机审计工作台。选型理由与作品场景高度契合：前端是**纯本地工具**，不需要 SSR、不需要庞大的框架运行时；而是需要**小体积、少依赖、细粒度更新**——审计过程中会持续收到执行器推送的事件与模型调用流，细粒度更新意味着长列表与实时状态能以低开销渲染。

**Vite**

Vite（法语"快"，读音 /vit/）由尤雨溪于 2020 年创建，是新一代前端**构建与开发服务器**。它针对传统打包器（webpack 等）在大型项目上"启动慢、热更新慢"的痛点是这样解决的：

- **开发时**：不对整个应用预先打包，而是让浏览器以**原生 ES 模块（ESM）** 方式按需请求源码；Vite 只在请求到某个文件时才即时编译它，因此**冷启动几乎是瞬时的**。热更新（HMR）也因此只需精确替换被改动的模块。
- **生产构建**：改用基于 Rust 的 **Rollup（现为 Rolldown）** 做完整打包、Tree-shaking、代码分割与资源优化，输出体积小、可缓存的静态资源。

Vite 还内置了 TypeScript、CSS 预处理器、PostCSS 等的开箱支持，插件生态成熟。

**在本作品中的角色**：作品用 Vite 构建前端，并有意**不引入额外的服务端渲染（SSR）服务**——构建产物是**纯静态资源（HTML/JS/CSS）**，直接由 Rust 控制服务（Axum）一并分发。这样整个系统在部署上只有"一个 Rust 服务 + 一个 SQLite 文件"，无需再维护 Node 服务，符合单机、零运维的设计取向。

**Monaco Editor / Cytoscape.js**

**Monaco Editor** 是微软为 VS Code 编写的**代码编辑器内核**，后被独立成可在浏览器中嵌入的组件。它基于自研的文本模型与渲染层，提供语法高亮（由 TextMate 语法或 Monarch 定义）、行号与折叠、多光标、查找替换、括号匹配、代码跳转与内联提示等 IDE 级能力，并支持按语言注册高亮规则（包括自定义语言）。因为它"把 VS Code 的编辑器搬进浏览器"，在需要展示与阅读真实代码的 Web 应用中是事实标准。

**Cytoscape.js** 是一个开源的**图论（网络）可视化库**，最初面向生物信息学网络分析，后成为通用的关系图渲染引擎。它用图模型（节点 + 边 + 属性）描述数据，提供布局算法（力导向、层级、环形等）、交互（缩放、平移、选中、悬停）与样式映射（按属性决定颜色/大小），适合展示"谁调用谁""谁引用谁"这类拓扑结构。

**在本作品中的角色**：二者分别承担审计工作台的**两类关键视图**——Monaco Editor 用于展示与阅读**源码 / 反编译伪代码**（多语言高亮，便于人工复核），Cytoscape.js 用于渲染**调用关系图**（模块/函数间的调用与引用拓扑，帮助分析者把握整体结构与可疑路径）。它们把后端产出的结构化事实以"人可读"的形式呈现出来，是人工复核环节（REVIEWER）的主要工作界面。

### 2.8 模型服务

**大语言模型（LLM）与 DeepSeek**

大语言模型（Large Language Model, LLM）是基于 **Transformer 架构**、在海量文本/代码上预训练的神经网络，核心机制是**自回归生成**：根据已给上下文逐 token 预测下一个 token 的概率分布。经由大规模预训练 + 指令微调（SFT）+ 偏好对齐（RLHF/DPO 等），LLM 具备了"以自然语言理解与生成代码语义"的能力——这也是它在本作品中能承担"读懂一段伪代码并判断其是否存在漏洞"这一任务的原理基础。

但必须清醒认识其固有局限，这也正是本作品全部设计的出发点：

- **会产生幻觉（hallucination）**——模型可能自信地引用不存在的代码、杜撰函数名或行号、给出无法复现的结论；
- **非确定性**——同一输入可能得到不同输出，因此结论需要可复现的证据，而不是"模型说过"；
- **不具备执行能力**——它只能"读与写文本"，不能真正运行程序或验证可利用性。

DeepSeek 是国内的 LLM 服务提供商，提供与 OpenAI 风格兼容的对话式 HTTP API（`chat/completions` 形态），便于在 Rust 中直接集成。作品当前默认模型标识为 **`deepseek-v4-flash`**。

**在本作品中的角色**：作品通过 DeepSeek 官方 API 接入模型审计，但其**核心设计是把模型当作"不可信的判断者"**：模型只负责阅读代码、提出候选结论（`FindingDraft` / `ReviewDraft`），**不直接执行任何操作**；其每一条输出在入库前都必须通过服务端契约校验——包括引文校验（所引代码必须在快照中真实存在）、字段完整性校验，以及状态机约束（如 `exploitation` 必须保持 `NOT_RUN`）。这套"模型提议、服务端校验"的分工是本作品的技术主线，详见第 4 章。

### 3.2 为什么这样分层

- **模型密钥只在控制服务，且以密文保存**：密钥不下发给执行器，也不进入目标运行环境，避免"被审计对象能拿到模型凭据"这一越权面。当前版本把模型连接凭据用 **Windows DPAPI**（`CryptProtectData`，`credentials.rs`）加密后落库（迁移 `0006_model_settings.sql` 注释明确"只持久化 DPAPI 密文，原始密钥永不进入请求或产物"）；解密缓冲区在释放前逐字节清零。执行器注册表中只保存令牌哈希，不保存明文凭据。
- **执行器不直连数据库**：执行器只能通过协议领任务、回报证据，所有状态变更由控制服务在事务中落库。这样即使执行器崩溃或重放，也不会写出半成品状态。
- **前端生产资源由 Rust 服务直接提供**：省去独立的 Node SSR 服务与数据库服务，把"单机可部署"作为硬约束。

## 4. 关键机制与技术原理


### 4.1 导入与程序建模：统一的"程序单元"抽象

**原理**：无论目标是源码还是二进制，审计流程都需要一个统一的操作对象。作品的做法是把两者都归一为 **程序单元（ProgramUnit）**，从而让下游的审计、复核、报告逻辑不必区分语言与文件形态。

| 目标类型                | 解析技术                    | 产出                              | 已知边界                                         |
| ------------------- | ----------------------- | ------------------------------- | -------------------------------------------- |
| 源码（Python/Go/C/C++） | **Tree-sitter** 多语言语法解析 | 模块、函数、位置、语法分支、保守调用候选            | 动态分派、宏、跨模块关系无法确定时保留"推断/未知"，**不宣称全程序污点分析**    |
| 二进制（PE / ELF）       | **Ghidra Headless** 反编译 | 函数、伪代码、入口/RVA、基本块、P-code、字符串与引用 | 伪代码不是可直接编译的 C；地址映射主要在**函数级**；保留反编译失败与截断的原始日志 |

**导入安全约束**（只读分析不等于运行目标）：

- 源码由浏览器打包或上传 ZIP；HTTPS Git 导入固定最终提交，**不自动执行 hooks、安装脚本或递归子模块**；
- 导入时检查相对路径、符号链接、大小写/Unicode 冲突、文件数量与大小，并记录每一条排除原因（`Exclusion`）；
- 导入结果形成**不可变快照**（Snapshot），源文件、来源/提交与目标哈希三者一致。

**分析结果的强校验**：执行器通过 `AnalysisResult` 回报结构分析结果，服务端在入库前调用 `AnalysisResult::validate(manifest)`，逐项校验：

- `schema_version` 必须匹配；
- 程序单元数 ≤ 50000、边数 ≤ 500000；
- 每个 `unit.key` 非空且全局唯一；
- 每个程序单元的 `path` 必须存在于快照清单内，且语言与文件记录一致；
- 非二进制的行号 / 字节区间必须落在原文件范围内，且 `end_byte - start_byte == code.len()`（**拒绝伪造源码位置**）；
- 二进制的 `address` 必须是合法十六进制 `0x...`；
- 每条边引用的程序单元必须存在；
- 文件覆盖记录必须与清单文件**一一对应**，且单元计数一致。

这一层校验把"执行器编造出快照外的代码"在入库前挡住，是引文可信的前提。

**统一检索接口**：`Corpus` 向内提供 `inspect_target`、`read_unit`、`read_span`、`search_code`、`query_graph`、`scan_rules`、`key_logic_candidates` 七个能力，且查询**限于当前快照**、读取有长度与轮次预算。这既是安全边界，也是成本边界。

**别名映射机制**：为了减轻模型对内部 UUID 的误用，`Corpus` 会把每个程序单元映射为短别名 `U0001`、`U0002`……模型输入输出中只见别名；服务端在调用模型前把真实 ID 换成别名，在收到模型输出后把别名换回真实 ID（`references(value, to_model)`）。这既降低了模型幻觉引用错误 ID 的概率，也避免了内部标识泄露。


### 4.2 加壳与混淆的处理：识别 → 规划 → 受控恢复

这是本作品区别于"只做源码扫描"的同类工具的核心机制。

**第一步：保护识别。**
  
`protection.rs` 检查 PE 节区签名、节区熵值、入口点、导入表等特征，判断目标是否可能被 UPX 打包或遭遇字符串混淆。这里的原理边界必须明确：**签名或高熵只是线索**，既不能证明保护已被处理，也不能证明目标具备"闭源加壳软件"的正式资格。

**第二步：由 REVERSE 智能体提交恢复计划。**
  
模型不直接执行命令，而是提交一份**结构化的恢复计划**（`RecoveryPlan`，最多 8 步）。该结构在领域层用 `#[serde(deny_unknown_fields)]` 定义，**任何未声明字段（例如 `command`）都会在反序列化阶段直接失败**——从数据结构层面根除"模型塞进一条 shell 命令"的可能。服务端在其上再做契约校验：

- `assessment` 非空且 ≤ 8192 字节，`evidence` 非空且 ≤ 16 条；
- 步骤数 ≤ `MAX_RECOVERY_STEPS = 8`；每个步骤必须给出 `reason`；
- 每步引用的 `tool` 必须属于枚举 `RecoveryTool`（`upx` / `floss` / `ghidra` / `ida_d810` / `builtin_strings`），不允许任意命令；
- 每步 `input` 必须属于 `RecoveryInput`（`original` / `unpacked`），即输入只能指向原始目标或已解包产物，不能指向任意路径；
- `profile` 字段仅当工具为 `IdaD810` 时允许出现。

计划通过校验后才创建 `RECOVER` 工作项交给执行器。**模型不能提供任意命令或任意路径**——这是把"提示词注入"和"模型幻觉"挡在执行边界之外的关键设计。

**第三步：受控恢复执行。**

| 能力        | 工具与版本                                              | 技术作用                                       | 边界声明                                                    |
| --------- | -------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------- |
| 解包        | **UPX 5.2.1**（固定摘要）                                | 真实解包，保留原件、派生产物、哈希及节区/入口映射                  | 仅支持 UPX 可处理格式；**派生文件作为后续工具输入，不修改原始目标**                  |
| 字符串恢复     | **FLOSS 3.1.1**                                    | PE x86/x64 模拟执行恢复字符串；另有内建 XOR/Base64 启发式候选 | 恢复结果进入伪代码注释与证据，**不证明全部混淆已还原**                           |
| 反编译与代码级优化 | **Ghidra 12.1.3**；可选**本机 IDA/Hex-Rays + D-810-ng** | 输出伪代码；D-810 按规则优化微码（等价化简）                  | IDA 由使用者提供并**真实探测**；D-810 命中数与优化前后伪代码必须留痕；**不能宣称通用解混淆** |

恢复结果以 `RecoveryResult` 结构回报，服务端校验其 `input_artifact_id` / `input_sha256` / `output_sha256` 与租约及已上传产物一致后才接受；`RecoveredStrings` 同样带 `input_sha256` 与工具标识，用于核验"这份字符串到底是从哪一个字节序列里恢复出来的"。

**设计要点**：恢复产物（伪代码、字符串、映射关系）会自动进入后续的语义审计与报告链路，形成"保护 → 恢复 → 审计"的闭环；而所有失败原因、原始/派生哈希同样留痕，**失败也是证据**。


### 4.3 多智能体协作审计：分角色 + 上下文隔离

**原理**：用多个"角色"分解审计任务，比让一个模型一次答完更可控。作品定义了六个角色，它们**可以共用一个模型服务**（不要求六个不同模型，也不是开发成员 A/B/C 分工）。

| 角色           | 职责                                                      | 关键约束                                              |
| ------------ | ------------------------------------------------------- | ------------------------------------------------- |
| **PLANNER**  | 根据目标、入口与现有结构安排审计优先级                                     | 工具预算被压缩为最多 1 轮（`min(max_tool_rounds, 1)`），只做优先级排序 |
| **REVERSE**  | 二进制任务中识别保护特征、规划 UPX/FLOSS/Ghidra/IDA-D-810 恢复步骤，并评估恢复质量 | 只能提交结构化计划，不能提交命令                                  |
| **AUDITOR**  | 阅读代码、追踪输入/危险操作/防护，提出候选发现与关键逻辑标注                         | 必须引用真实代码与有效行范围                                    |
| **REVIEWER** | **在新上下文中**根据原始代码独立复核，记录支持、反证与不确定性                       | **不继承 AUDITOR 的整段对话**                             |
| **VERIFIER** | 生成受校验的验证配置，或说明"缺少哪些正常运行条件"                              | **不自行写入成功状态**                                     |
| **REPORTER** | 根据已存证据整理解释与修复建议                                         | **不补写执行结果**                                       |

**为什么"独立复核"要新建上下文？**
  
如果让同一个模型带着审计时的推理链去复核，它会倾向于维护自己先前的判断（自我一致性偏差）。作品的做法是让 REVIEWER 只拿**原始代码上下文**重新判断，输出"支持 / 反证 / 不确定"三态结论。但要诚实指出：**同一模型即使换上下文仍可能重复同类错误**，因此独立复核必须与"修复版对照 + 真实执行"结合使用，才能作为有效性依据。

**智能体循环的工程约束**（`agents.rs` 的 `conversation`）：

- **工具预算**：每轮对话允许的工具请求数受 `max_tool_rounds` 限制；预算用尽后，即使模型继续请求工具，也会被替换为"无剩余工具请求，请基于已有证据收束"的用户消息，模型不能无限试探。
- **任务幂等**：`begin_agent_task` 对（run, role, item_key）建立唯一任务；若该任务已 `SUCCEEDED` 则直接复用结果，重试不会重复消耗模型调用。
- **完整输出要求**：若模型 `finish_reason != "stop"`（被截断），该轮输出被判为无效并触发修复重试。
- **校验-修复回路**：模型提交的结构化结果先在服务端校验，失败时把**校验错误信息**连同真实上下文回喂给模型要求重出，而不是直接落库或直接丢弃；`repairs` 计数存在，且修复阶段降低 `reasoning_effort`。
- **受限重试**：提供商可重试错误（`ProviderFailure.retryable`）只重试一次，避免无限重试放大成本。

**发现的结构化范式**：
  
每条发现按 `可控输入 → 危险操作 → 防护缺口 → 前提/影响` 四段组织（对应 `FindingDraft` 的 `input_source` / `sink` / `missing_guard` / `preconditions`）。这强制模型说明"漏洞为什么成立"，而不是只给一个位置和一句结论。

**发现合法性校验**（`FindingDraft::validate`）：

- `category` 必须属于 `INJECTION` / `PATH_TRAVERSAL` / `AUTHORIZATION` / `MEMORY_BOUNDS`；
- `severity` 必须属于 `CRITICAL` / `HIGH` / `MEDIUM` / `LOW` / `UNKNOWN`；
- `cwe` 必须是 `UNKNOWN` 或合法的 `CWE-数字`；
- 标题、依据、影响、修复建议均非空且不超长；
- **主位置（`unit_id`）必须在证据列表中至少出现一次**，否则拒绝——防止"结论和证据对不上"。

**引文校验**：服务端从**真实代码与有效行范围**重新生成引文（`domain::audit::evidence`），拒绝外部单元引用、越界位置与伪造引文。具体规则：

- 证据条数须为 1–16 条；
- 引用的 `unit_id` 必须在当前任务可见的程序单元集合内（否则报"引用了当前任务以外的程序单元"）；
- 行范围必须在单元代码行数内，且单次引用跨度 ≤ 100 行；
- 若模型提供了 `quote`，则要求其**与原始代码对应行内容一致**（做去缩进归一化后比对），不一致则拒绝并**把该范围的实际代码回喂给模型**要求纠正；
- 通过校验后，规范化的证据 `quote` **由服务端按原始缩进重新截取**，不采用模型文本。

这是对抗模型幻觉最直接的一层。

**复核的阶段化条件校验**（`ReviewDraft::validate_model`）：模型复核必须分别提供 `INPUT_CONTROL`（输入可控）、`REACHABILITY`（可达性）、`DEFENSE_GAP`（防护缺口）三项评估（各且仅一项），并可附 `EXTRA_PRECONDITION`；每项状态为 `SUPPORTED` / `REFUTED` / `UNKNOWN`。并且：

- 若结论为 `VALIDATED`，则**所有必要攻击条件都不得为 UNKNOWN 或被反证**；
- 若结论为 `REJECTED`，则**至少有一项有原始代码支持的 REFUTED 反证**。

这从结构上禁止了"条件未知却宣布有效"或"没有任何反证却宣布驳回"两种偷懒结论。

**PLANNER 的结构化审计计划**：最新版本把 PLANNER 的输出从"自由文本 + 优先级暗示"收敛为**结构化审计计划**（`AuditPlan`：`approach` 总体思路 + `priorities[]` 逐单元优先级 + `limitations[]` 已知限制）。每一条优先级给 `unit_id` 与 `reason`，因此"为什么先审计这个单元"必须落成可核对的数据，而不是散落在自然语言里。计划随运行持久化，并可通过 RPC 展示（`AuditPlan.svelte`），使"审计策略"本身成为可追溯证据。

**阶段化进度（run phases）**：为避免"运行中刷新页面 / 服务重启后进度归零"，作品把流程状态建模为**持久化阶段**（`domain/progress.rs`）。阶段按运行范围动态定义：

- 纯结构分析 → 1 个阶段（`STRUCTURE`）；
- 审计范围 → 程序结构解析 →（二进制时）逆向与代码恢复 →PLANNER 审计策略 → 逐单元审计与复核 → 验证方案生成 → 结论汇总，共 5–6 个阶段；
- 动态范围（`RUNTIME_VERIFICATION` / `DYNAMIC_TESTING`）→ 单一"动态执行与进程回收"阶段（`RUNTIME`）。

阶段状态**从持久化事实重建**而非内存计数：`workflow_phases` 依据 `agent_tasks` 的角色与状态（`SUCCEEDED` / `RUNNING` / `INTERRUPTED`）、`run.summary` 中的结构产物、以及 `TOOL_PROGRESS` 事件推断每个阶段是 `PENDING` / `RUNNING` / `COMPLETED` / `PARTIAL` / `SKIPPED`。代码注释明确一个关键取舍：**"后续角色已开始"表示前序交错阶段已闭合，但预算不是百分比**——即进度条不撒谎，不把 token 预算消耗当成完成度。此外，服务重启后中断的审计任务被确定性重建为"已完成结果保留、等待恢复"（`INTERRUPTED`），不会凭空重算。

**人工标注与冲突检测**：审计过程中产生的人工标注独立成 `LogicAnnotation`（`AnnotationDraft` + `EvidenceRef`），带 `revision` 修订号与 `annotation_revisions` 历史表，并通过 RPC `CreateAnnotation` / `ListAnnotations` 与前端 `AnnotationsPanel.svelte` 暴露。标注草稿在写入前同样走证据校验（`AnnotationDraft::validate`），保证"人工标签也引用真实代码"。

### 4.4 关键逻辑标定：认证 / 加解密 / 注册

课程要求单独标定这三类关键逻辑。作品的设计原理是把"逻辑标定"与"漏洞发现"**解耦**：

- 认证、加解密、注册标签**独立于漏洞发现**——安全函数同样可以被标注，不预设"必修漏洞"；
- 判定依据来自**三方面共同支撑**：候选模式匹配（`KEY_LOGIC_CLUES` / `clues(unit)`）+ 调用关系图 + 模型语义理解，**不能只按函数名贴标签**；
- 标签带子类型约束：`AUTHENTICATION` → `PASSWORD/SESSION/TOKEN`，`CRYPTOGRAPHY` → `PASSWORD_HASH/HASH/SYMMETRIC/ASYMMETRIC/RANDOM`，`REGISTRATION` → `ACCOUNT`；子类型为空（人工修订）或必须属于对应集合；
- 人工修改带修订号（`revision` 与 `annotation_revisions` 历史表），保留原始证据、冲突检测与历史记录。


### 4.5 证据链与可信约束

这是整套系统的"可信地基"。数据库迁移 `0001`–`0006` 定义了项目、快照、运行、执行器、工作项、工作尝试、产物、程序单元、程序边、工具运行、运行事件、报告导出、请求幂等、模型调用、审计工作流、智能体任务、发现、复核、逻辑标注、标注修订、运行记录，以及（`0006`）**模型设置密文**等表。

| 对象                                          | 必须保持的关系                                                                             |
| ------------------------------------------- | ----------------------------------------------------------------------------------- |
| Project / Snapshot                          | 导入形成不可变版本；源文件、来源/提交与目标哈希一致                                                          |
| Artifact / ProgramUnit / ProgramEdge        | 原始与派生产物分开；源码用文件/行号，二进制用原文件/地址/RVA；**推断边不冒充确定边**（`certainty` 字段）                     |
| AuditRun / WorkItem / AgentTask / ModelCall | 任务、角色、尝试、租约、状态、工具与用量全程可追溯                                                           |
| Finding / Review / LogicAnnotation          | 发现、独立复核、人工修订**分别保存**，引用本任务有效代码与产物                                                   |
| RuntimeRecord / RuntimeResult               | 固定原分析、目标、配置、范围、运行观察与**回收证明**；FUZZ 结果含崩溃签名、缩减与复放记录 |
| ModelSettings（`0006`）                        | 模型连接凭据以 **DPAPI 密文**保存，明文密钥不入库、不下发、解密缓冲区用后清零                     |
| RunEvent / Report                           | 事件有持久化序号（`PRIMARY KEY(run_id, seq)`），按 `after_seq` 补读；报告引用**已保存的事实**，不由浏览器内存或模型口述决定 |

**产物按内容寻址**：`artifacts` 表要求 `sha256` 长度恰为 64，且文件以内容哈希命名落盘（`blob_path(hash)`）。同一份字节只会存一份，同时天然得到完整性校验。

**并发与幂等原理**：

- 所有写操作经过单写锁（`writes` mutex）+ 数据库事务，控制服务是**唯一写入方**；
- 创建请求使用**幂等标识**：`requests` 表以 `(method, request_id)` 为主键记录 `body_hash` 与 `object_id`，重复提交返回同一对象，且**同一 request_id 携带不同内容会被拒绝**；
- 人工修订检查 `expected_revision` 版本号，避免覆盖他人修改；
- 执行器回报时校验 `attempt` 与**租约哈希**（`lease_hash = sha256(lease_token)`，数据库只存哈希），**迟到结果不能覆盖新尝试**；
- **租约超时**：`expire_leases` 把超时未续租的工作置为 `EXPIRED`，且**不会自动重跑**——运行被标为 `FAILED`，错误信息明确写作"旧工具进程回收尚未确认"。这是"宁可失败，不可伪造成功"的取舍；
- 浏览器断线只停止订阅；只有**显式取消**才要求回收进程；
- **`COMPLETED` 表示"工作结束"，不表示"目标安全"**——这是状态语义上刻意保留的边界。

**进程回收的诚实性约束**：

- 没有启动外部进程的工作必须明确记录"无待回收进程"（`processes_reaped` 语义）；
- 启动过但未确认终止的工作**不能伪造回收**；
- 执行器重启时必须先完成旧任务回收或幂等重报，**不能把未知进程状态当作成功**；
- 工作项带 `cleanup_confirmed` 字段，且**一个未确认清理的运行租约会阻塞所有执行器**领取新的运行类工作，避免宿主机上残留进程与新任务叠加。


### 4.6 动态验证与 Windows 运行契约

**原理**：动态验证要回答的是"这条发现能否在真实运行中被观察到"，而不是"能否攻破目标"。

**验证契约**（`domain::runtime`）：

- 固定**正常输入 1 次**（基线，`baseline`）+ **探测输入 2–5 次**（`probe`，`repeats` 校验为 2–5）；
- 单次目标时限 **1–15 秒**；
- 观察器与适配器匹配；Windows 目前**不支持 `RETURN_CANARY`**；
- 运行配置有总大小上限（128 KiB）与测试文件/全局变量数量上限（各 16），并做 `deadline()` 预算换算（`(repeats+1) * (timeout+5) + 150` 秒），使超时可控。

**四种 Windows 产品适配器**：

| 适配器                                                       | 用途                | 边界                              |
| --------------------------------------------------------- | ----------------- | ------------------------------- |
| `WINDOWS_PYTHON_CALL`                                     | 目标 Python 函数的组件验证 | 不支持 globals/kwargs，**拒绝静默丢弃输入** |
| `WINDOWS_NATIVE_SOURCE`                                   | 单入口 C/C++ 构建与执行   | 不能推定所有项目的构建系统都可用                |
| `WINDOWS_ORIGINAL_PE32 / PE64`                            | 匹配架构的原始 EXE 命令行执行 | **不等同于** GUI / DLL / 服务适配       |
| `WINDOWS_LIBFUZZER_PREBUILT`（FUZZ）                        | 预构建 libFuzzer 目标的模糊测试 | 仅接受文件输入；其他引擎格式显式拒绝              |

**两条动态模式**：`mode` 决定运行范围标签——`VERIFY` 对应 `RUNTIME_VERIFICATION`（组件观察与异常复现），`FUZZ` 对应 `DYNAMIC_TESTING`（模糊测试）。执行器在入口处即断言："Windows 产品链当前只支持 VERIFY 或预构建 libFuzzer 的 FUZZ"，其余组合明确报错而非静默降级。

**FUZZ 的崩溃处理闭环**（`domain::runtime` + `executor::runtime`）：

- **崩溃签名去重**：运行结果以 `crash_signature` 标识每个崩溃；服务端用 `BTreeSet` 保证签名唯一，同一签名只保留一份样本，避免"同一缺陷刷满报告"；
- **缩减**：对真实崩溃调用 libFuzzer 的 `-minimize_crash`，产出最小输入；
- **两次复放**：最小输入必须**两次复放均稳定触发**，才记为 `reproduced`，两次结果不一致时作为不确定处理；
- **证据留痕**：保留原始输入、最小输入、各自哈希、缩减日志与复放记录，全部进入证据链；
- **诚实边界**：`TinyInst` 的覆盖输出不能替代完整模糊测试；更广泛目标的构建（自定义 harness、调用约定适配）仍待验收。作品已用 `CVE-2016-5180` 验证该链路：漏洞版触发 ASan heap-buffer-overflow、修复版不崩溃，最小输入由 `a\.` 缩减为 `\.`。

**受限自动利用闭环**：当发现属于二进制 `MEMORY_BOUNDS` 时，可自动复用为 libFuzzer 任务；崩溃后生成**最小输入、Python 复现器与证据 JSON**，并据此更新报告中的利用状态（`exploitation`）。但必须强调其边界：这产出的是**崩溃 PoC（proof-of-crash）**，**不等同于任意代码执行**——因此 `exploitation` 的语义是"已验证到崩溃复现这一层"，而非"已获得代码执行"。

**路径安全**：`target_path` 校验要求路径非空、≤512 字节、不含 `\` `:` `\0` 与换行，且不可包含 `.`/`..` 段——目标路径被强制限制为快照内的相对路径。

**宿主机边界**：`windows_host.rs` 用 **Windows Job Object**（`windows_job.rs`，基于 `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` 限制）管理目标进程树，提供固定输入、超时、取消、环境白名单与临时目录，结果记录的平台为 `WINDOWS_HOST`。回收证明由 `reaping_proof` 生成，且明确：**一个仍然活跃的 Job 不能被当作回收证明**（有对应单元测试）。必须强调：**Job Object 只负责资源与进程回收，不提供文件/网络隔离**——它不是沙箱。因此产品契约要求"只导入和执行有权测试的目标"。

**结论分级**（避免把"跑起来了"当成"漏洞确认"）：

```
组件验证 < 异常复现 / 崩溃 PoC < 任意代码执行（未实现）
```

- **崩溃不能推导任意代码执行**；`exploitation` 最多记录到"崩溃 PoC 已复现"这一层，对未闭环目标**保持 `NOT_RUN`**；
- 当前源码客体的 C/C++ 构建仅使用 **Zig `-O0`**，虽然范围标签写作 `INSTRUMENTED_BUILD`，**不能据此声称已启用 ASan 插桩**；
- 预构建 libFuzzer 的 FUZZ 走 `INSTRUMENTED_BUILD` 范围，但"目标是否真的启用了 sanitizer"仍以真实构建记录为准；
- `RuntimeResult.image_id` 对 Windows 表示执行策略/版本组合摘要，**不是 Docker 镜像 ID**。

## 5. 关键技术选型原理

| 已选方案                           | 选择依据（原理层面）                                       | 不应推导的结论                           |
| ------------------------------ | ------------------------------------------------ | --------------------------------- |
| **Rust + Axum/Tokio**          | 任务状态、并发、证据与进程生命周期可用**显式类型**约束；外部分析工具仍通过进程/API 接入 | Rust 不会自动提高漏洞检出率，也不能替代目标隔离与模型输出校验 |
| **Connect RPC / Protobuf**     | 用一份 `.proto` 契约统一前后端与执行器，普通请求与事件流同构              | pre-1.0 依赖需锁版本；重连补读、幂等、取消仍由应用实现   |
| **SQLite + 按哈希保存产物**           | 单机单操作员场景下，控制服务独占写入即可满足一致性，部署无需独立数据库              | 不宣称具备多用户共享或分布式执行平台的全部能力           |
| **Svelte + TypeScript + Vite** | 面向单机审计工作台从零构建，静态资源由 Rust 服务提供，不引入额外 SSR          | React 同样是可行替代；本项目**没有**框架性能对比成绩   |
| **Python / Java 工具桥接**         | 复用成熟解析、逆向、扫描与运行工具，不重写核心引擎                        | 调用工具 ≠ 对应课程功能已端到端验收               |
| **Windows DPAPI 加密模型凭据**       | 用操作系统级用户绑定加密保护 API 密钥，明文密钥不入库、不下发、用后清零                      | 仅保护"存储与传输"，不替代网络层与模型侧的信任边界               |
| **预构建 libFuzzer 作为 FUZZ 引擎**   | 复用 LLVM 覆盖率引导引擎与其 `-minimize_crash` 能力，避免自研模糊器                     | 只接受预构建文件输入目标；harness 与更广目标适配仍待补               |

**依赖与许可**：所有外部组件按锁定版本接入并保留各自许可。核心依赖包括 Tree-sitter（MIT）、Ghidra 12.1.3（Apache-2.0）、Semgrep CE 1.176.1、UPX 5.2.1、FLOSS 3.1.1、Zig 0.15.2、LLVM/libFuzzer、D-810-ng / D-810、Connect Rust/ES 与 Buffa、Monaco、Cytoscape.js 等。运行包通过 `scripts/notices.py` 生成 `THIRD-PARTY-NOTICES/` 与逐文件 SHA-256 清单。**公开 GitHub 仓库不等于项目自身已选择开源许可证**。

## 6. 与同类方案的比较及自研范围

## 7. 能力边界与已知限制（必读）

作品当前是 **0.2.0 集成中原型**（代码基线 `main / 923e777`），不是课程验收完成版。以下限制是设计文档的一部分，不应在答辩或材料中被隐去：

1. **FUZZ 已接入最小产品链路，但覆盖仍有限**：Windows FUZZ 已支持预构建 libFuzzer 目标的崩溃签名去重、`-minimize_crash` 缩减与最小输入两次复放，并以 `CVE-2016-5180` 完成漏洞/修复对照（最小输入 `\.`）。但更广泛目标的**构建、harness 与调用约定适配**仍待验收；TinyInst 覆盖输出不能替代完整模糊测试。
2. **自动利用仅为受限闭环**：二进制 `MEMORY_BOUNDS` 发现可复用为 libFuzzer 任务并产出崩溃 PoC（最小输入 + 复现器 + 证据 JSON），但这是**崩溃复现**，**不等同任意代码执行**；更广泛目标的利用类型与影响判据仍待扩展。
3. **智能体恢复链与真实模型回归已在本基线复跑**：真实 UPX / FLOSS / Ghidra、本机 IDA 9.1 + D-810-ng、真实 DeepSeek 缺陷/修复对照（漏洞版四类 VALIDATED、修复版 0 条 VALIDATED）均已执行；正式闭源样本仍需复验。
4. **模型上下文与单次输出 token 已不再设置产品上限**：这是最新的设计选择，但意味着成本与延迟更依赖使用者的实际调用策略，作品不对此作性能承诺。
5. **恢复链路一处缺陷已在最新版修复**：FLOSS 返回空字符串集时，曾因上传 0 字节文本工件被服务端拒绝而把恢复步骤误记为 `FAILED`；最新版改为跳过空集（`crates/executor/src/recovery.rs`），恢复步骤的失败判读不再被该问题污染。

## 8. 小结

AegisAudit 的技术原理可以概括为一句话：

> **用工程约束把大模型的能力"关进笼子"，让它只能在没有幻觉余地的证据空间里做判断。**

具体来说：以**不可变快照**固定分析对象，以**统一程序单元抽象**抹平源码与二进制差异，以**受校验的结构化恢复计划**（数据结构层面拒绝任意命令与路径）让智能体处理加壳混淆，以**分角色 + 上下文隔离**的多智能体协作完成审计与独立复核（含结构化审计计划、阶段化进度、攻击前提分项校验与人工标注修订），以**引文校验、状态机、租约与幂等**保证每一条结论都可回溯、不可伪造，以**Windows DPAPI 加密的模型凭据**守住密钥边界，最后以**宿主机受控动态验证（VERIFY / FUZZ）+ 分级结论**把"发现"与"已被证实"严格区分开——崩溃 PoC 到此为止，绝不冒充代码执行。
