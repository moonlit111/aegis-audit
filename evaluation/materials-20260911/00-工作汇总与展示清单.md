# 对照池评测：工作汇总与展示清单

**日期**：2026-09-11 ｜ **系统**：AegisAudit 0.2.0（Rust/Axum + Svelte + Connect RPC + SQLite 的多智能体漏洞挖掘工作台）
**本文档用途**：说明这轮评测做了什么、结果如何、有哪些可以直接展示的材料。所有材料在本目录内自包含。

> **口径先行（诚实声明）**：本轮检验的是系统的**语义审计通道**（AUDITOR/REVIEWER 多智能体），不是规则引擎；全程**盲测**（只喂源码，不喂 CVE 编号/公告/修复信息）；**"修复包零命中"≠"修复版安全"**（覆盖率有限，逐条标注）；任务跑完（COMPLETED）只代表结束，**不代表目标安全**。六项正式软件验收仍是 0/6，本批是能力证据。

## 一、我们做了什么

### 1. 挖掘：从 Git 历史里挖"安全修复对照"（15 对）

- **方法**：把"修复提交"当成 ground truth——**父提交 = 有漏洞的版本，该提交 = 已修复版本**。对 6 个通用开源仓库（llama-cpp-python、FastChat、ollama、DeepSeek-Coder、DeepSeek-V3、DeepSeek-Coder-V2）的约 7,900 个非合并提交，用安全关键词 + diff 防护型改动双通道筛选，得到 312 条候选；再对 deepseek 的 agent 仓库 `deepseek-harness`（9,612 个非合并提交，关键词法在此失效）改用**架构决策记录（ADR）反查**，得 223 条候选。
- **人工核实**：逐条读 `git diff` 判定"父提交确实有该缺陷、该提交确实修掉它"，核实出 **15 对**（9 对通用 + 6 对 harness），同时留档 9 条误报样例用于报告精度（实测精度约 1/3）。
- **产物**：`scripts/mine_security_commits.py`（挖掘工具，本轮新增 `--strict` 口径）、`evaluation/reference/security-commit-pairs-verified.json`（15 对权威数据）。

### 2. 范围裁剪：15 对里 9 对可测

- harness 6 对是 TypeScript 代码，本系统源码通道暂不支持 ts/tsx → 本轮评测**只做 9 对**（3 对 Python + 6 对 Go），按文件规模分三阶段（小 ≤200 行 / 中 200–1300 / 大 >1300）。

### 3. 执行：单文件钉死输入 + 盲测 + 四分列判定

- 每对构造两个输入包：`git show <有洞提交>:<文件>` 和 `git show <修复提交>:<文件>`，打成**单文件 ZIP**（钉死范围，避免大仓库耗尽审计预算造成"没检出"假象）；两包同路径、同配置。
- **判定四分列**（不合并）：命中（类别匹配 + 复核通过 VALIDATED + 引文覆盖目标文件）/ 有候选未成立 / 未检出 / 未覆盖（不算"安全"）；更严一档"**命中改动点**"= 复核通过的证据行落在 git diff 的改动行上。
- **PASS 判据**：有洞版本命中了改动点，且修复版本 0 条命中改动点。
- 全程证据留档：每个 run 的原始审计 JSON、三种格式报告（JSON/HTML/Markdown）、模型调用量与 token 用量。

### 4. 本轮新增的两个工具能力

- `scripts/check_pair_pool.py --rejudge`：**离线复判**——不连服务、不花模型钱，直接按"git diff 改动行 ∩ 复核证据行"重算全部批次判定（本轮 11 个批次复判结果与在线判定一致）。
- `scripts/mine_security_commits.py --strict`：针对大仓库收窄挖掘噪声。实测：harness 上最噪声的通道从 **1245 条压到 13 条**，总候选 2462 → 1230；6 个通用仓库上原 9 对对照**全部保留**（零损伤）。

### 5. 附带验证：deepseek-harness 有洞版本可构建、可启动

- 漏洞版 `19c772f4`（CVE-2026-82533 的载体）：本地 clone → pnpm 11.7.0 / Node 24.15 → 安装、构建成功 → `dsh web` 启动，**127.0.0.1:3080 返回 HTTP 200**（仅监听回环），验证后已关停。为后续把它作为课程"开源大模型软件"名额候选打下环境基础（审计侧仍需 ts 通道）。证据：`03-其他验证/harness-可构建可启动证据.txt`。

## 二、结果如何

### 总表：9 对已核实对照

| 对 | 目标文件 | 类别 | 判定 | 一句话 |
| --- | --- | --- | --- | --- |
| **p01** | llama-cpp-python `llama_chat_format.py` | 注入 | ✅ **PASS** | 系统定位到 **CVE-2024-34359 的修复点**：未沙箱化的 Jinja2 渲染聊天模板（SSTI），2 条复核通过且落在改动点 |
| p02 | llama-cpp-python `llama.py` | 内存越界 | ⛔ 截断 | 运行被实例关停截断（修复包未跑），如实记录不补跑 |

| p04 | ollama `readline/history.go` | 权限 | ✗ 非 PASS | 候选精确指向 `0o666`，但权限类被复核规则压成"未成立"（**规则口径问题，非能力问题**） |
| p05 | ollama `llm/server.go` | 内存越界 | ⛔ 截断 | 同上，运行被关停截断 |
| **p06** | ollama `server/download.go` | 内存越界 | ✅ **PASS** | 命中"HEAD Content-Length 未校验 → Parts 为空 → 越界 panic"，机理与答案完全一致 |
| **p07** | ollama `server/images.go` | 路径遍历 | ✗ 非 PASS | 命中改动点；修复包仍有 2 条复核通过落在改动点——**发现上游修复不彻底**（realpath 仍无目录边界约束） |
| p08 | ollama `auth/auth.go` | 授权 | ✗ 非 PASS | 目标那条被复核驳回；但同文件**找到另一个真实缺陷**：`NewNonce` 未校验长度 → 超大值 panic（DoS），复核通过 |

### 关键数字

| 指标 | 数值 |
| --- | --- |
| 可判定 / 截断 | **7 对可判 / 2 对截断** |
| PASS | **2 对**（p01、p06） |

| 离线复判 | 11 个批次全部重算，与在线判定一致（`03-其他验证/离线复判记录.txt`） |

### 四个系统性发现（评测的"副产品"，同样有价值）

1. **权限/umask/TOCTOU 类缺陷在"源码快照即全部输入"下无法被判定为成立**：复核规则要求所有必要条件有证据，而这类缺陷依赖运行环境前提（如 umask、多用户环境）——评测口径需要为这类单列一档，否则永远计 0（p04 实证）。
2. **服务端健壮性缺陷**：单个审计单元的模型响应校验失败会**中止整轮**（对比：验证方案生成有容错处理）。本轮 12 个失败任务分布在 9 个批次，**8 个批次的覆盖率数字由这个缺陷决定**（最典型：p01 修复包因 1 次复核分歧只审了 1/91 个单元）。这是最值得修的一项。
3. **运行方差**：同一输入两轮结果可不同（p03 修复包首轮 0 条通过、重跑 2 条）——单轮结果不能下死结论。
4. **"零命中"的证据强度受覆盖率限制**：p01 修复包 1/91、p06 修复包 2/19——判定带覆盖缺口备注，不能写成"修复版安全"。

**推荐的 3 分钟展示动线**：② p01（打开 md 报告指出 finding 与证据行 → 对照 diff）→ ⑩ PoC1（终端跑 10 秒看"漏洞版执行/修复版拒绝"）→ ④ p07（修复版里仍有命中，"能评判修复"）→ ⑪ PoC2（浏览器打开两个页面看标题被改写 vs 保持干净）→ ⑥ 随手打开一个 `summary.json` 展示用量与判定 → ⑧ 收尾到 harness（下一步）。

## 五、口径与限制（随材料一起提交）

- 本轮只测**语义审计通道**；规则引擎（Semgrep）对 9 个目标基本不命中，结论不能写成"整条工具链的检出率"。
- 全程**盲测**：审计输入只有源码本身。
- **未覆盖 ≠ 安全**；**任务完成 ≠ 安全**；**修复版零命中 ≠ 修复版安全**（覆盖缺口逐条备注）。
- p05/p02 两对因实例关停**截断**，如实记录、不重跑、不补算。
- 六项正式软件验收 **0/6** 的结论不因本轮结果改变；本轮是"系统能在真实开源代码上定位并复核成立真实缺陷"的能力证据。
