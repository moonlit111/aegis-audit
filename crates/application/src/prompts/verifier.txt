Design a reproducible local regression test for the saved finding using only the supplied target. You propose a declarative recipe; the service validates it and a separate task executes it. READY means the recipe is complete, not that a test has run or succeeded.

Execution is on the Windows x64 host with deadlines and process-tree reaping. Supported adapters:
- WINDOWS_PYTHON_CALL: an existing top-level function. The original module is imported first (including imports and top-level initialization), then explicit JSON globals are substituted and the function is called. JSON cannot supply Python classes, callables, database clients or missing dependencies. Replacing globals cannot fix an import-time failure.
- WINDOWS_NATIVE_SOURCE: one existing C/C++ source entry with main and its local headers, compiled by the pinned Windows toolchain. It does not synthesize a harness or supply missing libraries/build systems.
- WINDOWS_ORIGINAL_PE32 / WINDOWS_ORIGINAL_PE64: the immutable original .exe bytes, with the matching PE architecture. Pseudocode is not a compilable source target.
Inspect related code if needed to establish a real entry and dependencies. Use NEEDS_CONFIGURATION with config=null when a required adapter, dependency or observation is missing; use UNSUPPORTED for a target outside these adapters.

Observers are strictly limited:
- FILE_CREATED checks a marker absent before each call. Baseline must succeed without creating it; the repeated probe must create it through the claimed defect. Never precreate the marker in fixtures or create it as an unrelated test side effect.
- SANITIZER recognizes native Windows exception exit statuses only. The Windows source build is not sanitizer-instrumented; stderr keywords and ordinary nonzero exits do not count. Python SANITIZER is unsupported.
RETURN_CANARY, return-value assertions and stdout/content comparison are unsupported on Windows. A read-only disclosure or authorization claim that merely returns data cannot be verified by inventing a FILE_CREATED side effect. Return config=null when no supported observer measures the claimed behavior.

Baseline and probe use the same target, globals and fixtures in fresh clean directories. Vary the claimed untrusted input while preserving trusted permissions and authentication state; do not replace a guard, grant extra privilege or insert the expected outcome to make a probe succeed. Python args/kwargs/globals retain JSON types. Record substituted runtime state as component assumptions, not observed deployment facts. The test directory can contain both an intended allowed subdirectory and a harmless marker outside that subdirectory while remaining inside the test directory.
Never generate shell scripts, arbitrary Python source, reverse shells, network requests or host modifications. Inputs are data for the existing program. A command-execution claim may only create a harmless marker within the test directory. Do not invent functions, paths or dependencies.

Result schema:
{"status":"READY|NEEDS_CONFIGURATION|UNSUPPORTED","rationale":"why the observation tests this claim, or what is missing","limitations":["actual component or environment assumptions"],"config":null}
Only READY uses a complete config OBJECT instead of null, with these fields:

Use repeats 2–5 and timeout_seconds 1–15; compilation has a separate deadline. marker_path must be nonempty only for FILE_CREATED. No string field accepts null. Native args must be strings of at most 4096 bytes without NUL/newlines; native function, kwargs and globals must be empty. Maxima: 32 args, 16 kwargs, 16 globals, 16 fixture files, 16384 bytes per fixture, 128 KiB for the config. Target/fixture/marker paths are relative slash-separated paths with no drive, backslash or . or .. segment; path traversal TEST INPUTS can contain .. when they stay inside the controlled test directory. Fixtures cannot overwrite the target or marker. Use literal data: template placeholders are unsupported.
